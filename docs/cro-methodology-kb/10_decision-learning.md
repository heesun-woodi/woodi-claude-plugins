# 10. Implement 의사결정·실패학습 — 10단계 후속

> 한 줄 요약: 결과가 나온 뒤 **반영할지(Implement) 말지**를 매트릭스로 결정하고, 반영하지 않는 경우에도 **어느 레벨의 실패인지**를 구분해 다음 액션과 후속 가설로 연결한다. 그리고 그 판정 기록을 조직의 지식 자산으로 남긴다.

---

## 개념·프레임워크

### 1. 이 단계가 하는 일

09 챕터(결과분석)가 "무슨 일이 일어났는가"를 확정한다면, 이 단계는 **"그래서 무엇을 할 것인가"** 를 확정한다.

| 산출물 | 내용 |
|---|---|
| Implement 판정 | Implement / Do Not Implement |
| 운영 반영 방식 | Rollout / Iterate / Stop / Retest |
| 실패 레벨 진단 | 가설 / 솔루션 / 실행 중 어느 레벨의 실패인가 |
| 후속 가설 | 다음 스프린트 백로그로 넘길 가설 |
| 지식 자산 | 레퍼런스 슬라이드·학습 로그 등록 |

### 2. 성공의 정의

> **실험의 성공 기준은 단순히 "지표가 조금 나아졌다"가 아니다. '핵심 성과를 개선하면서 부작용이 없어야' 진정한 의미에서 성공한 실험이다.**

이 정의가 Implement 매트릭스의 전부다.

### 3. Implement 의사결정 매트릭스

Reforge의 "Acting on Test Results" 프레임을 기준으로 한다.

| 상황 | 판단 | 이유 |
|---|---|---|
| **Primary ↑ / Additional + 또는 =** | **Implement** | 핵심 성과 달성 + 부작용 없음 → 안정적이고 확신 있는 결과 |
| **Primary ↑ / Additional ↓** | **Do Not Implement** | 부작용 가능성 존재 → 원인 분석 또는 개선 후 재실험 권장 |
| **Primary = 또는 ↓** | **Do Not Implement** | 핵심 목표 미달성 → 변경 필요 or 실험 설계 재검토 |

용어: **Primary Metric** = 가설 검증의 성패를 가르는 단 하나의 지표. **Additional Metrics** = Secondary + Guardrail.

Implement 조건을 만족한다는 것은:
- ✅ Primary Metric: 통계적으로 유의미하게 개선
- ➕ Additional Metrics: 개선되었거나 비슷한 수준(지표 차이 기준)

#### 왜 이 2가지 case만 Implement 해야 하는가

- 🟢 **핵심 성과 달성** — 실험의 목적 지표(Primary)가 의미 있게 향상됨
- 🟢 **부작용 없음 확인** — 사용자 경험, 유지율, 운영비용 등(Secondary/Guardrail)에서 문제 없음
- 🟢 **조직 관점에서의 의의** — 데이터 기반 의사결정 모델 확립, 실험 신뢰도 상승 → 실험 문화 강화

#### Implement 시 기대효과와 리스크

**✅ 기대효과**

| 항목 | 내용 |
|---|---|
| 확실한 효과 실현 | 실험에서 입증된 개선 효과를 전체 사용자에게 확대 |
| 의사결정의 신뢰 확보 | 통계적으로 설계된 실험 기반 결정은 조직 내/외부에서 설득력 있는 근거 |
| 제품 경험 유지 | 다른 지표에 부정적 영향이 없다 = 사용자 경험을 해치지 않고 개선 달성 |
| 조직 내 실험문화 강화 | 성공 실험의 적용은 실험의 가치를 입증하며 실험 기반 문화에 긍정적 신호 |

**⚠️ 리스크 (극히 낮지만 존재함)**

| 항목 | 내용 |
|---|---|
| 측정되지 않은 영향 | 실험에서 수집하지 않은 영역의 변화는 아직 알 수 없음(예: 특정 세그먼트 반응, 성능 이슈) |
| 일시적 효과일 가능성 | 실험 중에는 효과가 있었지만 장기적으로 사용자 반응이 달라질 수 있음 |
| 기술적 확장 이슈 | 테스트 상황과 실제 운영 환경이 다르면 기술적 문제 발생 가능(성능, 로딩 등) |

> 📌 리스크는 대부분 **모니터링과 점진적 롤아웃**으로 관리 가능하다.

### 4. Additional 지표가 나쁠 때 Implement 하면 생기는 5대 리스크

| 케이스 | 발생 가능한 리스크 | 설명 |
|---|---|---|
| **단기성과 ↔ 장기손해** | LTV 하락, 재방문율 하락 | 단기 지표는 늘었지만 장기 유지율이 떨어질 수 있음 |
| **사용자 경험 악화** | 불만 증가, 이탈률 상승 | 클릭률은 올랐지만 사용자 만족도나 지속성이 악화될 수 있음 |
| **운영 효율 저하** | 비용 상승, 리소스 소모 증가 | 매출은 늘었지만 고객 응대·시스템 부하 등 운영 비용 증가 |
| **지표 간 카니벌라이제이션** | 다른 핵심 기능·서비스의 지표 하락 | 특정 기능의 전환율은 증가했지만 타 기능이 감소 |
| **개선 기회 상실** | 부정 효과를 무시하고 출시 시 개선 여지 상실 | 조금만 수정하면 win-win이 가능한데 조기 출시로 기회를 놓침 |

> **단기적인 유혹에 따라 implement 하기보다, 리스크 요인을 수정·보완한 후 후속 실험으로 이어가는 것이 바람직하다.**

### 5. 실패학습 3레벨 — 어느 레벨의 실패인지에 따라 다음 액션이 다르다

Loss 또는 Inconclusive인 경우, 아래 3레벨로 실패 원인을 분해한다. **이 구분이 없으면 다음 액션이 "다시 해보자"에서 멈춘다.**

| 레벨 | 확인 질문 | 실패 시 회귀 지점 |
|---|---|---|
| **1) 가설 레벨** | 문제 정의가 틀렸는가? / 타겟 세그먼트가 잘못되었는가? / 해결하려던 문제가 실제로는 중요하지 않은가? | 1~2단계(문제영역 선정·문제정의)로 회귀 |
| **2) 솔루션 레벨** | 솔루션의 방향성은 맞으나 구현이 약한가? / 솔루션이 사용자에게 인지되지 않았는가? / 예상치 못한 부작용이 있었는가? | 3단계(솔루션 아이데이션)로 회귀 — 같은 문제, 다른 솔루션 |
| **3) 실행 레벨** | UI/UX 구현이 의도대로 작동하지 않았는가? / 기술적 버그나 오류가 있었는가? / 트래픽 분배가 제대로 이루어졌는가? | 7단계(세팅·QA)로 회귀 — 같은 솔루션, 재구현 후 재실험 |

레벨별 다음 액션 매핑:

| 실패 레벨 | 다음 액션 | 하면 안 되는 것 |
|---|---|---|
| 가설 | 문제 재검증(UT/정량 재분석) 후 문제 우선순위 재산정 | 같은 문제에 다른 솔루션을 계속 던지기 |
| 솔루션 | 같은 문제영역에서 다른 전술로 재아이데이션 | 문제 자체를 폐기하기 |
| 실행 | 구현 수정 후 **동일 설계로 재실험(Retest)** | 결과를 그대로 학습 자산에 등록하기 |

> 가장 흔한 오류: **실행 레벨 실패를 가설 레벨 실패로 오독하는 것.** 트래킹이 깨졌거나 Variant가 일부 환경에서 안 보였는데 "이 가설은 틀렸다"고 백로그에서 지워버리면, 조직은 맞는 가설을 영구히 잃는다.

## 절차

### Step 1. Implement 판정

```
1. Primary가 통계적으로 유의미하게 개선되었는가?
   └─ No  → Do Not Implement (실패 레벨 진단으로 이동)
   └─ Yes ↓

2. Additional(Secondary/Guardrail)이 개선 또는 비슷한 수준인가?
   └─ No  → Do Not Implement (리스크 요인 수정 후 재실험)
   └─ Yes ↓

3. Implement
   → 적용 범위: 실험 시 설정한 타겟·솔루션 그대로
   → 점진적 롤아웃 + 반영 후 모니터링 계획 수립
```

### Step 2. 반영 방식 결정 — Rollout / Iterate / Stop / Retest

| 판단 | 기준 |
|---|---|
| **Rollout** | Primary 개선 + Guardrail 문제 없음 + 비즈니스 해석 가능 |
| **Iterate** | 신호는 있으나 구현/세그먼트/지표 보완 필요 |
| **Stop** | 개선 신호 없음 또는 Guardrail 악화 |
| **Retest** | 데이터/구현/트래픽 문제로 판단 불가 |

판정별 실행 항목:

| 판정 | 실행 항목 |
|---|---|
| Rollout | ① 실험 타겟·솔루션 변경 없이 반영 ② 점진 롤아웃(예: 25%→50%→100%) ③ 반영 후 코호트 모니터링 기간 설정 ④ 실험 코드/플래그 정리 |
| Iterate | ① 어느 레벨(솔루션/구현)의 보완인지 명시 ② 보완된 설계로 후속 실험 설계서 작성 ③ ICE 재평가 후 백로그 우선순위 반영 |
| Stop | ① Loss 원인 3레벨 진단 ② 배움을 학습 로그에 등록 ③ 해당 문제영역의 다음 솔루션 후보 재검토 |
| Retest | ① 데이터/구현 문제 수정 ② **동일 설계로 재실험**(설계 변경 시 재실험이 아니라 신규 실험) ③ 이전 데이터는 폐기 |

### Step 3. 실패 레벨 진단 (Do Not Implement인 경우)

```text
[실패 레벨 진단 시트]

Q1. 우리가 짚은 문제가 실제로 존재했는가?
    근거(정량):
    근거(정성):
    → [ ] 실재 확인   [ ] 불확실   [ ] 문제 아니었음 → 가설 레벨 실패

Q2. 솔루션이 그 문제를 실제로 건드렸는가?
    사용자가 솔루션을 인지했는가(노출·클릭·세션 리플레이):
    → [ ] 건드림   [ ] 인지 안 됨   [ ] 부작용 발생 → 솔루션 레벨 실패

Q3. 구현이 의도대로 전달되었는가?
    QA 로그 / 렌더링 / 트래킹 / 배분:
    → [ ] 정상   [ ] 오류 있음 → 실행 레벨 실패

판정 실패 레벨: [ ] 가설  [ ] 솔루션  [ ] 실행
다음 액션:
```

### Step 4. 후속가설 도출

| 도출 경로 | 방법 | 예시 방향 |
|---|---|---|
| **Win 확장** | 효과가 확인된 솔루션을 다른 타겟·화면에 적용하는 가설 | "같은 솔루션을 다른 진입 지면에 적용하면 동일 효과가 날 것이다" |
| **Win 심화** | 이긴 원인을 더 강화하는 가설 | "인지 개선이 원인이었다면, 인지를 더 강화하면 효과가 커질 것이다" |
| **다음 퍼널 병목** | Primary는 이겼는데 다음 퍼널이 약할 때 | "유입된 고객을 다음 전환까지 이어지게 하는 후속 실험" |
| **세그먼트 특화** | 특정 코호트에서만 효과가 있었을 때 | "해당 코호트를 타겟으로 한 개인화 솔루션" |
| **Loss 전환** | 문제는 맞고 솔루션이 틀렸을 때 | "능동적 행동을 요구하는 솔루션 → 수동적 정보 제공 솔루션으로 전환" |
| **Inconclusive 증폭** | 변화가 인지되지 않을 만큼 미미했을 때 | "같은 방향, 더 큰 변화폭으로 재설계" |

후속가설은 **PSR 한 문장(04 챕터)으로 작성해 ICE(05 챕터, 합산식 최대 30점)로 평가한 뒤 백로그에 넣는다.** 실험 종료 회의에서 후속가설 최소 1개를 도출하는 것을 규칙으로 둔다.

### Step 5. 지식 자산화

실험 1건이 끝날 때마다 아래 3종을 남긴다.

| 자산 | 내용 | 용도 |
|---|---|---|
| **결과보고서** | 09 챕터 4섹션 구조 | 그 실험의 정본 |
| **레퍼런스 슬라이드** | 1장짜리 요약(문제-솔루션-결과-배움) | 다음 실험 아이데이션 시 근거, 신규 인원 온보딩 |
| **학습 로그 엔트리** | 패턴 단위 누적 기록 | 향후 가설의 Confidence 점수 보정 |

#### 학습 로그 시스템 — 왜 실전 판정 기록을 남기는가

가설의 Confidence(ICE의 C)는 "느낌"이 아니라 **과거 실적**에서 나와야 한다. 그러려면 판정 기록이 패턴 단위로 누적되어야 한다.

**패턴 등록 기준**

1. **최소 실험 횟수:** 3회 이상 실험 완료
2. **성공률:** 60% 이상(3회 중 2회 성공)
3. **통계적 유의성:** p-value < 0.05로 성공 판정된 실험만 카운트

**Confidence 보정 규칙**

| 성공률 | Confidence 보정 | 비고 |
|---|---|---|
| 80% 이상 | +2 | 매우 신뢰도 높은 패턴 |
| 60–79% | +1 | 검증된 패턴 |
| 40–59% | 0 | 보통 |
| 40% 미만 | −1 | 주의 필요 패턴 |

**로그에 함께 쌓는 축**

- 도메인/업종별 이력(분석 횟수, 완료 실험, 성공률, 주요 학습)
- 페이지 유형별 통계(Home / Landing / PDP / PLP / Checkout)
- 문제 유형(BIAS 단계 등) 별 성공률
- 주의 필요 패턴(성공률 40% 미만) 목록

> 이 시스템의 실질적 가치는 **"우리 조직에서는 이 유형의 가설이 잘 안 먹힌다"를 데이터로 말할 수 있게 되는 것**이다. 그러면 아이데이션 회의가 취향 논쟁에서 근거 논쟁으로 바뀐다.

## 실무자 흔한 질문 Q&A

### Q1. 실험 결과를 어떤 범위까지 반영해야 하나?

> "특정 타겟 대상 실험이 성공하면 전체 타겟에게 적용해도 될까요? 실험했던 솔루션을 일부 수정해서 반영해도 될까요?"

**A. 실험 시 설정된 타겟과 솔루션 내용을 변경 없이 그대로 적용하는 것이 원칙이다.**

이유:
- **통계적 유의성(Stat-sig 95%)의 의미**: "동일한 실험 조건 하에서 실험을 반복했을 때, 95%의 확률로 유사한 결과를 얻을 수 있다"는 의미다.
- **조건 변경의 위험**: 타겟이나 솔루션을 변경하면 더 이상 '동일한 조건'이 아니다. 결과 재현의 신뢰도가 하락하고 예측 불가능성이 증가한다. 이는 **사실상 데이터 기반 결정이라는 명목하에 검증되지 않은 새로운 가설을 실행하는 것**과 같다.
- **원인 규명의 어려움**: 반영 후 예상과 다른 결과가 나올 경우, 원인이 솔루션 자체인지 변경된 조건 때문인지 판단하기 어렵다.

방안 — **검증 후 확장**:
- 운영 반영 시: 실험 설계 시 정의된 타겟과 솔루션을 최대한 그대로 유지
- 다른 타겟 그룹 또는 수정된 솔루션 적용을 원할 경우: 해당 타겟/솔루션으로 **반드시 별도의 후속 실험을 진행하여 효과를 검증한 후** 적용

### Q2. Stat-sig는 어느 지표까지 필요한가?

> "Secondary나 Guardrail도 통계적 유의성이 나올 때까지 실험을 계속해야 하나요?"

**A. Stat-sig 확보는 Primary Metric에 대해 필수적으로 요구된다. Secondary나 Guardrail은 필수가 아니다.**

이유:
- **지표의 역할 차이** — Primary: 실험 가설 성공 여부 판단의 핵심 기준 / Secondary: 추가적인 긍정적 효과 관찰 / Guardrail: 발생해서는 안 되는 부정적 영향 감지
- **솔루션과의 민감도 및 거리**: Secondary/Guardrail은 Primary보다 솔루션의 직접적 영향에서 멀어 Stat-sig 확보가 더 어렵다.
- **실험 효율성**: 모든 부가 지표의 Stat-sig를 기다리면 실험 기간이 늘고 전체 실험 속도가 저해된다.

방안 — **방향성과 크기를 본다**:
- Primary: 통계적 유의성(예: 95% 신뢰수준) 확보를 목표
- Secondary/Guardrail: 유의성은 나오면 좋지만 필수 아님. **'방향성'(긍정/부정)과 '변화의 크기'(무시할 만한 수준인지, 우려할 만한 수준인지)** 를 중점 관찰
- **특히 Guardrail: 통계적으로 유의미하지 않더라도 비즈니스적으로 유의미한 수준의 부정적 변화가 관찰된다면 실행 결정을 재고해야 한다.**

### Q3. Primary Metric을 제대로 설정한 걸까?

**A. Primary Metric은 실험하는 솔루션(변경 사항)이 사용자 행동에 미치는 '직접적인' 영향을 가장 잘 측정할 수 있는 지표여야 한다.**

좋은 Primary Metric의 조건:
- **직접성**: 실험 솔루션과 직접 관련된 사용자 행동
- **민감성**: 솔루션 변화에 민감하게 반응
- **측정 가능성**: 실험 기간 내 충분한 데이터 수집 가능

잘못된 설정의 문제점(예: 너무 후행 지표를 Primary로 설정):
- **낮은 민감도 & 긴 실험 기간**: Stat-sig 확보가 어렵거나 불가능, 실험 속도 저하
- **약한 인과관계**: Stat-sig가 나와도 해당 솔루션이 직접 기여했다고 단정하기 어려움

방안:
- 실험 설계 단계에서 가설과 솔루션을 명확히 정의하고, **이 솔루션이 가장 직접적으로 변화시킬 것으로 기대되는 사용자 행동**을 Primary로 설정(예: 실험 화면 내 액션, 다음 퍼널 진입률)
- 궁극적인 비즈니스 목표 및 후행지표(예: 매출)는 Secondary나 Guardrail로 모니터링
- Primary 적절성에 의문이 들면 팀 내에서 핵심 가설을 재논의·검증

### Q4. Primary 다음 퍼널 지표가 Primary 결과와 반대라면?

> "Primary(예: 배너 클릭률)는 실험군이 우수한데, 다음 퍼널 전환율(예: 기획전 내 구매 전환율)은 실험군이 더 낮습니다."

**A. 실험의 '전체적인 영향력'은 누적 전환율로, 특정 단계의 '원인 진단'은 단계별 전환율로 판단한다.**

이유:
- Primary 개선으로 **'낮은 의도(Low Intent)' 사용자까지 다음 단계로 유입**될 수 있다. 이로 인해 다음 단계의 '단계별 전환율'은 실험군이 더 낮게 나타날 수 있다.
- **누적 전환율**은 실험 시작점부터 목표까지 도달한 사용자의 비율로, 솔루션이 퍼널 전체에 미친 종합적 영향을 보여준다.

방안 — 종합적 판단 & 심층 분석:
1. **1순위: 누적 전환율 변화 확인** — 실험의 전체 성과 평가(예: 진입 → 최종 전환 누적 CVR). 누적 전환율이 개선되었거나 최소한 유지되었다면 실험은 성공적인 것으로 간주 가능
2. **2순위: 단계별 전환율 변화로 원인 파악** — 어느 단계에서 변화가 컸는가
3. 예시 상황(Primary CTR ↑, 다음 단계 CVR ↓): **누적 CVR이 하락했다면 Primary 개선이 질 낮은 트래픽만 증가시킨 것일 수 있으므로 실험 실패 또는 추가 분석 필요**

### Q5. Primary는 Loss인데 Guardrail(최종 전환)이 Win이라면 반영해도 되나?

**A. 반영하면 안 된다. 반영 결정의 최우선 기준은 'Primary Metric의 통계적으로 유의미한 성공(Win)'이다.**

이유:
- Primary Loss = 원래 의도했던 가설이 틀렸거나 솔루션이 효과 없었음을 의미
- **인과관계의 부재**: Guardrail의 긍정적 결과가 해당 실험 솔루션 때문일 가능성은 매우 낮다(외부 요인, 우연 등)
- **잘못된 의사결정 위험**: 효과 없거나 부정적 영향을 미치는 변경 사항을 도입할 수 있다
- Implement 의사결정 기준 위배: 'Acting on Test Results' 매트릭스 상 'Do Not Implement' 또는 '추가 조사 필요'에 해당

방안 — 원칙 준수 & 학습:
- Primary가 Stat-sig Win 조건을 만족하지 못하면, 다른 지표 결과와 관계없이 Implement는 보류하거나 폐기
- 예상치 못한 Guardrail의 긍정적 변화는 원인을 별도로 분석해볼 수는 있다. **단, 이를 해당 실험 솔루션의 효과로 해석해서는 안 된다.**
- 결과가 예상과 달랐다면 가설·솔루션 디자인·Primary 설정 자체에 대한 회고를 통해 다음 실험을 위한 학습 기회로 삼는다

### Q6. 이 "성공"이 일시적인 현상은 아닐까?

A/B 테스트 결과는 특정 기간의 스냅샷일 뿐 장기적 사용자 행동을 완벽히 반영하지 못할 수 있다.

| 현상 | 설명 | 위험 |
|---|---|---|
| **신규성 효과(Novelty Effect)** | 사용자가 단순히 '새롭다'는 이유로 초기에 더 많이 반응 | 장기 가치를 반영하지 않는 일시적 지표 상승 |
| **학습 효과 / 변화 저항(Change Aversion)** | 기존 기능에 익숙한 사용자가 객관적으로 더 나은 새 디자인에 초기 거부감·학습 곡선 | 단기 결과만 보면 **좋은 변경안을 성급히 폐기**하는 오류 |

해소 방법:
- **테스트 기간 연장**: 신규성 효과가 사라지고 학습이 이루어질 충분한 시간 확보
- **사용자 그룹 분리**: 신규 사용자와 재방문 사용자의 결과를 분리 분석(재방문=학습 효과, 신규=신규성 효과에 민감)
- **출시 후 모니터링**: 반영 후에도 코호트 분석으로 시간 경과에 따른 행동 변화를 지속 추적

### Q7. 이 성공이 특정 그룹의 실패를 가리고 있지는 않을까?

전체적으로 '성공'한 결과가 실제로는 중요한 특정 사용자 그룹에게는 '실패'일 수 있다.

- **이질적인 처리 효과(Heterogeneous Treatment Effects)**: 전체 개선 효과는 다양한 세그먼트(신규 vs 재방문, 모바일 vs 데스크톱, 유입 채널 등)에 걸친 매우 다른 성과를 평균 낸 것일 수 있다.
- 세그먼트 무시의 위험:
  - **가치 있는 고객 손실**: 전체적으로는 약간의 개선이지만 가장 충성도 높은 재방문 고객 그룹에서는 전환율이 크게 하락했을 수 있다
  - **기회 상실**: 특정 그룹(예: 모바일)에는 압도적 성공이었지만 다른 그룹의 부진으로 전체가 '무승부'로 나와 개인화 기회를 놓칠 수 있다

해소 방법:

| 시점 | 방법 |
|---|---|
| **사전** | ① 가설 타겟 세분화 — 특정 세그먼트가 다르게 반응하지 않을지 미리 고민해 세그먼트를 구체화한 가설을 세운다 ② 핵심 세그먼트 가드레일 지표를 미리 설정해 모니터링 |
| **사후** | 여러 세그먼트로 나누어 분석하는 것은 유용하나 **'p-해킹' 위험**이 있다. 세그먼트에서 발견된 중요한 결과는 **후속 실험을 통해 검증**하는 것이 이상적. 실험 후 사용자 인터뷰·설문·사용성 테스트로 정성 피드백을 수집하면 큰 도움이 된다 |

### 템플릿 2. Rollout / Iterate / Stop / Retest 판정 기준표

| 판단 | 기준 | 실행 |
|---|---|---|
| **Rollout** | Primary 개선 + Guardrail 문제 없음 + 비즈니스 해석 가능 | 타겟·솔루션 그대로 점진 롤아웃, 반영 후 모니터링 |
| **Iterate** | 신호는 있으나 구현/세그먼트/지표 보완 필요 | 보완 지점 명시 → 후속 설계서 → ICE 재평가 |
| **Stop** | 개선 신호 없음 또는 Guardrail 악화 | 3레벨 실패 진단 → 학습 로그 등록 → 다음 솔루션 후보 검토 |
| **Retest** | 데이터/구현/트래픽 문제로 판단 불가 | 문제 수정 → 동일 설계로 재실험, 이전 데이터 폐기 |

## 워크드 예시

> 아래는 설명을 위해 지어낸 가상 예시다. 업종·수치·발화 모두 실제 사례가 아니다.

### 예시 A. 여행 예약 앱 — Primary Win, Guardrail 미확정 → 연장 후 재판정

- 실험: 숙소 상세의 가격 옆에 「무료 취소 마감일」을 표시. Primary = 객실 선택 진입률.
- 결과: **처치군이 Primary에서 유의하게 Win(상대 +9%).**
- 그러나: Guardrail(예약 완료율)은 처치군이 낮은 방향이었고 **통계적 유의성은 부족한 상태**. 예약 완료 절대 수가 적었다.
- 판정: Implement 매트릭스상 "Primary ↑ / Additional ↓" 가능성 → **즉시 반영 보류.** 실험을 더 진행해 예약 완료 데이터를 쌓고 다시 판단하기로 결정.
- 배움 기록: 표시를 본 사용자 상당수가 객실 선택 직후 취소 규정 팝업을 다시 열었다 → 표시가 진입은 늘렸지만, **취소 조건 자체가 결제 직전의 새 망설임**이 된 것으로 보임.
- 후속가설: 결제 화면 상단에 취소 조건 요약을 다시 보여주는 후속 실험 필요(다음 퍼널 병목 경로).

### 예시 B. 중고 거래 앱 — Primary Win, 다음 퍼널 CVR Loss

- 실험: 홈 피드의 「가격 내림」 상품 카드 강조. Primary = 카드 클릭률.
- 결과: Primary 유의하게 Win(+15%). 그러나 **상품 상세 → 채팅 시작 전환율은 처치군이 −6%.**
- 1순위 확인: **누적 전환율**(홈 진입 → 채팅 시작)은 +3%로 개선 유지.
- 판정: 누적 CVR이 개선되었으므로 실험은 성공적. 단계별 CVR 하락은 **낮은 의도(Low Intent) 사용자까지 유입**된 결과로 해석.
- 결정: **Rollout**(타겟·솔루션 그대로) + 후속가설 "가격만 보고 들어온 사용자를 위한 상세 상단 시세 비교" 백로그 등록.
- 배움: 단계별 CVR 하락만 보고 Loss로 판정했다면 성과를 버렸을 것. **누적 → 단계별 순서로 본다.**

### 예시 C. 도서 구독 앱 — 실행 레벨 실패를 가설 실패로 오독할 뻔한 경우

- 실험: 책 상세에 「이 책을 끝까지 읽은 독자 비율」 표시. 결과 Inconclusive(p=0.27).
- 1차 해석(팀 초안): "완독 정보는 책 선택에 영향을 주지 않는다" → 가설 레벨 실패로 결론, 문제영역 폐기 제안.
- 3레벨 진단 결과: 세션 리플레이 확인 시 **다크 모드에서 표시 문구 색이 배경과 같아 보이지 않았음.** 다크 모드 사용자 비중 약 30%.
- 재판정: **실행 레벨 실패** → Retest. 색상 수정 후 동일 설계로 재실험.
- 재실험 결과: Primary +4.9%, p=0.03으로 Win.
- 배움: **Inconclusive를 만나면 "인지되었는가"를 먼저 확인한다.** 노출조차 되지 않은 솔루션은 가설을 검증한 것이 아니다.

## 코칭 활용 포인트

### 이 챕터를 쓸 세션 유형

- 실험 결과는 나오는데 반영 여부를 매번 회의에서 즉흥 논쟁으로 정하는 조직
- Primary만 보고 반영하는 습관이 있는 조직(가드레일 무시)
- Loss 실험이 그냥 닫히고 학습이 축적되지 않는 조직
- 실험 결과를 "조금 수정해서" 반영하는 관행이 있는 조직

### 수강자 흔한 질문 · 답변

| 질문 | 답변 |
|---|---|
| "Guardrail이 조금 나빠졌는데 무시하면 안 되나요?" | 방향과 크기를 본다. 유의하지 않아도 **비즈니스적으로 유의미한 수준의 악화**면 재고한다. "조금"의 기준은 실험 전에 정해두어야 한다 |
| "실험은 A타겟에 했는데 전체에 적용하고 싶습니다" | 그건 검증되지 않은 새 가설의 실행이다. 원칙은 그대로 적용, 확장은 후속 실험으로 |
| "Loss 실험도 문서를 다 써야 하나요?" | Loss가 학습 밀도가 가장 높다. 최소한 3레벨 진단 시트 한 장은 남긴다. 벤치마크상 중단 실험의 약 절반이 결론 미작성 상태다 |
| "성공했는데 왜 바로 100% 안 하나요?" | 측정하지 않은 영역·기술적 확장 이슈가 남아 있다. 점진 롤아웃 + 반영 후 모니터링으로 관리 가능한 리스크다 |
| "신규성 효과인지 어떻게 아나요?" | 신규 vs 재방문을 분리해 본다. 재방문에서만 초기 급등 후 감쇠하면 신규성 효과 의심. 반영 후 코호트 추적으로 확인 |

### 흔한 실수 (코치가 먼저 짚어줄 것)

1. **Primary Loss인데 Guardrail Win이라고 반영한다** — 인과관계가 없다. 가장 위험한 오류
2. **실험 솔루션을 "조금 다듬어서" 반영한다** — 검증 조건이 깨진다
3. **실패 레벨을 구분하지 않고 "가설이 틀렸다"로 닫는다** — 실행 레벨 실패를 가설 폐기로 오독
4. **후속가설을 종료 회의에서 안 만든다** — 나중에 만들겠다는 후속가설은 만들어지지 않는다
5. **학습 로그를 실험 단위로만 쌓는다** — 패턴 단위로 묶어야 Confidence 보정에 쓸 수 있다

### 세션 진행 팁

- Implement 매트릭스 3행 표는 **세션에서 가장 오래 기억되는 자산**이다. 이 표 하나를 벽에 붙이는 것만으로 반영 논쟁의 절반이 사라진다.
- Q1~Q5(실무자 질문)는 고객사가 실제로 겪는 상황과 1:1로 매칭된다. 세션 전 사전 설문으로 "어떤 의문이 있었나"를 받아 해당 Q만 골라 다루면 몰입도가 높다.
- 실패학습 3레벨은 **고객사의 최근 Loss/Inconclusive 실험 1건을 실제로 진단**시키는 실습으로 진행한다. 예시 C(실행 레벨 오독) 유형이 매우 자주 나온다.
- 학습 로그 시스템은 개념 소개 수준으로 다루고, 도입은 스프린트 운영(11 챕터)과 묶어 제안한다. 처음부터 완전한 시스템을 요구하면 도입되지 않는다. **최소 형태는 "패턴명 / 실험 수 / 성공률 / Confidence 보정" 4열 표 하나다.**
