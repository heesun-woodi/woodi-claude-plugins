# 12. 코칭 프로그램 설계·실험 조직 — 지원 레이어 (코칭)

> 한 줄 요약: 고객사에 CRO 방법론을 이식하는 코칭 프로그램을 어떻게 설계·진단·운영하고, 코칭이 끝난 뒤에도 실험이 굴러가는 조직·문화를 어떻게 남기는가.

11장이 "스쿼드가 실험을 반복하는 법"이라면, 12장은 "그 반복이 가능한 상태로 조직을 끌어올리는 법"이다. 코칭 설계 → 사전 진단 → 세션 운영 → 조직·문화 순으로 다룬다.

---

## 개념·프레임워크

### 1. 코칭 프로그램 표준 구조

기간·예산과 무관하게 유지되는 뼈대는 네 구간이다.

```
Prep-Sprint (진단)  →  Experiment Sprint 반복  →  중간/최종 회고  →  Handover (자산화)
```

| 구간 | 목적 | 핵심 산출물 |
|---|---|---|
| **Prep-Sprint** | 무엇을 코칭할지 데이터로 확정 | 진단보고서, 코칭 과제 정의서, 카운터파트 합의 |
| **Experiment Sprint** | 1스프린트 = 1과제. 실제 실험을 돌리며 과제별 집중 코칭 | 실험설계서, 결과보고서, 과제별 코칭 자료 |
| **회고** | 중간 = 방향 조정, 최종 = 성과 점검·자산 인계 | 회고 기록, 액션아이템, 차기 로드맵 |
| **Handover** | 코치 없이 유지 가능한 상태로 전환 | 운영 SOP, 실험 포트폴리오, 내재화 액션아이템 |

**Prep-Sprint를 생략하지 않는다.** 진단 없이 커리큘럼부터 짜면 "이미 잘하고 있는 것"을 가르치고 "실제 병목"을 놓친다. 특히 이미 실험을 운영 중인 조직에서는 Prep-Sprint가 프로그램 성패를 가른다.

### 2. 기간별 설계 — 7주 / 10주 / 12주

예산과 목표 범위에 따라 세 가지 표준안을 쓴다.

| 구분 | 7주형 (저예산) | 10주형 (중예산·진단 중심) | 12주형 (고예산·내재화) |
|---|---|---|---|
| 목표 | 1사이클 경험 및 학습 | 기존 실험 교정·보강·고도화 | 다회 스프린트 + 완전 내재화 + 플레이북 |
| 대상 조직 | CRO 경험 없음, TF 소규모 | 이미 실험 운영 중 | 스쿼드 체제 확립, KPI 명확 |
| 구조 | Week 0 킥오프 → Week 1~5 1사이클 → Week 6 마무리 | Prep 1주 + Sprint 4회(각 2주) + 중간/최종 회고 워크숍 | Prep 2주 + Main Sprint 4회(8주) + Handover 2주 |
| 투입 인력 | 메인 코치 + 서브 코치 | 총괄 코치 + 메인 코치 (+보조 코치 선택) | 풀 스쿼드 구성 |
| 세션 빈도 | 주 1회 2시간 + 주간 과제 | 스프린트당 집중 코칭 | 주 1회 60분 + 격주 스프린트 리뷰 |
| 실험 목표 | 1건 완주 | 스프린트당 1~2건 | 총 4~6건 이상, 1건 이상 유의미한 결과 |

**예산 대비 목표 조정 원칙**: 예산이 작을수록 "내재화"가 아니라 **"1사이클 경험 및 학습"**으로 목표를 축소한다. 6~7주에 내재화를 약속하면 반드시 미달한다.

| 예산대 | 목표 | 기간 |
|---|---|---|
| 저예산 | 1사이클 경험·학습 (내재화 제외) | 6~7주 |
| 중예산 | 1사이클 완료 + 기본 내재화 | 10~12주 |
| 고예산 | 다회 스프린트 + 완전 내재화 + 플레이북 인계 | 12주 이상 |

#### 7주 커리큘럼 표준 (주차별 투입시간 차등 배분)

저예산 코칭형의 정본. 총 시간은 유지하되 주차별로 차등 배분해 예산을 최적화한다.

| 주차 | 투입 시간 | 세션 주제 | 수강자 과제 |
|---|---|---|---|
| Week 0 | 5h (축소) | 킥오프 + 데이터 분석 방법론 | 전환 퍼널 데이터 분석 |
| Week 1 | 10h (집중) | 실험 영역 선정 + PSR 가설 아이데이션 + 그루밍 | 가설 백로그 작성 |
| Week 2 | 10h (집중) | ICE 우선순위 선정 + 실험 설계서 작성법 | 실험 설계서 작성 |
| Week 3 | 10h (집중) | 설계서 피드백 + 실험 툴 세팅/QA | 실험 세팅 + QA |
| Week 4 | 5h (축소) | 세팅 리뷰 + 런칭 + 모니터링/종료 의사결정 방법론 | 실험 모니터링 |
| Week 5 | 7h | 실험 결과 분석 방법론 + 보고서 작성법 | 결과 분석 및 보고서 작성 |
| Week 6 | 5h (축소) | 보고서 리뷰 + 회고 + 마무리 | 최종 결과 보고서 |

**설계 원리**
- **집중 주차(Week 1~3)**: 가설 아이데이션, 설계서 작성, 실험 세팅이 코칭 효과가 가장 큰 구간
- **축소 주차(Week 0, 4, 6)**: 킥오프·런칭/모니터링·마무리는 상대적으로 적은 시간으로 충분

#### 10주형 — 진단 중심 (이미 실험 중인 조직)

| 단계 | 기간 | 핵심 산출 |
|---|---|---|
| Prep-Sprint (진단) | 1주 | 코칭 과제 정의서 · 카운터파트 합의 |
| Sprint 1 + 코칭과제 1 | 2주 | 과제1 코칭 · 필요 도구 |
| Sprint 2 + 코칭과제 2 | 2주 | 과제2 코칭 · 필요 도구 |
| 중간 회고 | 워크숍 1회 | Sprint 1~2 점검 · 방향 조정 |
| Sprint 3 + 코칭과제 3 | 2주 | 과제3 코칭 · 필요 도구 |
| Sprint 4 + 코칭과제 4 | 2주 | 과제4 코칭 · 필요 도구 |
| 최종 회고 | 워크숍 1회 | 성과 점검 · 산출물 인계 · 차기 로드맵 |

**핵심 원칙: 1 스프린트 = 1 과제.** 진단에서 확정된 과제를 스프린트별로 하나씩 배분해 집중 코칭한다. 과제 4개를 기본으로 하되 진단 결과에 따라 범위·순서는 조정한다.

#### 12주형 — 내재화 중심

| 스프린트 | 주차 | 주제 | 핵심 활동 |
|---|---|---|---|
| Prep Sprint | 1~2주 | 기반 세팅 | 문제정의 워크샵 · Quick Win 실험 1건 선정·설계·실행 · 태깅 현황 점검 · 프레임워크 교육 |
| Sprint 1 | 3~4주 | 체험 학습: 첫 실험 사이클 | Quick Win 결과 분석·의사결정자 보고 · 백로그에서 다음 실험 선정 · 설계서 작성 실습(코치 리뷰) |
| Sprint 2 | 5~6주 | 심화: 병렬 실험 + 분석 역량 | 결과 분석 + 후속 가설 도출 · 실험 2~3건 병렬 · 결과 분석 템플릿 실습 |
| Sprint 3 | 7~8주 | 자립 운영: 코치 의존도 최소화 | 스쿼드 주도 설계(코치는 리뷰만) · 플래닝/리뷰 자체 운영 연습 |
| Sprint 4 | 9~10주 | 완전 자립 + 성과 가속 | 스쿼드 완전 자립 · 세그먼트 전략 업데이트 · 증분 효과 측정 |
| Handover | 11~12주 | 내재화 완성 + 인수인계 | 실험 포트폴리오 정리 · 운영 SOP 문서화 · 내재화 액션아이템 · 최종 리포트 |

**코치 개입도 곡선**: Prep(코치 주도) → Sprint 1(코치 시연 + 함께) → Sprint 2(수강자 주도 + 코치 밀착) → Sprint 3(수강자 주도 + 코치 리뷰만) → Sprint 4(코치 관찰) → Handover(코치 부재 시뮬레이션). 이 곡선을 설계안에 명시해야 "언제까지 코치가 해주나"에 대한 기대가 정렬된다.

**주간 루틴 예시 (12주형)**

| 요일 | 활동 | 상세 |
|---|---|---|
| 월 | 스프린트 플래닝 | 스쿼드 자체 운영: 이번 주 실험 목표·담당·블로커 |
| 화 | 코칭 세션 (60분) | 실험 설계 리뷰, 문제정의 피드백, 프레임워크 적용 실습 |
| 수~목 | 실험 실행/분석 | 스쿼드 자체 작업 |
| 금 | 주간 리뷰 | 진행 점검 + 다음 주 준비. 격주 금요일은 의사결정자 포함 스프린트 리뷰 |

### 3. 3레버 진단 프레임 — 교정 / 보강 / 고도화

**언제 쓰는가**: 이미 실험을 운영 중인 조직. "0에서부터 방법론을 내재화"가 아니라 "지금 하고 있는 것을 진단해 개선"하는 코칭에서 진단 결과를 분류하는 틀이다.

| 레버 | 정의 | 대표 발견 유형 |
|---|---|---|
| **① 교정 (Fix)** | 지금 잘못하고 있는 부분을 바로잡기 | 잘못된 지표 선정 · 부적절한 표본·기간 · 결과 오해석 · 유의성 판단 오류 |
| **② 보강 (Fill)** | 빠뜨리거나 모르고 있던 단계·기준을 채우기 | 누락된 프로세스(문제 validation, 가드레일 지표) · 없는 판단 기준 · 기록되지 않는 산출물 |
| **③ 고도화 (Level-up)** | 이미 하는 것을 더 잘하는 방법을 터득 | 우선순위 정교화 · 실험 설계 심화 · 세그먼트 분석 · 후속 가설 생산 |

**사용법**: 진단에서 나온 발견을 하나씩 세 유형 중 하나로 태깅한다. 태깅 결과가 곧 코칭 과제 리스트가 되고, 스프린트별 배분의 근거가 된다.

- 교정 과제는 **앞 스프린트에 배치**한다. 잘못된 것을 계속하면서 고도화를 배울 수 없다.
- 보강 과제는 교정 직후. 누락 단계를 프로세스에 끼워넣는 작업이다.
- 고도화는 뒤 스프린트. 앞의 둘이 안정된 뒤에 의미가 있다.

**전통 코칭과의 차이**

| | 전통 CRO 코칭 | 3레버 진단 코칭 |
|---|---|---|
| 대상 | 실험을 처음 도입하는 조직 | 이미 실험을 운영 중인 조직 |
| 시작점 | 방법론 교육 | 실제 실험 참관·인터뷰 진단 |
| 커리큘럼 | 사전 확정 | 진단 결과로 확정 |
| 성공 기준 | 1사이클 완주 | 기존 실험의 품질·판단 신뢰도 향상 |

### 4. Mode A(코칭형) vs Mode B(실무형) 판정

스코핑 단계에서 어떤 제안이 맞는지 결정하는 분기다.

| Mode | 조건 | 제안 방향 |
|---|---|---|
| **Mode A — 코칭형** | 고객사 TF가 있고 일하는 방식 내재화가 중요 | 1사이클 경험/학습, 실험 프레임워크 코칭, 플레이북 인계 |
| **Mode B — 실무형** | 실행 리소스가 부족하거나 속도가 중요 | 진단·설계·세팅·분석을 대행/동행, 성과와 산출물 중심 |

**판정 체크리스트**

| 질문 | Mode A 가능성 | Mode B 필요성 |
|---|---|---|
| 실험을 함께 운영할 TF가 있는가? | 높음 | 낮음 |
| 디자이너/개발자/마케터가 참여 가능한가? | 높음 | 중간 |
| 주 1회 이상 그루밍/리뷰에 참여 가능한가? | 높음 | 낮음 |
| 내부자가 직접 실험 툴·분석 도구를 만질 수 있는가? | 높음 | 중간 |
| 당장 실행 리소스가 부족한가? | 낮음 | 높음 |

**추가 판단 질문**
- 이번 프로젝트가 단기 매출/전환 개선 목적이 큰가, 내부 역량 내재화가 더 중요한가?
- "몇 주 안에 작은 증거"가 필요한가?
- 성공 판단 기준은 무엇인가? (실험 런칭 수 / 전환율 개선 / 조직 내재화 / 플레이북 인계)

**제안 메시지 원형**
- Mode A: "마켓핏랩이 대신 실험을 해주는 것보다, 고객사 TF가 1사이클을 직접 경험하면서 CRO·Experimentation 일하는 방식을 익히도록 코칭합니다."
- Mode B: "마켓핏랩이 진단, 실험 설계, 세팅, 검증, 결과 분석을 직접 실행하거나 밀착 지원해 빠르게 작동하는 실험 사이클을 만듭니다."

## 절차

### 절차 A. 사전 진단 (Prep-Sprint)

#### A-1. 사전 질문지 설계

질문지는 **리더용**과 **실무 스쿼드용** 두 종을 따로 만든다. 둘의 관심사가 다르기 때문이다.

**리더용 질문지 — 2파트 구조**

| 파트 | 시점 | 문항 수 | 목적 |
|---|---|---|---|
| Part A | 스코핑 미팅 전 | 7문항 | 프로젝트 범위와 방향을 정하기 위한 핵심 질문 |
| Part B | 킥오프 전 | 5문항 | 코칭 설계 단계에서 필요한 상세 정보 |

Part A 문항 유형:
1. 현재 운영 중인 전체 스쿼드 현황 (이름·미션·구성원·운영 방식: 스프린트 주기, 데일리싱크 여부)
2. 각 스쿼드의 핵심 지표(KPI)와 추적 지표
3. 코칭이 필요한 스쿼드는 어디이고, 성과가 좋은 스쿼드 대비 **어느 프로세스 단계에서** 차이가 나는가
4. 이번 코칭의 목표와 종료 후 '성공' 판단 기준
5. 기간·방식에 대한 선호나 제약조건
6. 직전 코칭(있다면) 중 효과적이었던 것과 아쉬웠던 것
7. 기타 논의 희망 사항 (조직 개편, 협업 구조 변화 등)

Part B 문항 유형:
8. 코칭 대상 스쿼드의 PO 경험 수준, 핵심 지표, 현재 가설 리스트/백로그
9. 최근 실험 사례 1~2건 (가설문·설계·결과·아쉬웠던 점)
10. 기존 코칭 스쿼드의 현재 상황과 방법론 전파 방식
11. 분석/실험 툴, 데이터 접근 환경, 지원부서 협업 구조, 경영진 보고 체계
12. 참고 자료 (설계서·결과 문서·가설 리스트)

**실무 스쿼드용 질문지 — 5섹션 구조**

| 섹션 | 문항 | 목적 |
|---|---|---|
| 1. 우리 스쿼드 소개 | 스쿼드명·미션·구성원 / 핵심 지표(Primary·Guardrail·Secondary 설정 여부) | 현황 파악 |
| 2. 현재 CRO 프로세스 | 아이디어 발굴 → 가설 → 설계 → 실행 → 분석 각 단계를 어떻게 하는가 / 최근 실험 사례 1~2개 | 프로세스 현황 |
| 3. 어려움과 코칭 니즈 | **어려운 단계 체크리스트** + 이번 코칭에서 가장 얻고 싶은 것 | 과제 후보 |
| 4. 실무 환경 | 분석/실험 도구, 데이터 접근 방식, 개발·디자인 리소스 충분성 | 제약 조건 |
| 5. 참고 자료 | 가설 리스트·백로그·설계서·결과 문서 | 산출물 검토 대상 |

**섹션 3의 어려움 체크리스트 (정본)** — CRO 프로세스 단계를 그대로 항목화한다.

```
□ 데이터에서 문제/기회 발견하기
□ 고객 관점에서 문제 정의하기
□ 날카로운 가설 수립하기 (PSR 프레임워크)
□ 가설 우선순위 정하기 (ICE 스코어링)
□ 실험 설계하기 (Primary/Guardrail/Secondary Metric 설정)
□ 실험 결과 분석하기
□ 분석 결과에서 후속 가설 도출하기
□ 기타:
```

**질문지 작성 요령**
- 각 섹션 상단에 **"이전 프로젝트 참고"** 박스를 넣는다. 앞선 프로젝트에서 무엇을 했는지 알려주면 응답의 구체성이 크게 올라간다.
- "정확한 답변이 어려운 항목은 비워두셔도 괜찮습니다"를 명시한다. 빈칸 자체가 진단 정보다.
- 전문 용어(PSR, ICE, Guardrail)를 쓸 때는 반드시 괄호 설명을 붙인다.

#### A-2. 진단 인터뷰 가이드

**운영 원칙**

| 항목 | 기준 |
|---|---|
| 시간 | 1인당 30~45분 |
| 방식 | 반구조화(semi-structured) — 질문 트리를 축으로 하되 실마리는 자유롭게 파고든다 |
| 녹취 | 시작 전 구두 동의 확인 ("진단 목적으로만 사용, 외부 공유하지 않음") |
| 기록 | 인터뷰이 표현을 최대한 **원문 그대로(verbatim)** — 진단보고서 인용에 사용 |
| 톤 | 평가가 아니라 진단임을 먼저 안심시킨다 |

**오프닝 멘트 (그대로 사용 가능)**
> "오늘은 최근에 진행하신 실험 1건을 같이 따라가보면서, 지금 방식이 어떤지 편하게 말씀해주시면 됩니다. 정답을 찾는 자리가 아니라 저희가 정확히 이해하기 위한 자리예요."

**공통 질문 트리 — 프로세스 워크스루 × 3단 탐침**

인터뷰이가 **최근 진행한 실험 1건**을 구체적으로 떠올리게 한 뒤, 점검 대상 프로세스 5단계를 그 실험 기준으로 워크스루한다. 각 단계마다 3단으로 탐침한다.

```
0. 워밍업 — 최근 실험 1건 선정
   "최근 진행하셨거나 진행 중인 실험 중 하나를 예로 들어주시겠어요?"
   "그 실험은 왜 하게 됐나요? (계기, 배경)"

이후 아래 5단계를 이 실험 기준으로 워크스루:

① 사용자 문제 정의
② 가설 근거 그루밍
③ 근거 기반 솔루션 도출
④ 가설 우선순위 평가
⑤ 결과 모니터링·분석

각 단계마다 3단 탐침:
  (a) 지금 어떻게 하는가   — 사실 확인
  (b) 무엇이 어려운가       — 페인 포인트
  (c) 무엇을 바꾸고 싶은가  — 개선 의지·방향
```

**3단 탐침이 중요한 이유**: (a)만 물으면 "문제없이 잘 하고 있다"는 답이 돌아온다. (b)에서 실제 병목이 나오고, (c)에서 그 조직이 스스로 인지한 개선 방향이 나온다. (c)의 답은 코칭 과제 합의 단계에서 저항을 줄이는 근거가 된다.

**필수 탐침 주제 (자연스럽게 안 나오면 반드시 별도로 묻는다)**

1. **가설 수립 방식과 근거** — 누가, 어떤 근거로 세우나? (데이터 기반 / 정성 리서치 기반 / 직관·경험 기반 — 실제 비중은?)
2. **결과 대시보드 해석 방식** — 구체적으로 어떤 지표를 보나? 유의성 판단은 어떻게? 샘플 사이즈·기간 기준이 있나? "이 정도면 됐다"는 확신은 어디서 오나?
3. **AI 활용 방식과 사람별 편차 사례** — 실험 과정에서 AI 도구를 어떻게 쓰나? 같은 질문을 다른 동료가 물었을 때 답이 달랐던 구체적 사례가 있나?
4. **판단 기준이 없어 곤란했던 실제 사례** — 기준이 없어 결정이 늦어지거나 의견이 갈렸던 순간을 에피소드 형태로
5. **실험 산출물의 존재 여부와 형태** — 가설 문서·설계·결과 분석·결정 기록을 어디에 어떤 형태로 남기나? 나중에 다시 찾을 수 있나?

**역할별 변형 섹션** (공통 트리 + 필수 탐침 후 시간이 남으면)

| 대상 | 추가 질문 초점 |
|---|---|
| **의사결정자 (CPO/본부장급)** | 실험 프로그램이 회사의 어떤 목표와 연결되는가 / 실무자 실험 결과를 어떻게 검토·승인하는가, 최종 결정권은 누구에게 / 조직 차원에서 느끼는 가장 큰 갭(방법론? 속도? 신뢰도?) / 실무자 간 실험 품질 편차를 체감하는가 / 이번 코칭으로 조직 차원에서 얻고 싶은 것 |
| **실무 PM/기획자** | 한 실험을 기획부터 종료까지 얼마나 걸리나, 어느 단계에서 병목이 생기나 / 실험 툴 세팅은 직접 하나, 개발자와 어떻게 협업하나 / 동시 실험 운영 시 관리는 어떻게 / 다른 동료·상급자에게 물어보고 싶었지만 못 물어본 것 / 본인만의 노하우·체크리스트가 팀에 공유되고 있나 |
| **마케터 / PJ 담당자** | 마케팅 관점에서 참여하는 실험 유형 / 제품 실험과 마케팅 캠페인이 얽히는 지점의 어려움 / PJ 담당자로서 가장 기대하는 것과 가장 우려되는 것 / PJ 운영 실무(방문 요일, 채널, 데이터 접근 권한) 사전 조율 필요 사항 / 코칭에 도움이 될 정성 데이터(VoC, 리서치, 인터뷰 기록) |

**인터뷰 기록 템플릿** — 종료 직후 정리한다.

**과제 후보 태깅**
| 발견 내용 | 유형 (교정/보강/고도화) | 관련 프로세스 단계 |
|---|---|---|

#### A-3. 진단보고서 구조

진단보고서는 4개 축으로 구성한다: **현행 프로세스 맵 → 문제 카드 → 과제 리스트 → 우선순위**.

```markdown
# 진단보고서

## 1. 진단 개요
- 진단 방법: 인터뷰 N명 + 산출물 검토(가설 문서, 실험 설계, 결과 분석, 결정 기록)
- 진단 기간 / 인터뷰 대상 / 검토한 산출물 목록
  → "왜 이렇게 진단했는가"보다 "무엇을, 어떻게 봤는가"를 사실 위주로

## 2. 현행 실험 프로세스 맵
| 단계 | 현재 방식 요약 | 담당/관여자 | 사용 도구·산출물 |
|---|---|---|---|
| ① 사용자 문제 정의 | | | |
| ② 가설 근거 그루밍 | | | |
| ③ 근거 기반 솔루션 도출 | | | |
| ④ 가설 우선순위 평가 | | | |
| ⑤ 결과 모니터링·분석 | | | |
  → 평가·판단은 3장으로 미루고 여기서는 현황 서술에만 집중

## 3. 발견된 문제 (문제 카드)
### 문제 N. (제목)
- 현상: 무엇이 문제인지 한두 문장
- 근거: 인터뷰 인용 "..." (대상자, 일시) 또는 산출물 검토 결과
- 영향: 실험 품질·속도·신뢰도에 미치는 영향
  → 추정이나 일반론은 배제. 근거는 반드시 인용 또는 산출물로 뒷받침

## 4. 코칭 과제 리스트
| 과제명 | 유형 (교정/보강/고도화) | 대응 문제 | 기대 효과 | 권장 스프린트 |
|---|---|---|---|---|

## 5. 우선순위 제안
| 과제명 | 임팩트 | 시급성 | 실행 난이도 | 제안 우선순위 |
|---|---|---|---|---|
  → "최종 우선순위는 진단 보고 미팅에서 함께 확정합니다"를 명시. 이 표는 논의를 위한 초안

## 6. 부록 — 인터뷰 요약
(대상자별 기록)
```

**설계 의도 3가지**
1. **2장(현황)과 3장(문제)을 분리한다.** 현황 서술에 판단을 섞으면 고객사가 방어적으로 읽는다.
2. **문제 카드는 반드시 인용 근거를 단다.** "그런 것 같다"는 진단은 과제 합의에서 무너진다.
3. **우선순위는 초안으로 제시하고 미팅에서 확정한다.** 코치가 일방적으로 정한 순서는 실행되지 않는다.

**가설 정의 101 — 목차 수준**

| # | 섹션 | 내용 |
|---|---|---|
| 1 | 세션 목표 & 미션 | 목표: 좋은 가설이 무엇인지 이해 / 근거를 뽑는 5가지 도구를 이해하고 활용. 미션: 팀별 실험 가설 5개 도출 |
| 2 | 좋은 가설이란? | 좋은 가설의 4요소 — '한 문장'에 PSR을 명시할 것. Problem(어느 지면·어떤 유저 그룹) / Solution(어떤 방법으로 개선) / Result(어떤 지표를 얼만큼) |
| 3 | 가설 평가지표(ICE)를 먼저 고려하기 | 가설을 쓸 때부터 ICE를 염두에 두면 작성이 쉬워진다 |
| 4 | 근거를 뽑는 5가지 도구 | ① 정량분석 ② 데스크리서치 ③ 유저리서치 ④ 히트맵 ⑤ 내부 전문가 인터뷰 |
| 5 | 실습 | 팀별 가설 5개 도출 |

- 진행 방식: 이론 1시간 + 실습 1시간
- 실험 지면은 서비스의 주요 퍼널 단계로 먼저 정의해두고 시작한다 (예: 메인홈 → PLP → PDP → 구매페이지 → 장바구니 → 로그인 → 주문하기 → 주문완료)

| (휴식) | 10분 | |
| Part 2 | 90분 | 팀별 실습 — 실험설계서 v0.1 작성 → 템플릿 가이드 → 가설 선정 + v0.1 작성 → 공유 → 구체화 → 수정 |

핵심 메시지: **"실험설계서는 모두가 당황스럽지 않게, 구체적으로 예측 가능하도록"** 작성한다. 설계서를 타 부서에 공유하는 상황을 전제로 작성 수준을 정한다.

운영 파트에서는 실험 1건의 전체 타임라인을 번호·구분·담당자·협의 대상·소요기간 표로 그리게 한다. 대규모 조직에서는 실험 1건이 17주가 걸리기도 하며, 그 안에서 **어느 구간이 협의·승인 대기인지**를 눈으로 보게 하는 것이 목적이다.

#### B-3. TF팀 구성 표준

**코칭형 프로젝트 TF팀 (권장)**

| 역할 | 인원 | 주요 책임 |
|---|---|---|
| CRO PM | 1명 | 실험 스프린트 전체 운영, 의사결정, 커뮤니케이션 |
| DA (데이터 분석가) | 1명 | 실험 가설 데이터 분석, 실험 결과 분석 |
| UX 담당자 | 1명 | 실험 솔루션 기획 |
| 엔지니어 | 1명 | 실험 런칭 전 최종 검토 |

**전제 조건 (간소화 버전 — 핵심 2~3개만 명시)**
- 세션에 TF 인원은 반드시 참여 (엔지니어 제외)
- 주간 과제 반드시 수행 — 과제가 지연되면 코칭 일정도 지연된다
- 과제와 산출물은 **TF팀이 직접 작성**한다 (코치가 대신 쓰지 않는다)

> 전제 조건을 10개씩 나열하지 않는다. 많을수록 지켜지지 않고, 지켜지지 않은 조건은 프로젝트 후반에 책임 논쟁의 재료가 된다.

#### B-4. 의사결정자 커뮤니케이션 설계

코칭 대상 조직의 가장 큰 병목이 **기술이 아니라 신뢰**인 경우가 많다. 이때는 커뮤니케이션 자체를 설계 항목으로 다룬다.

| 커뮤니케이션 | 빈도 | 목적 |
|---|---|---|
| 스프린트 리뷰 | 격주 (스프린트 종료 시) | 실험 결과 + 학습 공유, 다음 스프린트 계획 승인. 의사결정자 + 관련 조직 참석 |
| 상급자 싱크 | 주 1회 (기존 구조 유지) | 정의된 문제와 실험 방향 정렬. 코칭 기간에는 성과를 데이터로 공유하는 채널로 활용 |
| 경영진 리포트 | 월 1회 | 실험 성과와 KPI 진척 보고. 데이터 기반 스토리텔링으로 신뢰 구축 |

**신뢰 회복 로드맵 (코칭 초반에 신뢰가 낮은 조직용)**

| 시점 | 액션 |
|---|---|
| 2주 이내 | Quick Win 실험 1건 실행 + 결과 보고. "체계적으로 접근하고 있다"는 증거 제시 |
| 4주 | 첫 스프린트 리뷰에 의사결정자 초청. 실험설계서 + 결과 데이터로 "근거 있는 의사결정" 시연 |
| 8주 | 실험 포트폴리오 공유: 문제정의 → 가설 → 결과의 일관된 스토리. KPI 진척 보고 |
| 12주 | 최종 리포트: 전체 실험 성과 요약 + 세그먼트별 증분 효과 + 향후 자체 운영 계획 |

**Quick Win 설계 규칙**: ICE 상위 가설 중 **개발이 불필요한 것**을 고른다. 임팩트보다 "2주 안에 결과가 나온다"가 우선이다. 첫 실험이 늦어지면 코칭 전체의 신뢰가 늦게 시작된다.

### 절차 C. 제약 조건 대응

코칭 설계에서 반복적으로 마주치는 제약과 표준 대응.

| 제약 | 대응 |
|---|---|
| **개발자 부재** | 개발 불필요 실험 우선 배치(문구·CTA 변경, 요소 순서·배치, 팝업 노출 조건, 랜딩/메시지, 세그먼트별 메시지). 개발 필요 실험은 IT 협업 요청을 플래닝 시점에 사전 정리 |
| **태깅 미비 / 데이터 지연** | Prep에서 기존 태깅된 지표로 Quick Win 설계 + 추가 태깅 요청 목록 병행. 초기 스프린트는 프락시 데이터(서버 로그·내부 DB)로 빠른 확인 → 정교 데이터로 최종 확정하는 **이중 트랙** |
| **DA 부재** | 통계·해석 판단 기준을 문서로 남기는 것을 최우선 과제로. 사람이 아니라 기준이 남아야 함 |
| **보안 제약 (금융·규제 산업)** | 원본 PII를 직접 다루지 않고 집계·이벤트 데이터 범위 내에서 진행. 이 범위를 제안 단계에서 명시 |
| **AI 답변 편차** | "같은 질문에 사람마다 다른 답이 나온 사례"를 진단에서 수집 → 조직 내 판단 기준 문서화를 과제로 |
| **겸업·시간 부족** | 세션 시간을 주차별로 차등 배분. 집중 주차와 축소 주차를 명시해 부하를 예측 가능하게 |

```

□ 실험 플랫폼을 외부에서 구매해 사용한다
□ 우리 조직에는 실험만을 지원하는 조직·역할이 없다
```

## 실험 조직·문화

### 실험 조직 운영의 3대 투자 영역

성숙한 실험 조직이 공통적으로 중요하다고 말하고 실제로 투자하는 세 가지다.

| 영역 | 내용 |
|---|---|
| **Adoption (확산)** | 조직 내 실험 참여자 확대. 코드 배포 자체를 실험화하는 등의 접근으로 실험을 일상화 |
| **Efficiency (효율성)** | 실험당 리소스·비용 감소 → 더 많은 시도 가능. 예: 승인 절차 단축, 회의 간소화 |
| **Trustworthiness (신뢰성)** | 통계적 정확도, 결과 해석 교육, 리플레이 도구 등 신뢰성 확보 |

### 실험 문화의 KPI — 5축

실험 조직의 성숙도를 5개 축으로 측정한다. 조직 진단·목표 설정에 그대로 쓸 수 있다.

| 축 | 설명 | 지표 | 목적 |
|---|---|---|---|
| **Velocity (속력)** | 개발·제작 중이거나 출시된 실험 및 아이디어의 볼륨 | 월/분기별 시작된 실험 수 · 진행 중인 실험 수 · 프로세스에 삽입된 아이디어 수 | 모든 실험이 이기지도 않고 그래서도 안 된다. 속도를 높이면 궁극적으로 더 많은 성공을 거둔다 |
| **Efficiency (효율)** | 프로덕션 사이클을 통과하는 실험의 효율성 | 자원당 실험 시작 개수 · 실험 준비에 걸리는 총 시간 | 팀이 실험을 만드는 데 얼마나 효율적인지 측정·개선 |
| **Quality (품질)** | 비즈니스 지표에 임팩트를 준 실험 또는 유의미한 배움을 남긴 실험의 개수 | 통계적 유의성에 도달한 결과 개수 | 가장 빠른 실험 환경을 갖춰도 결국 성과는 품질에 제한된다 |
| **Depth (심도)** | 가능한 모든 솔루션에 대한 실험의 깊이 | 실험별 평균 베리에이션 수 · 실험별 평균 측정 지표 수 · 실험 시작당 유니크 지면·이벤트 수 | 문제 영역을 충분히 브레인스토밍하고 다양한 후속 가설을 만들어내고 있는지 |
| **Proficiency (숙련도)** | 프로그램 참여 개인의 기준 역량 | 교육 코스 완료 횟수 · 인증 완료 횟수 | 실험 숙련이 높고, 의사결정 방식의 기본으로 이해되는지 |

**코칭에서의 사용법**: 5축 중 고객사가 실제로 측정하는 축이 몇 개인지 세어본다. 대개 Velocity 하나만 세고 있고, Depth와 Proficiency는 전혀 측정하지 않는다. Depth를 측정하기 시작하면 "실험 1개 = 변형 1개" 관성이 깨진다.

### 실험 조직 운영 원칙 — 성숙 단계별

성숙도에 따라 조직이 다뤄야 하는 과제가 달라진다.

**1단계 — 초기 문화 정립 (Foundational Rigor & Culture Building)**

| 원칙 | 내용 |
|---|---|
| 성과 중심 팀 구성 | 팀을 독립적인 실험 엔진(예: 제품 매니저 + 디자이너 + 기술 리드 3인 조합)으로 조직화하고, 기능 로드맵 대신 **달성해야 할 성과(Outcomes)**를 부여 |
| 해결책이 아니라 문제를 테스트 | 가설을 만들고 신속한 실험을 실행. 실패 시에도 학습을 축하하는 심리적 안전 문화 |
| 학습 속도 최우선 | "주당 실행하는 실험 수"를 최우선 지표로. 분기 릴리스 → 매일 실험으로 전환 |
| 실패의 재프레이밍 | 리더가 실패한 실험을 "귀중한 학습"으로 프레이밍해 시스템이 작동하고 있음을 보여준다. 완벽함이 아닌 학습을 정상화 |
| 임원 챔피언 확보 | 리더가 실험을 요구하고 행동으로 모범을 보이는 구조 |
| 초기부터 엄격하게 | 상관관계가 아닌 인과관계를 측정. 시스템 고장 시 AA 테스트로 조직의 신뢰를 회복 |
| 공식 교육 커리큘럼 | 실험 지식을 PM·디자이너·엔지니어 전 직군에 확산하는 사내 교육 프로그램 |

**2단계 — 규모 확장 및 표준화 (Scaling & Standardization)**

| 원칙 | 내용 |
|---|---|
| 셀프서비스 플랫폼 투자 | 데이터 사이언티스트 의존도를 깨기 위해 자체 서비스 실험 플랫폼에 투자 |
| 데이터 챔피언 지정 | 실험에 대한 깊은 이해를 가진 엔지니어링 데이터 챔피언을 지정해 소유권 확립 |
| 지표 중앙 관리 | 데이터 팀이 핵심 지표(Topline Metrics)를 정의·관리 |
| 표준화된 자동 결정 프레임워크 | 모든 제품 팀의 KPI를 매핑. **"볼 수는 있지만 만질 수는 없다"** 원칙으로 P-해킹 방지 |
| 반복(Iteration) 시스템화 | 실험의 80~90%가 실패한다는 현실 위에서 일관된 반복을 유도하는 시스템 구축. 테스트 결과·분석·권장사항을 문서화해 다음 로드맵을 만드는 플라이휠 |
| 실패에 대한 코칭 | 실패하는 테스트에 대해 코칭해 팀이 "더 빨리 지고(lose faster)" 다음 아이디어를 얻게 함 |
| 학습 단위의 전환 | 학습 단위를 개별 테스트에서 **공통 목표를 가진 실험 프로그램**으로 변경 → 개별 테스트 비용과 인지 부하 감소 |
| 10% 아닌 10x | 증분 개선이 아닌 10배 목표로 도전. 선택성(optionality)과 모듈성(modularity)을 코드 베이스에 인코딩 |

**3단계 — 자동화 및 신제품 프로세스 투입**

| 원칙 | 내용 |
|---|---|
| 루프 자동화 | 아이디어 구상부터 분석까지 전체 실험 루프를 자동화. "복사-붙여넣기 자동화"부터 시작 |
| AI에 컨텍스트를 준다 | 아이디어 품질을 높이려면 과거 실험 결과·모범 사례 등 풍부한 컨텍스트를 제공 |
| AI에 근거를 요구한다 | AI에게 Impact/Confidence 점수에 대한 **증거**를 요구하고 인간이 검증 |
| 역할 전환 | 장기적으로 코드 작성자가 아닌 **코드 검토자**가 되는 역할 변화 |
| 병목의 이동 | 엔지니어링 병목이 해소되면 **의사결정이 새 병목**이 된다 |
| 가정 검증 우선 | MVP 구축 전에 가장 중요하면서 증거가 가장 부족한 가정(LOFA)을 찾아내고, 이를 검증할 최소 실험(MVT)을 먼저 만든다 |

### 실험 문화 정착의 전제조건

툴 도입만으로는 실험이 늘지 않는다. 조직 안에 아래 조건이 갖춰져야 한다.

| # | 전제조건 | 없을 때 나타나는 증상 |
|---|---|---|
| 1 | **정성 근거를 확보하는 경로** | 정량 데이터는 넘치는데 "왜"를 몰라 가설이 추측에 머문다 |
| 2 | **가설·변형의 품질 게이트** | "실험 많이 돌리자"는 있지만 약한 가설을 걸러낼 기준·합의 구조가 없어 백로그가 오염된다 |
| 3 | **세그먼트 단위의 판단 습관** | "한 페이지 = 한 winner" 관성. 사용자별로 다른 답이 있다는 전제가 없다 |
| 4 | **사람이 개입할 지점의 명확화** | "AI가 알아서" 기대와 책임 주체 모호가 공존. 반대로 사람이 모든 단계에 붙어 병목이 된다 |
| 5 | **판단 기준의 문서화** | 같은 결과를 사람마다 다르게 읽고, 그 차이를 조정할 기준이 없다 |

**Human-in-the-loop 원칙**: 실험 자동화가 어디까지 가더라도 사람을 끝까지 두는 이유는 네 가지다. ① AI 점수는 신호일 뿐 최종 책임은 사람 ② 조직 KPI·OKR 정렬 판단은 AI가 못 함 ③ 윤리·규제는 부서 간 합의가 필요 ④ AI는 결정이 아니라 결정용 자료를 준비한다. 정리하면 — **AI는 결정을 대신하지 않는다. 결정의 일관성과 속도를 키워줄 뿐이다.**

## 코칭 활용 포인트

### 이 챕터를 여는 시점

- **제안 단계**: Mode A/B 판정, 예산별 목표 조정, 기간별 커리큘럼 선택
- **스코핑 미팅 전**: 사전 질문지 Part A 발송
- **킥오프 직후 1주**: 진단 인터뷰 가이드 + 기록 템플릿
- **진단 보고 미팅**: 진단보고서 4축 구조
- **프로그램 중반**: 조직 성숙도 5축 KPI로 진척 점검
- **Handover**: 실험 조직 운영 원칙 + 문화 정착 전제조건

### 흔한 수강자·고객사 질문

**Q. 3개월이면 실험이 내재화되나요?**
A. 예산과 기간에 따라 목표를 다르게 잡아야 한다. 6~7주면 "1사이클 경험", 10~12주면 "1사이클 완료 + 기본 내재화", 12주 이상이어야 "다회 스프린트 + 완전 내재화"다. 내재화를 짧은 기간에 약속하는 것은 프로젝트를 실패로 설계하는 것이다.

**Q. 우리는 이미 실험을 하고 있는데 코칭이 필요한가요?**
A. 그 경우 커리큘럼형이 아니라 **진단 중심(3레버)** 코칭이 맞다. 방법론을 0부터 가르치는 것이 아니라, 지금 하고 있는 실험을 참관·인터뷰로 진단해 교정·보강·고도화 과제를 뽑아 스프린트별로 하나씩 다룬다.

**Q. 진단 인터뷰에서 다들 "잘 하고 있다"고만 답합니다.**
A. (a) 질문만 하고 있을 가능성이 높다. 3단 탐침의 (b)"무엇이 어려운가", (c)"무엇을 바꾸고 싶은가"를 반드시 붙여라. 그리고 추상적 질문 대신 **최근 실험 1건을 구체적으로 떠올리게 한 뒤** 그 실험을 따라가며 물어라. "일반적으로 어떻게 하시나요"는 일반적인 답을 부른다.

**Q. 코칭 대상 스쿼드가 방어적입니다.**
A. 오프닝에서 "평가가 아니라 진단"임을 명시하고, 진단보고서에서 현황(2장)과 문제(3장)를 분리해 서술하라. 그리고 우선순위를 코치가 확정하지 말고 초안으로 제시한 뒤 미팅에서 함께 확정하라.

**Q. 개발자가 없는데 실험이 가능한가요?**
A. 가능하다. 개발 불필요 실험(문구·CTA, 요소 배치, 팝업 조건, 메시지·랜딩, 세그먼트별 메시지)만으로 첫 사이클은 완주할 수 있다. 오히려 개발자 없는 조직이 레벨 1 실험에 집중하면서 실험 속도가 더 빨라지는 경우도 있다.

### 자주 나오는 실수

| 실수 | 처방 |

## 외부 레퍼런스

진단·조직 파트에 바로 쓸 수 있는 외부 근거만 모았다. 성숙도 모델 4종 비교와 실험 승률 벤치마크는 [00 개요](00_overview.md) 외부 레퍼런스에 있고, 여기서는 **코칭 진단 도구로 어떻게 쓸 것인가**를 다룬다.

> **인용 규칙**: 아래 Speero·Kameleoon·VWO 자료는 CRO 업계 에이전시·플랫폼사가 자체 발행한 **벤더 리서치**다. 표본·방법론 투명성이 낮은 편이므로 킥오프·제안 슬라이드에 인용할 때 **"벤더 리서치"임을 각주로 반드시 병기**한다.

### 1. Speero 5단계 점수 체계 — 자가진단 워크시트의 골격

본 챕터의 3레버 진단(교정·보강·고도화)은 **무엇을 고칠지**를 정한다. Speero 5단계는 **지금 몇 점인지**를 정량화해 진단보고서에 넣을 기준선을 만든다.

| 레벨 | 이름 | 점수 구간 | 특징 |
|---|---|---|---|
| 1 | Beginner (초급) | 0–20% | 실험 여정 시작 단계. 효과적 프로그램에 필요한 기본 요소가 거의 없음 |
| 2 | Aspiring (지향) | 21–40% | 준비에 필요한 일부 요소 확립. 내부 장애물 극복 과제 다수 |
| 3 | Progressive (진행) | 41–60% | 통찰력 중심 실험의 중요성 인식. 기본 실험 프로그램 운영 요소 확보 |
| 4 | Strategic (전략) | 61–80% | 기본·고급 관행 대부분 구현. 실험을 핵심 성장 동인으로 인식하는 조직적 지원 존재 |
| 5 | Transformative (혁신) | 81–100% | 업계 최상위. 잘 정비된 프로그램으로 지속적 성과 창출 |

- Speero는 4개 핵심 영역(원문에는 *"4 key areas required for effective experimentation programs"*로만 명시되어 있고 **영역 이름은 미확인** — 문화/전략/프로세스/기술로 추정)을 기준으로 매년 벤치마크 리포트를 발행한다(2024년판 206개 기업).
- 무료 자가진단 도구를 제공하므로 **킥오프 전 사전 질문지와 함께 고객사에 돌려두면** 진단 인터뷰에서 바로 대조할 수 있다.

> **본 챕터 도구와의 결합 방식**: ① Speero 5단계로 **현재 점수**를 잡고 → ② Kohavi의 Crawl-Walk-Run-Fly를 **고객사에 설명하는 쉬운 언어**로 쓰고 → ③ Optimizely·VWO의 "velocity 병목" 개념을 **다음 단계 액션 제안의 근거**로 붙인다. 세 모델을 각각 다른 용도로 쓰는 것이 하나를 통째로 이식하는 것보다 실무적이다.

출처: [Speero — Experimentation Program Maturity Audit](https://speero.com/experimentation-program-maturity-audit) / [Speero — 2025 Maturity Reports](https://speero.com/experimentation-maturity-program-reports-2025)

### 2. Velocity Trap — 진단의 별도 축

VWO 벤치마크(2025-2026, **벤더 리서치**)는 응답 조직의 **56%가 낮은 월간 테스트 볼륨에서 실행 병목(execution bottleneck)에 갇혀 있다**고 진단하며 이를 "Velocity Trap"으로 명명한다.

진단 단계에서 이 개념을 별도 축으로 다루는 이유: 성숙도 점수가 낮은 조직과 **"점수는 중간인데 볼륨이 안 오르는 조직"**의 처방이 완전히 다르기 때문이다. 후자에는 방법론 교육이 아니라 병목 제거(구현 난이도 하향, 승인 절차 단축)를 처방한다 → [07 세팅·런칭](07_setup-launch.md) 구현 난이도 3레벨.

*(상세 단계 정의·기업 규모별 월간 테스트 수 벤치마크는 이북 다운로드 후 확인 필요 — 랜딩페이지에서는 **확인 불가**)*

출처: [VWO — Experimentation Maturity Benchmark Report](https://vwo.com/ebooks/experimentation-maturity-benchmark-report/)

### 3. 성숙 조직 vs 미성숙 조직 — ROI 설득용 통계

Speero × Kameleoon 공동 리서치 **(벤더 리서치)**. 초기 세일즈·킥오프 미팅에서 "왜 실험 프로그램에 투자해야 하는가"를 설득할 때 쓴다.

| 지표 | 수치 |
|---|---|
| 성숙한 테스팅 프로그램 보유 기업이 유의미한 성장을 이룰 가능성 | **69% 더 높음** |
| 제품·마케팅의 성장 전략이 정렬된 기업의 유의미한 성장 가능성 | **81%** |
| 성숙한 실험 프로그램 중 표준화된 프로세스를 갖춘 비율 | **87%** |
| 중앙화된 지식 저장소(learning repository)가 **없는** 팀 비율 | **50%** |
| 잘 통합된 툴 스택을 가진 팀 비율 | **13%** |
| 2개 이상 시스템이 통합된 팀이 결과 개선을 경험한 비율 | **18% 더 많음** |

> **원문에 정확한 표본 크기·조사 방법론이 명시되어 있지 않다.** 인용 시 "Speero-Kameleoon 공동 리서치(벤더 자체 조사, 방법론 미공개)"로 출처와 한계를 함께 밝힌다.

**진단 인터뷰 질문으로의 변환**: 위 통계 중 뒤쪽 3개(지식 저장소 50%, 툴 통합 13%, 통합 효과 18%)는 그대로 **진단 질문**이 된다.

- "실험 결과를 모아두는 **중앙 저장소**가 있습니까? 지난 분기 실험을 지금 검색할 수 있습니까?"
- "실험 툴 / 분석 툴 / 프로젝트 관리 툴이 서로 연결되어 있습니까, 아니면 사람이 옮겨 붙입니까?"

출처: [Speero — Why mature programs grow faster (Speero × Kameleoon original research)](https://speero.com/post/why-mature-programs-grow-faster-speero-kameleoon-original-research)

### 4. 실험문화 정착의 3대 성공요인 — 조직 진단 인터뷰 설계

본 챕터 "실험 문화 정착의 전제조건" 5가지가 **프로세스 레벨**의 조건이라면, 아래 3가지는 **조직·리더십 레벨**의 조건이다. 진단 인터뷰 질문지 설계에 직접 연결된다.

| # | 성공요인 | 근거 | 진단 질문 |
|---|---|---|---|
| 1 | **경영진 스폰서십·신념** | 톱다운 지원이 없으면 실험이 개별 팀의 부업(side project)에 머문다. Amazon·Booking.com 모두 경영진 신념 확립 이후에야 확산됐다 | "실험 결과를 임원이 직접 보십니까? 실험 때문에 출시를 미룬 적이 있습니까?" |
| 2 | **실패 허용 문화 + 심리적 안전감** | Google **Project Aristotle** — 심리적 안전감이 고성과 팀을 결정짓는 **가장 강력한 단일 요인**. 팀원이 안전하다고 느낄 때 반대 의견 개진·독특한 관점 공유·실패 두려움 없는 리스크 감수가 촉진된다 | "실패한 실험을 **공개적으로 리뷰하는 세션**이 있습니까? 마지막으로 실패를 발표한 사람이 누구입니까?" |
| 3 | **지식 공유 인프라** | 중앙화된 학습 저장소 부재가 성숙도의 가장 큰 격차 지점(팀의 50%가 저장소 없음). 표준화된 프로세스(성숙 프로그램의 87%)와 결합될 때 조직 전체의 학습 복리효과가 발생 | "6개월 전 실험 결과를 지금 5분 안에 찾을 수 있습니까?" |

학술 근거 보강(지식공유): 지식공유는 구성원이 인지적 자원(아이디어·정보·지식)을 획득하는 통로이며, 팀의 심리적 안전감 분위기가 **"심리적 가용성 → 지식공유 행동"** 경로를 강화한다. **리더의 코칭 행동이 구성원의 심리적 가용성을 높여 지식공유를 촉진**한다는 결과가 보고된다 — 코치가 조직에 들어가는 것 자체가 이 경로에 개입하는 행위라는 점에서 코칭 프로그램의 이론적 근거가 된다.

실행 시사점(문헌 공통 권고): **승패와 무관하게 정기적 지식공유 세션을 운영하고, 실패한 실험도 반드시 발표 대상에 포함한다.**

출처: [PMC — Humble Leadership, Psychological Safety, Knowledge Sharing, and Follower Creativity](https://pmc.ncbi.nlm.nih.gov/articles/PMC6156152/) / [AWA Digital — Amazon & Booking.com experimentation culture](https://www.awa-digital.com/blog/truth-about-amazon-booking-experimentation-culture/)

### 5. 기대치 관리 — "선도 기업도 7~8년 걸렸다"

Booking.com은 창립(1997)에서 첫 실험(2004)까지 7년, Amazon은 창립(1994)에서 첫 실험(2002)까지 8년이 걸렸다. 현재 각각 연 24,000건 / 12,000건 이상을 돌린다. 상세는 [00 개요](00_overview.md) 외부 레퍼런스 3절.

> **코칭 오프닝 문장**: *"실험 기술은 이제 누구나 접근 가능합니다. 7.5년을 기다릴 필요가 없다는 게 지금의 유일한 차이입니다."* — 초기 실험 실적이 저조한 고객사의 방어적 반응을 낮추는 데 효과적이다. 본 챕터 코칭 활용 포인트의 "평가가 아니라 진단" 프레이밍과 함께 오프닝에 배치한다.

또한 Kohavi의 반복 주장 — **"아이디어의 성공률은 33%에 불과하다"**, 실패를 실험 프로세스의 필수 요소로 받아들여야 한다 — 를 함께 제시한다. 다만 통계적 유의 승률 벤치마크는 기관별로 12~25% 수준이므로, 수치를 인용할 때는 [00 개요](00_overview.md) 외부 레퍼런스 2절의 표를 근거로 쓴다.
