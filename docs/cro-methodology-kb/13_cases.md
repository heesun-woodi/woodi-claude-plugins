# 13. 케이스 모음 (공개 사례) — 지원 레이어 (교보재)

> 한 줄 요약: 코칭 세션에서 바로 꺼내 쓸 수 있는 실전 케이스. 해외 AI × 실험 사례(케이스 F)와 금융·핀테크·보험 공개 사례(외부 레퍼런스의 케이스 G)를 담았다.

## 이 챕터의 익명화 규칙

공개판은 **공개 자료 기반 케이스만 싣는다.** 고객사 코칭 케이스는 익명화하더라도 싣지 않는다. 케이스 F(공개 컨퍼런스 발표·포스터)와 케이스 G(공개 기사·블로그·컨퍼런스 자료)는 익명화 대상이 아니므로 회사명·발표자명을 그대로 쓰고 출처를 함께 적는다. 케이스 기호(F·G)는 원래 기호를 그대로 쓴다.

> 새 케이스를 추가할 때도 공개 자료로 확인되는 사례만 넣고, 출처(회사명·발표자명·행사명 또는 원문 링크)를 붙인다.

## 케이스 F. AI × 실험 해외 사례 하이라이트

**교보재 용도**: "AI 시대에 실험 조직은 어떻게 바뀌는가" 세션의 사례 뱅크. 아래는 모두 **공개 컨퍼런스 발표·포스터**(Circus London 2026, AI × Experimentation) 기반이므로 회사·발표자 실명을 그대로 인용한다.

#### 1. TomTom — AI가 가설을 쓰는 게 아니라 약한 가설을 거절하게 한다
*Bjarn Brunenberg, Head of Experimentation*

| 항목 | 내용 |
|---|---|
| 진단 | 슬랙에 던져진 raw 아이디어가 2주 뒤에도 가설·지표·세그먼트 없이 방치. 담당자가 매주 4시간 이상 소모 |
| 스택 | 노코드 폼 빌더(Lovable) + Claude(구조화) + n8n(자동화) + Airtable(저장) + Slack(사람 리뷰) |
| 6단계 | 아이디어 제출 → 에이전트가 구조화 → Confidence Score(0~1) 산출 → **Quality Gate(>0.75만 통과)** → Slack 사람 리뷰 → Airtable 저장(팀·날짜·지표·신뢰도 메타데이터) |
| 4축 평가 | ① Success Metrics ② Guardrail Metrics ③ Hypothesis 구조 ④ KPI/OKR 정렬 |
| 임팩트 | raw 아이디어 → 구조화된 실험까지 **2분**. 주당 4시간 회수, 아이디어 제출 2배, **약한 가설의 스프린트 진입 0건** |
| 핵심 문구 | "이 워크플로우의 핵심은 'AI가 가설을 쓰는 것'이 아니라 **'AI가 약한 가설을 거절하는 것'**이다. 0.75 임계값이 곧 백로그의 품질 보증이다." |

**코칭 활용**: ICE 스코어링을 도입한 조직에 "다음 단계"로 보여준다. 점수를 매기는 것과 **점수로 진입을 차단하는 것**은 다르다.

#### 2. Skyscanner — 9단계 실험 프로세스에서 사람이 남기는 결정은 5가지뿐
*Oliver Paton, Flights Product Analytics*

| 항목 | 내용 |
|---|---|
| 진단 | "프로세스가 느리고, 단편화되고, 일관성 없음" — 학습보다 셋업·검증·조율에 시간 낭비 |
| 솔루션 | Human + AI Agent Model — 9단계 표준 워크플로 + AI 자동화 + 내장 품질 체크 + 지속적 지식 capture |
| 9단계 | Discovery → Design → Tech Setup → Creation → QA → Running → Analysis → Conclusion → Launch |
| 인프라 | 자체 실험 플랫폼(월 1억 명 규모, 수백 건 동시 실험) + 자체 Bayesian 의사결정 엔진 |
| 통계 표준화 | 지표를 **Primary(1개) / Guardrail(복수) / Monitoring(복수)** 로 **사전 등록 강제** → 결과 체리피킹 방지 |
| 결과 표시 | ✅ Beats / ❌ Worse / ➖ No conclusive / ⏳ Keep testing (모두 90% HDI 기준) |
| 자동 판정 | Primary가 "Beats control" + 모든 Guardrail이 worse 아님 → Winning |

**9단계 × AI 역할 매트릭스 (요약)**

| 단계 | 사람이 결정 | AI가 자동화 |
|---|---|---|
| Discovery | **무엇을 볼까** | 패턴 탐지, 자연어→SQL, 중복 체크 |
| Design | **가설 핵심** | 가설 구조화, MDE 추천, 지표 3분류 |
| Tech Setup | 측정 정의 | 트래킹 플랜 + 코드 자동 생성 |
| Creation | **변형 컨셉** | 변형 코드, 플랫폼 자동 셋업 |
| QA | 핵심 경로 확인 | 렌더링/이벤트/SRM/접근성 자동 점검 |
| Running | 큰 이상에만 반응 | 일일 Bayesian 갱신, 이상 알림 |
| Analysis | 직관 대조 | 분포·HDI·결정 자동, narrative 생성 |
| Conclusion | **출시/포기 결정** | 학습 카드 저장, 장기 매출 추정 |
| Launch | **ramp 승인** | 점진 롤아웃, 가드레일 회귀 감시 |

**코칭 활용**: "AI를 어디까지 쓸 것인가"를 논의할 때 이 매트릭스를 빈 표로 나눠주고 직접 채우게 한다. 사람이 남기는 5가지 결정을 스스로 정의하는 것이 목적이다.

#### 3. RYZON — "당신이 도구들 사이의 API다"
*Jakob Halm, Customer Journey Lead*

| 항목 | 내용 |
|---|---|
| 진단 | 도구들(프로젝트 관리·실험 툴·분석 툴) 사이의 **coordination tax** = 5단계 수동 작업이 진짜 병목. 병렬 3개 테스트가 한계 |
| 메타포 | 사이클링의 **Domestique** — 우승자를 위해 물·페이스·바람막이를 담당. 본인은 우승 못 하지만 우승자를 만든다 |
| 구성 | 3개 에이전트 — Analytics Agent(시그널 탐지) + 가설→중복체크→티켓 생성 에이전트 + Report Writer(리포트→학습 매핑) |
| 임팩트 | 병렬 테스트 3개 → **5~6개(2배)**, 사람 접점 5곳 → 2곳. **"티켓 가치 없다"로 버려지던 테스트들이 살아남음** |
| 핵심 문구 | "'AI가 실험을 한다'가 아니라 **'AI가 도구들 사이의 풀(glue) 역할을 한다'**. 사람은 두 군데서만 결정하고, 나머지 5단계 컨텍스트 전환은 사라진다." |

**코칭 활용**: 툴을 더 사는 것이 답이 아니라는 사례. 조직에 "당신 하루에서 도구 간 옮겨 붙이는 시간이 몇 시간인가"를 세어보게 한다.

### 해외 사례를 관통하는 3가지 방향

AI 시대 실험 조직의 공통 질문은 하나다 — **"AI로 실험 양·속도가 폭발했다. 그럼 품질은 어떻게 지키나?"** 답은 세 방향으로 갈린다.

| 방향 | 한 줄 | 대표 사례 |
|---|---|---|
| 1. 정성 데이터 근거 확보 | 정량은 AI가 빠르게 붙는데 정성은 아직 사람 손 → AI로 보강 | EchoLogy · Synthetic Users |
| 2. 가설·변형 품질 게이트 | AI가 양을 늘린 만큼, AI로 품질도 점검·거절 | TomTom · Dylan Davis |
| 3. 사람의 개입 지점 최적화 | 전 과정을 자동화하되 결정 순간만 사람에게 | Skyscanner · RYZON · The Initial |

**모든 사례에 깔린 전제 — Human-in-the-loop.** 사람의 개입을 완전히 뺀 사례는 하나도 없었다. 사람을 끝까지 두는 이유 네 가지: ① AI 점수는 신호일 뿐 최종 책임은 사람 ② 조직 KPI·OKR 정렬 판단은 AI가 못 함 ③ 윤리·규제는 부서 간 합의가 필요 ④ AI는 결정이 아니라 결정용 자료를 준비한다.

> **AI는 결정을 대신하지 않는다 — 결정의 일관성과 속도를 키워줄 뿐이다.**

## 케이스 사용 가이드 (코칭 활용 포인트)

### 상황별 케이스 선택

| 코칭 상황 | 꺼낼 케이스 |
|---|---|
| "AI 시대에 실험 조직은 어떻게 바뀌나요" (세션 오프너) | F (해외 사례를 관통하는 3가지 방향) |
| "AI로 실험을 어디까지 자동화하나요" | F (Skyscanner 9단계 매트릭스) |
| "가설 품질을 어떻게 관리하나요" | F (TomTom Quality Gate) |
| "툴을 더 사면 실험이 늘어나나요" | F (RYZON — 도구 간 coordination tax) |
| "분석·리포트 작성이 병목이에요" | F (The Initial — 분석·리포트 자동화) |
| "정성 데이터가 없어요" | F (EchoLogy) · G-2 (뱅크샐러드 — 정량만으로 시작) |
| "AI에게 사용자 인터뷰를 시켜도 되나요" | F (Synthetic Users — 역할 분해) |
| "개인화·다변량 실험을 늘리고 싶어요" | F (Dylan Davis — 가드레일 4축) |
| "실패한 실험을 어떻게 공유하나요" | G-3 (NerdWallet 실패 사례 · Turkey Demo) |
| 금융·보험·상담 연결형 서비스 코칭 | G (아래 「케이스 G 사용 가이드」) |

### 케이스를 쓸 때 지킬 것

1. **출처를 붙인다.** 해외 발표 사례는 회사명 + 발표자명 + 컨퍼런스명, 기사·블로그 사례는 원문 링크. 공개 사례이므로 실명이 오히려 신뢰를 만든다.
2. **수치는 출처의 성격과 함께 말한다.** 벤더·에이전시 블로그의 2차 인용 수치는 "업계에서 반복 보고되는 수준"으로 표현하고 정확값 단정을 피한다.
3. **공개 사례에 코칭 고객사의 상황을 겹쳐 말하지 않는다.** "지금 고객사도 같은 문제입니다"를 외부 자리에서 말하는 순간 고객사가 드러난다.
4. **실패 케이스를 반드시 함께 보여준다.** Win만 나열한 레퍼런스는 신뢰를 잃는다. G-3(NerdWallet)의 실패 사례가 그 역할이다.

## 외부 레퍼런스

외부 공개 자료로 확보한 케이스 묶음이다. 익명화 대상이 아니며, 케이스 F(해외 AI 실험 사례)와 같은 취급을 받는다.

### 케이스 G. 금융·핀테크·보험 외부 공개 사례 묶음

**교보재 용도**: 금융·보험·상담 연결형 서비스 코칭 시의 도메인 사례 뱅크. **모두 공개된 기사·블로그·컨퍼런스 자료 기반**이므로 케이스 F와 마찬가지로 **회사 실명을 그대로 쓴다.**

#### G-1. 토스 '웹뷰인토스' — 외부 이동 제거로 전환율 평균 48% 상승

| 항목 | 내용 |
|---|---|
| 배경 | 기존에는 토스 앱에서 대출·카드를 신청하려면 제휴 금융사 앱을 별도 설치하거나 외부 브라우저로 이동해야 했다 |
| 변경 | 한도 조회부터 신청 완료까지 **전 과정을 토스 앱을 벗어나지 않고** 처리하도록 통합 |
| 결과 | 2023년~2026년 2월 적용 금융사 기준 **전환율 평균 48% 상승.** 1·2금융권 모두 두 자릿수 이상 상승, 저축은행 일부는 **최대 4배 이상** 개선. 현재 30개 금융사가 이 방식으로 운영 |

**배울 점**

- "앱 전환(외부 이동)"이라는 **단 하나의 마찰 지점**이 신청 퍼널 전체 이탈의 핵심 원인이었다. 브랜드가 다른 두 앱 사이의 컨텍스트 스위칭 자체가 전환을 깎는다.
- **상담사 연결 모델에 그대로 이식된다**: 앱 안에서 상담 신청 → 별도 채널(전화·메신저·외부 예약 시스템)로 튕겨나가는 구간이 있다면, 그 이동 자체가 최대 손실 지점일 가능성이 높다.
- 효과가 업권별로 크게 갈렸다는 점도 유의미하다. **브랜드 신뢰가 상대적으로 낮은 카테고리일수록 마찰 제거의 임팩트가 더 크게** 나타났다.

**코칭 활용**: 문제영역 선정(01장) 세션에서 "우리 퍼널에 앱·채널을 벗어나는 구간이 몇 개인가"를 그 자리에서 세게 한다. 대개 본인들도 세어본 적이 없다.

#### G-2. 뱅크샐러드 vs Credit Karma — 단계를 **줄여야** 할 때 vs **쪼개야** 할 때

두 사례를 반드시 **한 세트로** 제시한다. 따로 보여주면 "multi-step이 정답"이라는 잘못된 일반화가 생긴다.

| | **뱅크샐러드 (단계 삭제)** | **Credit Karma (단계 분할)** |
|---|---|---|
| 진단 | Amplitude 퍼널 분석으로 "설치 → 회원가입", "회원가입 → 자산연동" 이탈이 예상보다 크다는 것을 발견 | 모바일 사용자가 긴 단일 페이지 가입 폼을 부담스러워한다 |
| 가설 | 단계를 줄이면 완료율이 오른다 | 화면당 정보량을 줄이면 화면별 "계속할지 말지"의 인지 부담이 줄어든다 |
| 변경 | **회원가입 프로세스 자체를 제거** | 단일 페이지 폼을 **질문 1개당 화면 1개, 총 4단계로 분할** |
| 결과 | 자산 연동 완료 신규 사용자 기준 **퍼널 전환율 30% 이상 상승** | "거의 매번(pretty much every single time)" multi-step이 단일 페이지보다 전환율이 높았다 — 반복 검증된 패턴 |

**두 사례를 관통하는 원칙**: 핵심은 **단계 수가 아니라 단계당 인지 부하**다. multi-step은 "인지 부하를 화면 단위로 쪼갠다"는 원리이지 무조건 단계를 늘리라는 뜻이 아니다. 쪼개기 전에 먼저 물어야 할 질문은 **"이 정보가 다음 단계 진행에 실제로 필요한가"**다.

- 뱅크샐러드의 회원가입은 서비스 제공자에게는 필요하지만 **사용자에게는 가치를 못 느끼는 "행정 절차"**였다. 상담 신청 퍼널의 본인인증·개인정보 동의·상담 목적 선택 등 사업자 편의를 위한 단계가 실제 병목인지 같은 방식으로 점검할 가치가 있다.
- 뱅크샐러드 케이스는 **정성 조사 없이 정량 퍼널 분석만으로 가설을 세우고 실험한** 전형적 Analytics-driven CRO 사례이기도 하다. "정성 데이터가 없어서 시작을 못 한다"는 조직에 반례로 쓴다.

**Credit Karma의 부가 사례 2건** (같은 회사, 구조 변경 없이 효과를 낸 경우)

- **당첨 안내 메시지 수정** — "1회만 당첨 가능"이라는 **신용카드식 멘탈모델** 때문에 재당첨 가능성을 모르고 이탈하는 유저를 발견 → 리더보드에 "몇 번 당첨됐는지"를 명시해 재참여 유도. 사용자의 **도메인 밖에서 학습된 멘탈모델**이 금융 상품 UX 해석에 개입한다는 사례.
- **직업 드롭다운 재정렬** — 알파벳순 → 인기순으로 재정렬해 **선택 소요 시간 50% 감소.**

**코칭 활용**: 03장(솔루션 아이데이션) 세션에서 "폼을 쪼갤까 합칠까" 논쟁이 나올 때 이 대조표를 띄운다. 정답은 둘 중 하나가 아니라 **"어느 단계가 사용자 가치 실현에 필수인가"를 먼저 검증하는 것**이다.

#### G-3. NerdWallet — 실패 사례와 규제 산업의 실험 규범

**드물게 공개된 실패 케이스**라 교보재 가치가 높다. 실패 학습(10장)을 다룰 때 함께 꺼낸다.

| 항목 | 내용 |
|---|---|
| 프레임워크 | **HBML** (Hypothesize–Build–Measure–Learn). "내 생각에는" 식 주장이 아니라 근본 원인 분석 후 가설화하는 것을 조직 규범으로 못박음 |
| 심리적 안전감 장치 | 실패한 실험을 공유하는 **"Turkey Demo"** 운영 |
| **실패 케이스** | 모기지 리드젠 플로우 재설계 — CTA 위치 변경·카피 단순화·숨겨진 정보 노출 등 **여러 변수를 동시에 변경**한 실험. 변형이 "조금이 아니라 크게" 언더퍼폼했으나 **사후 분석으로도 원인을 특정하지 못했다.** 다변량 동시 변경으로 인과관계가 교란(confound)된 것 |
| 이 실패가 남긴 규범 | **"한 번에 하나씩 격리해서 테스트하라"** |
| 규제 산업 가드레일 | **"Don't test what you wouldn't ship."** 트래픽이 적더라도 프라이버시·정보보안·신뢰를 해치는 실험은 애초에 후보에서 제외. 디자인 컴포넌트·스타일 가이드를 사전 구축해 브랜드 일관성 검토가 실험 속도를 늦추지 않게 함 |

**코칭 활용**: 06장(실험 설계)의 "단일 축 변형" 원칙을 가르칠 때 이 실패를 근거로 쓴다. **"여러 개를 동시에 바꾸고 싶은 유혹"은 리드젠 퍼널 실험에서 특히 흔하고, 졌을 때 아무것도 배우지 못하는 결과로 이어진다.** 또 "규제 때문에 실험을 못 한다"는 저항에는 *"이 변형을 이겼다고 해서 그대로 전체 배포해도 문제없는 안인가?"* 한 문장을 실험 설계 전 게이트키핑 질문으로 제시한다.

#### G-4. 상담사 연결형 모델의 지표 트리 — 폼 제출률을 북극성으로 쓰지 마라

보험·금융 상담 연결 서비스처럼 **리드 → 상담 예약 → 상담 완료 → 계약** 구조를 가진 모델에 적용되는 원칙이다.

**업계 퍼널 벤치마크** (독점 웹 리드 기준, 상품군별 편차 있음)

| 구간 | 벤치마크 |
|---|---|
| 접촉률(contact rate) | 70~85% |
| 접촉 대비 상담예약률 | 25~38% |
| 상담 대비 성사율(close rate) | 20~38% |
| **셀프서브 예약**(직접 캘린더 예약) | **38~50%** |
| **콜백 방식**(전화 연결 대기) | **18~25%** |
| 리드 발생 **5분 이내** 첫 연락 시 접촉률 | 70~85% |
| **1시간 경과** 후 접촉률 | **40~55%** |

- 셀프서브 예약이 콜백 대비 유의하게 높다는 점, 그리고 **응답 속도가 1시간만 지나도 접촉률이 급락**한다는 점이 실험 후보를 곧바로 시사한다.
- **No-show(예약 후 불참)가 "숨겨진 최대 비용"**으로 지목된다. 표준 대응은 예약 확정 시 SMS+이메일 준비 체크리스트 발송, 상담 48시간 전 재확인 SMS.

**지표 설계 원칙 (이 케이스의 핵심)**

> **"폼을 줄이면 제출은 늘지만, 자격 있는 리드 비율(qualified-lead rate)과 실제 예약 완료율(booked-call rate)은 가드레일로 유지되어야 한다."**

즉 북극성 지표를 **'폼 제출'이 아니라 '상담 완료' 혹은 '상담 후 계약 전환'에 최대한 가깝게** 두고, 폼 제출률은 가드레일이 아니라 **중간 지표**로 취급한다. 실험 지표 트리는 최소 3단으로 설계한다.

```
제출 → 예약 확정 → 상담 완료 ( → 계약 )
 ↑
 Primary로 쓰되, 아래 두 단계가 같이 오르는지 반드시 함께 본다
```

**폼 제출 전환율만 보고 승패를 판단하면 리드 품질이 나빠지는 로컬 최적화에 빠진다.** → 06장 외부 레퍼런스 2절(지면 근접 지표 vs 최종 전환 논쟁)과 정확히 같은 구조의 문제이며, 본 KB의 해법도 동일하다: **Primary는 상류에, 하류 전환은 Guardrail에 거부권으로.**

#### G-5. 보험·금융 도메인 실험의 구조적 제약 3가지

영국 보험사 CRO 컨설팅 자료 기반. 구체적 수치 케이스는 아니지만 **이 도메인에서만 발생하는 함정**을 정리한다.

| # | 제약 | 대응 |
|---|---|---|
| 1 | **가격 알고리즘 간섭** — 보험사는 보통 4~5개의 가격 산정 알고리즘을 동시에, 계속 튜닝하며 운영한다. A/B 실험과 가격 알고리즘 변경이 같은 트래픽에 겹치면 결과가 오염된다 | 실험 기간 중 어떤 가격 알고리즘 변경이 함께 일어났는지 **반드시 추적**하고, 사후 세그먼트 분석으로 편향 여부를 확인 |
| 2 | **애그리게이터(비교 사이트)별 단계적 롤아웃** | 신기능을 특정 유입 채널에만 우선 노출하고 나머지를 대조군으로 유지 — 가격 변동 등 다른 변수가 해석을 흐리는 것을 방지 |
| 3 | **저빈도 상황에서의 판정** | 전통적 유의성 기준 대신 베이지안으로 "B가 A를 이길 확률 92%" 같은 **확률적 리스크 커뮤니케이션** 사용 → 09장 베이지안 승자확률 해석 기준 표 적용 |

**일반화**: 가격·정책이 자주, 별도로 바뀌는 도메인에서는 **다른 팀(언더라이팅·프라이싱)이 같은 기간에 무엇을 바꾸는지 트래킹하는 것 자체가 실험 설계의 일부**여야 한다. 상담사 연결 모델도 마찬가지 — **영업팀 인센티브·리드 배분 로직이 바뀌는 시점과 실험 기간이 겹치면 결과가 오염된다.** 08장 종료 게이트 G4(외부 이벤트 로그)에 이 항목을 도메인 특화로 추가한다.

**규제 대응 프레임** — 규제가 막는 것은 "실험 자체"가 아니라 **특정 타겟팅 속성**이다.

- 금지 영역: ECOA(인종·성별·종교·출신국가·연령·공적부조 수급 여부), GDPR Art.9(건강정보·인종·정치성향·생체정보) 등 **보호 속성 기반 타겟팅**은 disparate impact(차별적 효과) 소송 리스크가 있다.
- 통과 가능한 타겟팅 4범주: ① **행동 기반**(세션 행동·최근 로그인·거래 빈도) ② **코호트 기반**(계정 연령·상품 유형·구독 등급) ③ **지리 기반**(국가·주·시간대 — 단 우편번호는 프록시 리스크로 별도 검토) ④ **텔레메트리**(기기·브라우저·OS).
- 실무 해법: 실험마다 법무 검토를 받는 방식(연 6건 수준으로 병목)에서 벗어나 **사전 승인된 세그먼트 라이브러리**를 구축한다 — 한 번의 법무 검토로 여러 실험에 재사용. 서버사이드 플래그 평가로 개인 속성이 외부 실험 플랫폼에 노출되지 않게 하고, 변형 배정과 승인 이력을 연결하는 **감사 추적(audit trail)**을 남긴다.

**코칭 활용**: "컴플라이언스 때문에 실험을 못 한다"는 저항이 나올 때 이 프레임을 제시한다. 실험을 막을 게 아니라 **타겟팅 기준을 행동·코호트·지리·기기로 한정하고 세그먼트 사전 승인 체계를 만들면** 속도와 규제 준수를 동시에 만족시킬 수 있다는 논리다.

#### G-6. 저빈도·고관여 상품에서 A/B가 잘 안 되는 이유와 우회로

보험은 전형적인 **고관여(high-involvement) 상품**이다. 자주 구매하지 않지만 구매자에게 중요도가 높아, 소비자가 특징·가격·보장 범위를 비교하며 확장된 문제해결 과정을 거친다.

**구조적 문제**: 전환 이벤트 표본이 절대적으로 부족해 전통적 A/B의 검정력 확보가 어렵다. 여기에 **사람(상담사)이 개입하는 구매 여정**까지 겹치면 무작위 A/B 자체의 실현 가능성이 낮아진다.

**대응 3가지**

| 전략 | 내용 |
|---|---|
| ① 상류 KPI를 1차 지표로 | 최종 계약 전환 대신 **상담 신청 완료 · 상담 예약 확정**처럼 표본이 충분히 쌓이는 상류 지표를 Primary로, **계약 전환·해지율은 후행 검증 지표로 이원화** |
| ② 실험 기간 연장 | 6~8주 이상으로 늘려 표본 누적. 단 08장 기간 실현성 기준(>90일 = 재설계)을 넘기지 않는다 |
| ③ 준실험적 접근 | 사람 개입이 강한 여정에서는 엄밀한 RCT 대신 **제안서·가격 모델에 의도적 변주를 주고 비교**하는 통제된 관찰·비교 설계 |

> **추가 대안 제시**: "이 정도 트래픽이면 실험보다 **상담사별 비교·코호트 관찰**이 더 빠른 학습 방법일 수 있다"는 선택지를 코칭에서 함께 제시한다. 08장의 **"작은 것에 테스트 돌리지 않기"**와 같은 판단 구조다 — 모든 것을 A/B로 증명하려는 조직이 아니라, **"이건 지금 A/B로 검증하지 않는다"고 판단할 수 있는 조직**이 성숙한 조직이다.

표본 부족 상황의 판정 프레임(신뢰구간·베이지안 승자확률·순차 검정)은 [09 결과분석](09_analysis-reporting.md) "저트래픽 서비스의 해석"을, 검정력을 끌어올리는 CUPED는 09장 외부 레퍼런스 A-2를 함께 본다.

#### G-7. 짧게 쓰는 보조 사례 2건

**토스페이먼츠 — 리드젠 폼을 "고민을 들어주는 창구"로 리프레이밍 (도입 문의 2.6배)**

PG 비교 검색으로 들어온 방문자의 도입 문의 전환율이 낮다는 문제에서 출발. ① 첫 화면에 **"결제 관련 고민"을 직접 적을 수 있는 자유 서술형 입력란** 배치 ② 사업자등록번호 자동 입력 ③ 웹폼 연동으로 응답 대기 최소화 ④ 문의 유형별 담당자 자동 배정. 3개월 내 2배 목표였으나 **2.6배** 달성했고, **가장 효과가 컸던 단일 요소는 "고객이 직접 고민을 남길 수 있는 화면"**이었다.

- 배울 점: 리드젠 폼을 "정보 수집 창구"가 아니라 **"고민을 들어주는 창구"로 리프레이밍**하면 심리적 진입 장벽이 낮아진다. 상담 신청 CTA 앞에 개방형 질문을 배치하는 패턴은 보험·금융 상담 퍼널에 그대로 이식 가능하다.
- 또 하나: **폼 최적화와 백엔드 라우팅 자동화를 함께 실험**했다. CRO를 프론트엔드 UI 문제로만 보지 않고 응답 속도·담당자 매칭까지 퍼널의 일부로 설계한 것. 의사결정이 빠른 B2B·금융 고객에게는 **"얼마나 빨리 응답받는가"가 카피나 디자인보다 전환에 더 크게 기여**할 수 있다.

- **배치 원칙**: 신뢰 요소는 랜딩페이지 전반이 아니라 **폼·가격 섹션 등 실제 전환 임계점 근처**에 놓을 때 효과가 크다. 일반 배너보다 **"지금 망설이는 지점"**에 두는 것이 핵심.
- 상담 신청 퍼널 적용: 폼 직전·도중에 **상담사 프로필·경력 / 실제 상담 후기 / "왜 이 정보가 필요한지"에 대한 개인정보 처리 요약**을 배치하는 것이 개인정보 입력 직전의 심리적 저항을 낮추는 데 유효할 가능성이 높다.
