# 09. 결과분석·보고서 — 10단계 중 [10단계]

> 한 줄 요약: 실험의 끝은 결과 통보가 아니라 **배움(Learning)과 다음 행동(So Next)의 도출**이다. 정량+정성 데이터를 모아 Win/Loss/Inconclusive를 판정하고, 왜 그런지 원인을 밝히고, 다음 액션까지 한 문서에 담는다.

---

## 개념·프레임워크

### 1. 결과분석의 목적 4가지

| 목적 | 질문 |
|---|---|
| **검증** | 가설이 맞았는지 틀렸는지 통계적으로 확인 |
| **해석** | 왜 그런 결과가 나왔는지 원인 분석 |
| **배움** | 이 실험에서 얻은 인사이트 정리 |
| **행동** | 다음에 무엇을 할지 구체적 액션 제시 |

보고서는 숫자를 나열하는 문서가 아니다. **가설 검증 결과를 해석하고, 이를 바탕으로 비즈니스 성장을 위한 구체적인 'So Next'를 제시하는 문서**다.

### 2. 보고의 3단 구조: verdict → why → So Next

모든 결과 공유는 이 3단으로 말한다.

| 단 | 내용 | 실패 신호 |
|---|---|---|
| **verdict** (검증 결과) | Primary/Guardrail 수치, 실험군 win or loss, Stat-sig 달성 여부 | "높게 나왔음"처럼 판정 없이 수치만 |
| **why** (원인) | 그 결과가 나온 이유를 추가 정량·정성 분석으로 파악 + 배운 점 | 현상만 기술하고 이유가 없음 |
| **So Next** (후속) | 운영 반영 여부·방식, 후속 가설, 배움의 일반화 | "결과 보고 결정하겠음" |

### 3. 판정의 3분류

| 판정 | 정의 |
|---|---|
| **Win** | 실험군이 대조군 대비 **통계적으로 유의미하게** 우수 |
| **Loss** | 실험군이 대조군 대비 **통계적으로 유의미하게** 열등 |
| **Inconclusive** | 통계적 유의성 없음(무승부) |

금지 사항:
- ❌ 단순 수치 비교로 결론 도출("A안이 B안보다 높음")
- ❌ 통계적 검증 없이 확정적 결론

### 4. 실험 도구와 분석 도구는 수치가 다르다 — 이를 전제로 시작한다

| 원인 | 설명 | 대응 |
|---|---|---|
| 모수 정의 차이 | 실험 도구는 "실험 노출 유저", 분석 도구는 "페이지 뷰 유저"를 셀 수 있음 | 노출 정의를 명시하고 양쪽 기준을 문서화 |
| 식별자 차이 | user id vs device id vs 세션 | 어느 단위로 집계했는지 표기 |
| 집계 시점·타임존 | 데이터 반영 지연, 일자 경계 | 동일 기간·동일 타임존으로 재추출 |
| 중복 제거 방식 | 유니크 처리 기준 차이 | 유니크 기준 명시 |

**원칙: 두 도구의 절대값이 다른 것은 정상이다. 문제는 "방향과 크기"가 다를 때다.** 방향이 엇갈리면 어느 한쪽 구현에 오류가 있다는 신호이므로 판정 전에 반드시 해소한다.

## 절차

### Step 1. 결과분석 준비 — 데이터 수집

#### 1-A. 정량 데이터

| # | 항목 | 확인 |
|---|---|---|
| 1 | 실험 도구에서 Primary/Secondary/Guardrail 원표 추출 | 노출 수, 전환 수, 전환율 원값(가공 전) |
| 2 | 분석 도구(제품 분석 툴)에서 동일 기간·동일 세그먼트로 교차 추출 | 방향·크기 일치 여부 확인 |
| 3 | 보고서의 lift %를 **원표 수치로 역산 검증** | (실험군 CVR − 대조군 CVR) / 대조군 CVR |
| 4 | 전환율과 **절대 전환 수**를 함께 확보 | 전환 수가 적으면 리프트가 크게 흔들린다 |
| 5 | 세그먼트별 원표 확보(최소 3개 축) | 신규/기존, 모바일/PC, 유입 채널 |
| 6 | 기간 중 외부 이벤트 로그 | 프로모션·장애·시즌 |

> 역산 검증은 결과 리뷰에서 가장 자주 오류가 잡히는 항목이다. 보고서에 적힌 "+5.64% 개선"이 원표로 재계산되지 않으면, 상대/절대 혼동이거나 다른 지표의 리프트를 잘못 옮겨 적은 것이다.

#### 1-B. 정성 데이터

| 소스 | 얻는 것 | 사용 시점 |
|---|---|---|
| **사용성 테스트(UT)** | 사용자가 Variant를 어떻게 인지·해석했는지 | Loss/Inconclusive 원인 규명 시 우선 |
| **VOC / CS 문의** | 실험 기간 중 관련 불만·혼란 증가 여부 | 가드레일 해석 보강 |
| **세션 리플레이** | 실제 행동 경로, 이탈 지점, 스크롤·클릭 패턴 | "왜 안 눌렀나"에 대한 직접 증거 |
| **심층 인터뷰** | 행동의 맥락(이유) | 결과 데이터만으로 해석이 안 될 때 추가 |

정성 데이터는 **정량 결과를 뒤집는 데 쓰는 것이 아니라, 정량 결과의 원인 가설을 세우는 데 쓴다.**

### Step 2. 판정 — Win/Loss/Inconclusive

#### 판정 플로우차트

```
1. P-value < 0.05인가?
   └─ Yes → 통계적 유의성 있음 → Win/Loss 판정
   └─ No  → 통계적 유의성 없음 → Inconclusive

2. 실험군 > 통제군인가?
   └─ Yes → Win
   └─ No  → Loss

3. 가드레일 지표는 안전한가?
   └─ Yes → 배포 가능
   └─ No  → 배포 보류 및 원인 분석
```

판정 기준은 **Primary 지표 1개**에 대해서만 적용한다. Secondary/Guardrail의 유의성은 판정 조건이 아니다(10 챕터 참조).

#### 판정 규칙표 (각 처치 vs Control)

| 조건 | 판정 |
|---|---|
| 개선 + p<0.05 + MDE 달성 + Guardrail OK | ✅ 승자(전체 반영) |
| 개선 + p<0.05 + **Guardrail 하락** | ⛔ 보류(부작용 — 가드레일 우선 거부권) |
| 개선 + **p≥0.05** 또는 **MDE 미달** | ⏸ 보류/추가 검증(우연 배제 못 함) |
| 개선폭 ≈0 또는 음수 | ❌ 기각(학습은 백로그로) |

### Step 3. 원인분석 — 3관점

결과 해석은 반드시 아래 3관점으로 나눈다. **어느 관점의 실패인지에 따라 다음 액션이 완전히 달라지기 때문이다.**

| 관점 | 질문 | Loss일 때 함의 |
|---|---|---|
| **문제** | 우리가 짚은 문제가 실제였는가? | 문제 자체가 틀렸다면 → 문제영역 재선정(1~2단계로 회귀) |
| **솔루션** | 제안한 해결책이 문제를 잘 건드렸는가? | 문제는 맞고 솔루션이 틀렸다면 → 같은 문제에 다른 솔루션(3단계로 회귀) |
| **구현/Variation** | 구현 방식이 의도대로 전달되었는가? | 구현이 문제였다면 → 같은 솔루션 재구현 후 재실험(7단계로 회귀) |

#### 상황별 분석 질문

**Stat-sig O, 실험군 Win**
- 왜 이겼는가? 솔루션의 어떤 요소(카피·디자인·위치)가 사용자의 심리·행동을 자극했는가?
- 다른 타겟/화면에서도 동일한 솔루션이 효과가 있을까? (확장 가능성)
- 전환율을 더 올릴 수 있을까?
- 확인: Primary 개선 폭, Secondary 변화 패턴, Guardrail 안전성, 특정 세그먼트의 두드러진 반응

**Stat-sig O, 실험군 Loss**
- 왜 졌는가? 고객 니즈를 잘못 파악했는가, 아니면 솔루션 구현(UI/UX)이 문제였는가?
- 실험 영역 **후속 퍼널 중 실험군이 win한 퍼널**이 있나?
- 예상하지 못한 부작용(Side Effect)이 있었는가?
- 전환율을 더 올릴 추가 아이디어는?

**Stat-sig X (Inconclusive)**
- 왜 차이가 없었는가? 모수가 부족했는가, 아니면 변화가 인지되지 않을 만큼 미미했는가?
- 실험 metric을 user 세그먼트 기준으로 쪼개서, metric이 특별히 높거나 낮은 코호트를 찾고 그 특성을 감안해 인사이트를 찾는다.

**실험설계 문제 (결과 해석·인사이트가 안 나옴)** — 아래 유형에 해당하는지 체크
- **우선순위가 높지 않은 실험 진행**: ICE 점수가 높지 않은 실험(특히 Impact가 기대되지 않는 실험)
- **실험 지표를 허술하게 설계·구현**: Primary 1개만 설계(Secondary/Guardrail 없이), 가설 검증과 무관한 metric 설계, 설계한 metric을 실험에 미반영
- **왜 win/loss 했는지 파악이 어려운 설계**: 실험군에 검증 요소 외 다른 요소가 함께 변형됨 / 실험군을 1개만 설계(해당 실험군의 검증 요소만 검증됨) / 가설 솔루션의 근거가 부족

### Step 4. 세그먼트 분석

전체 결과가 Inconclusive이더라도 특정 세그먼트에서는 유의미한 차이가 있을 수 있다. **Loss/Inconclusive는 최소 3개 이상 세그먼트를 확인한다.**

#### 주요 세그먼트 5분류

| 세그먼트 | 분류 기준 | 분석 목적 |
|---|---|---|
| **신규 vs 재방문** | 방문 횟수 | 신규 유저의 학습 곡선 확인 |
| **모바일 vs PC** | 디바이스 타입 | 디바이스별 UX 차이 검증 |
| **고관여 vs 저관여** | 행동 빈도/구매 이력 | 관여도별 솔루션 효과 차이 |
| **유입 채널별** | 광고/검색/직접 | 채널별 기대 수준 차이 |
| **시간대별** | 오전/오후/저녁 | 상황별 니즈 차이 |

추가 축(커머스): 상품/카테고리, 장바구니/결제 단계.

#### 세그먼트 분석의 함정

- 사후에 여러 세그먼트로 쪼개는 것은 유용하지만 **우연히 유의미한 결과를 찾아내는 'p-해킹'의 위험**이 있다.
- 세그먼트에서 발견된 중요한 결과는 **후속 실험을 통해 검증하는 것이 이상적**이다.
- 사전 대비책: ① 가설 단계에서 특정 세그먼트가 다르게 반응할지 미리 고민해 세그먼트를 구체화한다 ② 비즈니스에 중요한 핵심 세그먼트의 가드레일 지표를 미리 설정해둔다.

#### 핵심 발견은 위로 올린다

효과 있는 코호트나 중요한 반전은 **문서 하단에 묻지 말고 맨 위에 올린다.** 세그먼트에서 발견한 유효 코호트가 그 실험의 진짜 인사이트인 경우가 많고, 다음 실험의 타겟이 된다.

### Step 5. 보고서 작성

4개 섹션으로 구성한다.

```
1. 실험 설계 요약 (Experiment Design Summary)
2. 실험 결과 분석 요약 (Result Analysis)   ← 가장 중요
3. 상세 데이터 및 배움 (Detailed Data & Learnings)
4. 후속 액션 (So Next / Follow-up Action)
```

**1. 실험 설계 요약** — 결과 보고서만 본 사람도 실험을 이해할 수 있도록 최소한의 배경 제공
- 스프린트/실험 번호, 실험 가설 및 설계서 링크, 실험 기간, 실험 타겟, variant
- PSR 가설 한 문장, 문제 정의(정량·정성 근거), Primary/Secondary/Guardrail 정의

**2. 실험 결과 분석 요약** — "4. 배움"과 "5. 후속 액션"의 핵심을 요약
1. Primary metric 결과 요약(stat-sig 달성 여부, win/loss 여부)
2. Primary 이후 주요 후속 퍼널 metric에 대한 효과 요약
3. 실험 결과의 원인·이유 중 핵심 요약
4. 가설과 관련된 추가 인사이트·배움 중 핵심 요약
5. 후속 액션 요약

**3. 실험 Metric 결과** — 각 metric의 수치 기록 + 수치가 의미하는 바 짧은 요약(primary / secondary / guardrail 구분)

**4. 실험에서의 배움**
- Primary 결과 기록(stat-sig 달성 여부, win/loss)
- Primary 외 다른 metric(주요 전후·옆 퍼널 지표)에 대한 효과·영향 기록
- 결과 데이터가 이렇게 나온 원인·이유를 추가 정량/정성 분석으로 기록
- (필요 시) 심층 인터뷰 결과 — 사용자 행동 맥락 파악이 필요할 경우 정성조사 결과 추가
- 기타 추가 인사이트·배움 기록

**5. 후속 액션**
- 운영 반영 및 실험 지속 여부
- 후속·추가 가설

## 통계 기초

### 1. p-value (빈도주의 / two-proportion z-test)

- 정의: "두 변형이 **사실 같다(차이=0)** 고 가정했을 때, 관측된 차이 **이상**이 우연히 나올 확률."
- 판단: **p < 0.05 → 우연으로 보기 어렵다 → 유의(차이를 인정).** (관행적 임계값; 사전 합의)

#### z-test 계산 (각 처치 vs Control)

```
p̂_c = 전환_c / 노출_c          (Control 전환율)
p̂_t = 전환_t / 노출_t          (처치 전환율)
p̄   = (전환_c + 전환_t) / (노출_c + 노출_t)        # 풀링 전환율
SE  = sqrt( p̄ · (1 − p̄) · (1/노출_c + 1/노출_t) )
z   = (p̂_t − p̂_c) / SE
→ 양측 p-value (|z| > 1.96 ≈ p < 0.05)
```

- 개선폭: 절대 = (p̂_t − p̂_c) [pp] / 상대 = (p̂_t − p̂_c)/p̂_c [%]
- 95% 신뢰구간(차이): (p̂_t − p̂_c) ± 1.96 × SE_diff

#### 95% 신뢰구간 계산 (미풀링 SE)

```
SE = √[ p₁(1−p₁)/n₁ + p₂(1−p₂)/n₂ ]
CI = (차이) ± 1.96 × SE
```

#### 대입 예시

- Control 41.9%(n≈2,000) vs A 47.0%(n≈2,000): 차이 +5.1pp → z≈3.3, **p≈0.001 → 유의(승자).**
- Control 41.9% vs B 44.0%: 차이 +2.1pp → z≈1.34, **p≈0.18 → 유의하지 않음(보류).** 양수라도 우연 배제 못 함.
- A vs B(p≈0.053): **경계** → "A가 B보다 낫다"는 단정하지 않는다.

### 2. p-value의 4대 오해

| # | 오해 | 사실 |
|---|---|---|
| 1 | p는 "효과가 **클** 확률"이다 | 아니다. 크기는 개선폭(pp·%)·신뢰구간으로 본다 |
| 2 | p는 "가설이 **맞을** 확률"이다 | 아니다. p는 귀무가설 하에서의 관측 확률이다 |
| 3 | p ≥ 0.05는 "효과 없음"의 증명이다 | 아니다. "이 표본으론 **우연을 못 배제**"일 뿐이다 |
| 4 | p < 0.05면 반영해도 된다 | 아니다. MDE 달성·가드레일·비즈니스 해석이 남아 있다 |

> p-value는 "이런 결과가 얼마나 드문지"를 측정하는 지표다. **효과가 있을 확률을 직접 알려주지 않는다.**

### 3. 통계적 유의성의 한계

Stat-sig가 의미하는 것은 딱 하나: "결과가 clean test 하에서 단순 우연일 가능성이 낮다." 다음 중 무엇도 보장하지 않는다.

- ✗ 메트릭이 옳다 ✗ 효과가 지속된다 ✗ 일반화 가능하다 ✗ 비즈니스 성장으로 이어진다 ✗ Ship해도 된다

**Stat-sig는 1개 질문에 답한다. 실제로 알고 싶은 질문은 3개 질문이 더 떨어진 곳에 있다.**

경고 사례(Speero Keynote 1 / Leah Tharin 발표, 익명화): 한 SaaS가 18개월간 8개 실험(Copy/CTA/Packaging/Value props)을 돌려 6개가 stat-sig에 도달, 평균 lift 2–3%, **누적 +14% 트라이얼 전환율**을 달성하고 전부 shipped 했다. 그러나 같은 기간에 모바일 트래픽 비중 28%→53%, **60일 retention −17pp**, retained user 1명당 CAC **+41%**, 신규 MRR 기여 거의 0. 트라이얼 전환율은 **고객에게 의미 없는 시그널 메트릭**이었다. → 판정에서 "Primary가 최종 성과와 어떻게 연결되는가"를 항상 되묻는다.

### 4. 베이지안 (승자 확률 · 예상 손실)

- 정의: 결과를 확률 분포로 보고 **"A가 Control보다 나을 확률 = N%"**, **"틀렸을 때 잃는 양(예상 손실)"** 을 직접 제시.
- 장점: 비전문가 소통에 직관적("96% 확률로 A 우세"). **Bayesian Bandit**(우세 변형에 트래픽을 점진 배분)의 기반.
- 사용법: 실험 도구가 승자 확률/예상 손실을 주면 **그 값을 인용**. 없으면 p-value로 판단하되 "베이지안으로는 승자 확률로 환산 가능"이라고 안내.
- p-value와 관계: 상반된 게 아니라 **다른 질문**. p=절차적 우연성, 베이지안=의사결정용 확신도. 함께 보면 강하다.

#### 프리퀀티스트 vs 베이지안 비교

| 축 | 프리퀀티스트(p-value) | 베이지안(승자확률) |
|---|---|---|
| 답하는 질문 | "차이가 없다면 이 결과가 얼마나 드문가" | "A가 B보다 나을 확률은 몇 %인가" |
| 출력 | p-value, 신뢰구간 | 승자 확률, 예상 손실, 신용구간 |
| 중간 판독 | 취약(peeking으로 위양성 증가) | 순차 검정 설계와 결합하기 쉬움 |
| 커뮤니케이션 | 비전문가에게 오해 소지 큼 | 직관적 |
| 저트래픽 | 유의 도달이 매우 어려움 | 방향성 신호를 얻기 유리 |

#### 베이지안 승자확률 해석 기준

| 승자 확률 | 해석 | 액션 |
|---|---|---|
| 50~70% | 약한 신호 | 판단 보류 |
| 70~90% | 신중한 낙관 | 소프트 롤아웃 고려 |
| 90% 이상 | 강한 신호 | 배포 가능 수준 |

### 5. MDE (Minimum Detectable Effect)

- 정의: "이 **표본·기간**으로 **확실히 잡아낼 수 있는 최소 개선폭**." 설계 단계에서 Baseline·트래픽·기간으로 정한다.
- 판정 핵심: **실측 차이가 설계 때의 MDE를 넘겼는가.** 못 넘기면 p와 무관하게 **"표본 부족 → 보류"**.
- 표본↔MDE↔기간: 표본↑ → 감지 가능한 MDE↓(작은 차이도 잡음). 기간 = (그룹당 샘플 × 변형 수) ÷ 일 트래픽.
- 그룹당 샘플 Quick Ref: Baseline 2%/+15%≈25k · 3%/+20%≈15k · 5%/+20%≈8k · 10%/+20%≈4k · 40~50%/+10%(상대)≈2k.
- 실현성: **≤28일 ✅ / 28~90일 ⚠️(MDE 키우기·퍼널 세분화) / >90일 🚫 재설계.**

### 6. 통계 함정 체크 (반드시 점검)

- 표본·기간 부족(MDE 미달)인데 "이겼다" 단정
- p<0.05를 "효과가 크다"로 오해
- 다중 변형 비교 → 거짓양성↑(경계값은 "경계"로 표기, 필요시 보정)
- 노벨티 효과(초기 과대) / 조기 종료(원하는 결과 나올 때 멈춤)
- 가드레일·QA 무시한 채 Primary만 보고 반영

### 7. 한 줄 요약

**p = 우연인가 · 베이지안 = 얼마나 확신하나 · MDE = 표본이 충분했나 — 셋을 같이, 그리고 가드레일은 거부권.**

## 저트래픽 서비스의 해석

### 1. 문제 상황

- B2B SaaS·니치 커머스 등 트래픽이 매우 적은 플랫폼은 **실험을 30일 넘게 돌려도 p < 0.05가 잘 안 나온다.**
- 결과 해석이 불확실해서 의사결정을 못 하거나 '감'에 의존하게 된다.
- **p<0.05를 유일한 판정 기준으로 두면 이런 조직은 영원히 아무것도 결정하지 못한다.**

### 2. 대체 판정 프레임 3종

#### (1) 신뢰구간 해석

해석 순서:
1. **0을 포함하는가** → 포함하면 통계적으로 유의하지 않음
2. **구간이 넓은가** → 넓으면 데이터 부족
3. **구간이 대부분 양수 영역인가** → 긍정적 방향성 가능성

질문 프레임: **"최악의 경우에도 손해가 없나?"** / **"최선의 경우 얼마나 효과 있나?"**

#### (2) 베이지안 승자 확률

- "이 버전이 더 나을 확률 N%"로 환산해 의사결정에 사용. 해석 기준은 위 통계 기초 §4의 "베이지안 승자확률 해석 기준" 표(50~70% 판단 보류 / 70~90% 소프트 롤아웃 / 90% 이상 배포 가능) 참조.

#### (3) 순차 실험(Sequential Testing)

- 고정 샘플 없이 중간에도 종료 가능. **너무 높거나 낮을 때만 종료하고, 애매하면 계속한다**(Goldilocks 방식).
- 예: 승자확률 95% 이상 → Variation 채택 / 5% 이하 → Variation 폐기 / 그 사이 → 실험 계속
- 장점: 트래픽이 적은 환경에서 더 빠른 실험.
- 전제: **이 규칙을 실험 시작 전에 설계서에 명시**해야 한다(사후 적용은 peeking).

### 3. 저트래픽 판정 예시

**예시 1 — 유의하지 않지만 방향성이 뚜렷한 경우**

| 그룹 | 유저 수 | 전환 수 | 전환율 |
|---|---|---|---|
| Control | 886명 | 171건 | 19.3% |
| Variation 1 | 909명 | 185건 | 20.35% |

- 전환율 차이: +1.05%p
- p-value: 0.61 → 유의하지 않음
- SE = √[p₁(1−p₁)/n₁ + p₂(1−p₂)/n₂] = **1.88%**
- 95% 신뢰구간: 1.05% ± 1.96 × 1.88% = **[−2.65%, +4.73%]**
- 베이지안: Variation 1이 더 좋을 확률 **71%**
- 해석: 0을 포함 → 유의하지 않음 / 구간 넓음 → 데이터 부족 / 대부분 양수 → 긍정적 방향성. **71%는 "신중한 낙관" 범위이므로 소프트 롤아웃을 고려할 수 있다.**

**예시 2 — 애매한 p-value vs 명확한 신뢰구간**

| 그룹 | 유저 수 | 전환 수 | 전환율 |
|---|---|---|---|
| Control | 1,000 | 180 | 18.0% |
| Variation 3 | 1,000 | 210 | 21.0% |

- 전환율 차이: +3.0%p / p-value: 0.07 → 유의하지 않음
- 95% 신뢰구간: **[+0.1%, +5.9%] → 0을 포함하지 않음(양수 범위)**
- 베이지안 확률: **93% → 강한 신호**
- 해석: p만 보면 유의하지 않지만 신뢰구간이 완전히 양수. 베이지안도 93%로 방향성 확신 제공. **통계적으로는 유보적이나 실무적으로는 긍정적 효과 기대 가능.** 최악의 경우에도 손해 없고, 최선의 경우 최대 5.9%까지 상승 가능.

**예시 3 — 베이지안은 강하지만 p-value·신뢰구간은 애매**

| 그룹 | 유저 수 | 전환 수 | 전환율 |
|---|---|---|---|
| Control | 1,200 | 240 | 20.0% |
| Variation 4 | 1,200 | 264 | 22.0% |

- 전환율 차이: +2.0%p / p-value: 0.09 → 유의하지 않음
- 95% 신뢰구간: **[−0.2%, +4.2%] → 0 포함**
- 베이지안 확률: **96% → 매우 높은 신호**
- 해석: 빈도주의로는 유의하지 않으나 베이지안 관점에선 매우 강한 신호. **위험이 낮은 변화라면 롤아웃 고려 가능. 중요한 변화는 추가 실험 또는 보조 지표 확인 필요.**
- 핵심 메시지: **베이지안 확률은 "의사결정의 촉진자"로 활용 가능.**

### 4. 저트래픽 조직이 가져가야 할 관점

- **p-value 하나에 집착하지 말 것**
- **결정은 확률이 아니라 실험의 '방향성'과 '비즈니스 맥락'으로**
- **반복 실험과 누적 학습이 진짜 효과를 만든다**
- 리스크 기반 판단: 되돌리기 쉬운 저위험 변화는 낮은 확신도로도 반영 가능, 되돌리기 어려운 고위험 변화는 높은 확신도를 요구

| 3 | **원인 분석 없음** | 결과 수치만 나열, Why 섹션 부재 | "현상 설명이 아닌 **원인 분석**이 필요합니다. '왜 효과가 있/없었는지'를 **문제/솔루션/구현 3관점**에서 분석하세요. (1) 이 문제가 정말 사용자가 심각하게 느끼는 문제였을까? (2) 이 솔루션이 그 문제를 해결할 수 있었을까? (3) 이 variation이 솔루션을 잘 전달했을까?" |
| 4 | **실패 배움 없음** | Loss/Inconclusive인데 배움 섹션 부재 | "실험 실패는 귀중한 데이터입니다. 왜 솔루션이 작동하지 않았는지, 가설이 틀린 것인지 구현이 문제인지 분석하여 '실패로부터의 배움'을 적어주세요." |
| 5 | **지표 과다 / 핵심 지표 불명확** | Primary가 2개 이상 | "지표가 너무 많으면 실험의 초점이 흐려집니다. Primary Metric은 단 1개로 정의하고, 나머지는 Secondary 또는 Guardrail로 분류하세요." |
| (+) | **효과 있는 코호트 미부각** | 세그먼트에서 유효 코호트 발견됐으나 하단 배치 | "세그먼트 분석에서 **효과있는 코호트**를 발견했습니다. 이것이 이 실험의 핵심 인사이트입니다. 하단에 의미없이 배치하지 말고 **'핵심 발견'으로 상단에 부각**하세요. 이 코호트를 타겟으로 후속 실험을 설계할 수 있습니다." |

수업 상세에서 강사 소개를 짧은 수업 영상 썸네일로 바꿔 보여주었을 때,

- 기존 텍스트 위주의 강사 소개는 훑어보기 어려워(Block) 거의 읽히지 않았음

- 특히 '첫 예약' 세그먼트에서 클릭률이 높았음 (42.2% vs 37.5%)

### Next Action
1. 즉시 배포: 실험군1을 100% 트래픽으로 Rollout
2. 후속 실험: 재예약 사용자를 타겟으로 한 강사 추천 개인화 실험 기획

|---|---|---|---|---|
| 전체 | 3.2% | 3.5% | +9.4% | 0.12 |

- Next Action: 모바일에만 선택적으로 배포 고려 + 이 코호트 대상 후속 실험으로 재검증

### 실패 분석 예시 (가상 예시)

```markdown
## 실험 실패 분석

### 결과
- B2B SaaS 가격 페이지에 5문항 「플랜 추천 진단」을 넣은 실험군의 무료체험 시작률이 통제군 대비 −9% 하락 (p-value 0.02) → Loss 확정

### 실패 원인 분석 (3관점)
문제 레벨: 문제 정의는 맞음. 방문자는 실제로 어느 플랜이 우리 팀에 맞는지 몰라 결정을 미룸(인터뷰로 확인)

            의도하지 않은 부작용: 진단 3번째 문항 전후에서 이탈 발생(+6% 이탈률)
구현 레벨: 구현은 정상 작동함

### 배움
1. 플랜 선택 불안을 줄이는 방향은 맞으나, 문항에 답하게 하는 진단은 적절한 솔루션이 아님
2. 방문자는 질문에 답하기보다 바로 비교할 수 있는 정보를 원함
3. 단계를 하나 더 요구하는 솔루션은 마찰(Friction)을 키우기 쉬움

### Next Action
- 후속 실험: 진단 대신 팀 규모별 추천 플랜을 가격표 위에 바로 보여주는 안을 다음 실험으로 테스트
- 가설 수정: "보여주는 것" → "답하게 하는 것"으로 바꾼 것이 Act 단계 마찰을 키움
```

## 코칭 활용 포인트

### 이 챕터를 쓸 세션 유형

- 실험은 돌리는데 보고서가 "수치 나열"에서 멈추는 조직
- 저트래픽이라 p<0.05가 안 나와 의사결정이 멈춘 조직
- 결과 리뷰 회의가 매번 "그래서 어떻게 할까요?"로 끝나는 조직

### 수강자 흔한 질문 · 답변

| 질문 | 답변 |
|---|---|
| "실험 도구와 분석 도구 수치가 다른데 어느 쪽을 믿나요?" | 절대값 차이는 정상. 판정은 실험 도구 기준(랜덤 배분 단위로 집계되므로), 원인 분석은 분석 도구 기준. 단 **방향이 엇갈리면** 구현 오류 신호이므로 판정 전에 해소한다 |
| "p=0.06인데 사실상 이긴 거 아닌가요?" | "경계"로 표기하고 단정하지 않는다. 대신 신뢰구간과 승자확률을 함께 제시하고, 리스크 기반으로 결정한다(되돌리기 쉬운 변화면 소프트 롤아웃) |
| "세그먼트로 쪼개니까 유의한 게 나왔는데 이거 써도 되나요?" | 인사이트로는 쓰되 **결론으로는 쓰지 않는다.** 사후 세그먼트 유의성은 p-해킹 위험. 해당 코호트를 타겟으로 한 후속 실험으로 검증한다 |
| "정성 데이터는 언제 쓰나요?" | 정량 결과를 뒤집을 때가 아니라 **원인 가설을 세울 때.** 특히 Loss/Inconclusive에서 "왜 안 눌렀나"는 세션 리플레이·UT가 가장 빠른 답이다 |
| "보고서를 얼마나 길게 써야 하나요?" | 4섹션 골격만 채우면 된다. 길이가 아니라 **verdict→why→So Next 3단이 다 있는지**가 기준 |

### 흔한 실수 (코치가 먼저 짚어줄 것)

1. **lift를 역산 검증하지 않는다** — 상대/절대 혼동, 다른 지표의 lift를 옮겨 적는 오류가 가장 흔하다
2. **Primary lift와 Guardrail/Secondary lift를 혼동한다**
3. **전환율만 보고 절대 전환 수를 안 본다** — 전환 수가 적으면 리프트가 크게 흔들린다
4. **최종 KPI와 중간 지표를 혼동한다** — Primary는 선행 반응 지표이지 최종 KPI가 아니다
5. **Loss 실험을 그냥 닫는다** — 실패 원인을 3관점으로 분해하지 않으면 다음 액션이 정해지지 않는다

### 세션 진행 팁

- 통계 파트는 **공식 유도를 하지 않는다.** z-test 계산식은 "이런 게 있다" 수준으로 보여주고, 실제로는 **p-value 4대 오해 표**와 **판정 규칙표** 두 장만으로 대부분의 오독이 교정된다.
- 저트래픽 조직에는 **예시 2·3(신뢰구간·베이지안이 서로 다른 답을 주는 케이스)** 을 반드시 함께 보여준다. 이 두 케이스를 보면 "p 하나로 결정하지 않는다"가 체감된다.
- 흔한 실수 5가지 표를 최근 결과보고서 1건에 그 자리에서 적용시킨다. 감지 조건이 명시되어 있어 수강자가 스스로 판정할 수 있다.
- Good/Bad Case 대비는 세션 초반 5분에 배치하면 이후 모든 설명의 기준점이 된다.

### A. 결과 해석의 전제와 필터 (방법론 문헌)

#### A-1. 결과를 해석하기 전에 — SRM 검증

본 챕터 Step 1(데이터 수집)보다 **먼저** 통과해야 하는 게이트다. SRM이 있는 실험은 리프트가 아무리 예뻐도 해석 자체가 무의미하다.

**정의**: 실험군/대조군에 실제로 배정된 사용자 수 비율이 사전 설정한 배정 비율(예: 50/50)과 **통계적으로 유의하게** 다른 상태. 배정·로깅·집계 파이프라인 어딘가가 깨졌다는 신호다.

**원인 4단계 분류 (Microsoft 기준)**

| 단계 | 원인 |
|---|---|
| **① 배정(Assignment)** | 버킷팅 로직 오류, User ID 결손·중복, **캐리오버 효과**(이전 실험의 잔여 배정) |
| **② 실행(Execution)** | 리다이렉트 처리 차이, variant가 사용자 참여 자체를 바꿔 로깅 유입량이 달라짐 |
| **③ 로그 처리(Log processing)** | 조인 오류로 일부 로그 유실 |
| **④ 분석(Analysis)** | 세그먼트·트리거링 조건이 편향되게 걸림 |

추가 원인: 쿠키 삭제·차단으로 재방문자가 신규로 재배정, 특정 variant에서만 발생하는 JS 크래시로 로깅 누락, 봇 필터링이 트리트먼트에 의해 비대칭적으로 영향받음.

**감지 방법 — 카이제곱 적합도 검정**

- Pearson 카이제곱 적합도 검정(goodness-of-fit test)으로 "관측 배정 수 vs 기대 배정 수"를 비교한다.
- **일반 가설검정과 반대로, 귀무가설을 기각하지 않는 것(=유의하지 않음)이 정상**인 검정이다.
- 임계값: Microsoft는 오탐 최소화를 위해 보수적으로 **p < 0.0005**를 경고 임계값으로 쓴다. 다른 실무 문헌은 p < 0.01 또는 p < 0.1을 제시하기도 한다 — **조직 리스크 허용도에 따라 선택**하고, 선택한 값을 실험 설계서에 못박는다.
- 발생 빈도: Microsoft 실험의 약 **6%**, LinkedIn "zoomed-in" 실험의 약 **10%**. 게이트를 걸지 않으면 "승자"로 출시된 실험 중 상당수가 실제로는 SRM 오염 결과다.

> 본 챕터 템플릿 1(결과 판정 시트)에 **`[SRM] 설계 배분 __:__ / 실측 배분 __:__ / 카이제곱 p = ____ / 통과 □`** 한 블록을 [원표] 위에 추가한다. 통과하지 못하면 나머지 칸은 채우지 않는다. 감지 후 원인 조사 절차는 [08 모니터링·종료](08_monitoring-stopping.md) 외부 레퍼런스 A-3 참조.

출처: [Microsoft Research — Diagnosing Sample Ratio Mismatch in A/B Testing](https://www.microsoft.com/en-us/research/articles/diagnosing-sample-ratio-mismatch-in-a-b-testing/) / [Eppo — Understanding Sample Ratio Mismatch](https://www.geteppo.com/blog/understanding-sample-ratio-mismatch-ab-testing)

#### A-2. CUPED — 분산 감소로 필요 표본을 20~50% 줄이는 기법

본 챕터 "저트래픽 서비스의 해석"은 **표본이 적을 때 어떻게 읽을 것인가**를 다룬다. CUPED는 그 앞단에서 **표본 요구량 자체를 줄이는** 접근이다.

**개념**: CUPED(Controlled-experiment Using Pre-Experiment Data)는 실험 시작 **이전** 시점의 사용자 행동 데이터(공변량, covariate)를 이용해 실험 기간 중 관측된 지표에서 "원래도 있었을 사용자 간 변동성(노이즈)"을 통계적으로 제거한다. 2013년 Microsoft Research 발표, 현재 업계 표준.

**성립 조건 2가지**

- 공변량(사전 지표)이 실험 후 지표와 **강하게 상관**되어야 한다. 상관이 낮으면 분산 감소 효과도 작다.
- 공변량은 **외생적(exogenous)**이어야 한다 — 트리트먼트의 영향을 받지 않은, **실험 시작 전에 확정된 값**이어야 한다. 실험 시작 이후 값이 섞이면 편향이 발생한다.

**효과**: 동일한 검정력을 유지하면서 **필요 표본 크기를 약 20~50% 절감**. 같은 트래픽으로 더 빨리 유의성에 도달하거나, 같은 기간에 더 작은 효과(MDE)까지 탐지할 수 있다.

**도구 지원 현황**

| 도구 | 지원 상태 |
|---|---|
| Amplitude | 설정에서 토글 가능 (아래 B-3) |
| Optimizely | Experiment Scorecard에서 토글. 기본적으로 실험 시작 2주 전 데이터를 자동 수집(조정 가능). **수치형(numeric) 지표에만 적용 가능, 전환형(conversion) 지표는 미지원.** Snowflake/BigQuery/Databricks 연동 환경에서만 지원 |
| Netflix · Booking.com · Airbnb | 기본 분산 감소 기법으로 채택 |

**체크리스트**

- [ ] 핵심 지표에 대해 "실험 전 동일 지표의 과거 값"이 안정적으로 존재하는가 (신규 유저·신규 지표는 적용 곤란)
- [ ] 공변량이 트리트먼트로부터 절대 영향받지 않는 시점의 데이터인가
- [ ] 사용 중인 도구가 CUPED를 지원하는가, **어떤 지표 타입에 한정되는가**
- [ ] 적용 전후로 필요 표본·기간이 얼마나 줄어드는지 시뮬레이션해 팀에 공유했는가 (기대치 관리)

> **저트래픽 조직에서의 위치**: 필요 표본을 모으는 데 오래 걸리는 환경이므로 CUPED의 체감 효과가 가장 큰 구간이다(Optimizely 문서도 CUPED가 "트래픽 부족·높은 분산 문제"에 특히 유효하다고 명시). 다만 저트래픽 서비스는 **사용자별 과거 행동 데이터 자체가 희소하거나**(신규 서비스, 신규 유저 비중이 큰 경우) 지표 변동성이 커서 공변량-사후 지표 상관이 약할 수 있다. 즉 **"저트래픽 = CUPED 필수"가 아니라 "충분한 사전 행동 이력이 쌓인 지표에 한해 우선 적용"**이 현실적이다.

### B. Amplitude Experiment 통계 엔진 (공식 문서 기준)

본 챕터 "통계 기초"는 two-proportion z-test와 베이지안을 정본으로 다룬다. Amplitude를 쓰는 조직은 **어떤 엔진이 선택돼 있는지에 따라 화면의 숫자가 의미하는 바가 달라지므로**, 결과를 읽기 전에 설정을 먼저 확인해야 한다.

#### B-1. 4가지 통계 방법론 — 기본값은 Sequential Testing

실험 설정(statistical preferences)에서 선택한다.

| 방법론 | 원리 | 언제 쓰나 | 주의 |
|---|---|---|---|
| **Sequential testing** *(기본값)* | **mSPRT**(mixture Sequential Probability Ratio Test) 기반. **프리퀀티스트이며 Bayesian이 아니다.** 귀무가설 δ = μ_treatment − μ_control = 0을 검정 | "언제 봐도 유효한(always-valid)" 결과. 사전에 peek 횟수를 정할 필요 없이 유의해질 때까지 돌리다 멈춰도 위양성률이 부풀지 않음 | **"절대 lift와 variant 배분 비율이 시간에 따라 변하지 않는다"**는 가정에 의존. 가정이 깨지면 신뢰구간 방향이 뒤집힐 수 있다. exposure~conversion 지연이 큰 지표는 조기 종료 시 편향 위험 |
| **T-test (Fixed-horizon)** | 사전에 정한 표본 크기 도달까지 기다려야 p-value·신뢰구간 계산이 실행됨 | 정확한 효과 크기 추정이 중요할 때 | 중간에 반복 열람(peeking)하면 위양성이 인플레이션된다 |
| **Bayesian** | p-value·고정 가설검정 대신 **"한 variant가 다른 variant보다 우월할 확률"**을 직접 산출 | 사전 지식 반영, 작은 표본에서의 의사결정, 비즈니스 질문에 직접 답할 때 | 본 챕터 "베이지안 승자확률 해석 기준" 표(50~70%/70~90%/90%↑)를 그대로 적용 |
| **Thompson Sampling** | **Bayesian 밴딧(bandit)**. 실험 종료를 기다리지 않고 실시간으로 성과가 좋아 보이는 variant에 트래픽을 더 배분(exploration/exploitation 균형) | 다변량·다중 variant 최적화 | 판정용이 아니라 최적화용. "실험 결과 보고"의 대상이 아니다 |

비교 실험 결과(Amplitude 공식 블로그): peeking 시 **T-test는 30~50% false positive**가 발생하는 반면 **sequential testing은 의도한 alpha(5%) 수준을 유지**했다. 이 수치는 [08 모니터링·종료](08_monitoring-stopping.md) 외부 레퍼런스 A-1의 반복 확인 횟수별 위양성률(5%/15%/30%)과 같은 현상을 다른 축에서 측정한 것이다.

#### B-2. "왜 아직 결과가 안 나오나요"에 대한 답 — 최소 데이터 요건

sequential testing이 p-value·신뢰구간 계산을 **시작하기 위한** 최소 조건이다.

| 지표 계열 | treatment/control **각각** 필요한 최소치 |
|---|---|
| conversion 계열 (Uniques) | **최소 25건 전환 + 100건 노출** |
| average 계열 | **최소 100건 노출** |

> 저트래픽 고객사에서 "실험을 켰는데 화면에 숫자가 안 뜬다"는 질문이 반복적으로 나온다. 대부분 이 요건 미달이며 **버그가 아니다.** 실험 설계 시점에 이 임계치를 언제 넘길지 계산해 팀에 미리 공유하면 문의 자체가 사라진다.

#### B-3. 표시 규칙과 보정 옵션

- 유의성 지표는 **"1 − p-value"**로 표시된다. 신뢰구간이 **0을 포함 → 유의한 차이 없음**, 0보다 큼 → 우수, 0보다 작음 → 열등. 본 챕터 "신뢰구간 해석 순서"(0을 포함하는가 → 넓은가 → 대부분 양수인가)를 그대로 적용할 수 있다.
- 기본 신뢰수준 **95%**, 최소 80% 이상 권장. 위양성률 5% 기준.
- **CUPED 지원** — 실험 전 데이터를 covariate로 활용해 분산을 줄이고 검정력을 높인다(사전 편향 제거 목적). 설정에서 토글. 적용 조건은 위 A-2 참조.
- **Bonferroni Correction 지원** — 여러 metric·variant를 동시 검정할 때의 다중비교 보정 옵션. 보정을 켰다면 **결과보고서에 "Bonferroni 보정 적용"을 명시**한다. 보정 방법을 밝히지 않은 p-value는 비교 불가능한 숫자다 → [06 실험 설계](06_experiment-design.md) 외부 레퍼런스 3절.
