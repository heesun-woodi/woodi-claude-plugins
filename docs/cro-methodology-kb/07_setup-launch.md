# 07. 세팅 → 테스트 → 런칭 — 10단계 중 [7단계]

> 한 줄 요약: 확정된 실험설계서를 구현 난이도 3레벨로 트리아지해 담당과 소요를 정하고, 툴에 세팅한 뒤 QA를 통과시켜 런칭한다. 이 단계의 실패는 대부분 "설계 문제"가 아니라 "검증하지 않고 켰다"에서 나온다.

---

## 개념·프레임워크

### 이 단계가 하는 일

6단계에서 만든 설계서는 "무엇을 어떻게 측정할지"까지 확정했다. 7단계는 그것을 **실제로 사용자에게 노출되는 상태**로 만든다.

```
실험설계서 v1.0
   ↓
① 구현 트리아지 (난이도 3레벨 판정 → 담당·소요·리스크 결정)
   ↓
② 시안 확정 / 코드 작성
   ↓
③ 툴 세팅 (타겟팅 · 트래픽 배분 · 지표 연결)
   ↓
④ QA (기능 QA + 데이터 QA)
   ↓
⑤ 런칭 + 런칭 직후 확인 (30분 / 24시간)
   ↓
8단계 모니터링
```

### 원칙 3가지

1. **코드가 저장되었다고 실제 반영된 것은 아니다.** 최종 검증은 Preview/스크린샷/이벤트 수집으로 한다.
2. **추측하지 않는다.** 대상 URL, 지표명, 셀렉터 중 모르는 것이 있으면 만들어내지 말고 질문한다. 실행자가 추측해야 하는 항목이 하나라도 남아 있으면 세팅을 시작하지 않는다.
3. **한 번에 많이 실행하지 않는다.** 세팅과 QA는 step-by-step으로 진행하고, 매 단계 결과를 스크린샷으로 남긴다.

### 구현 난이도 3레벨

설계서가 확정되면 가장 먼저 하는 일은 **"이걸 누가 만드나"**를 정하는 것이다. 이 판정이 스프린트 일정과 실험 처리량(throughput)을 결정한다.

| 레벨 | 변경 범위 판단 기준 | 구현 주체·도구 | 예상 소요 | 리스크 |
|---|---|---|---|---|
| **레벨 1** | 화면 UX(레이아웃·인터랙션·위치) **변경 없이** 문구 및 디자인 변경 | 실험 스쿼드 내에서 **툴 비주얼 에디터**로 직접 세팅 | 반나절~1일 | 낮음. flicker와 반응형 깨짐만 주의 |
| **레벨 2** | **간단한** 화면 UX 변경 (레이아웃, 인터랙션, 위치, user flow) | 스쿼드 내에서 **비주얼 에디터 + 코드 에디터**(+ 코딩 어시스턴트) 직접 세팅 → **세팅된 캠페인을 엔지니어가 검토** | 2~4일 | 중간. DOM 구조 의존, 동적 렌더링 타이밍 |
| **레벨 3** | **복잡한** 화면 UX 변경 (user flow 변경, 화면 개발 필요) | **실험 구현 엔지니어 미팅**을 먼저 열고 → **코드 에디터로 엔지니어가 직접 세팅** (또는 기능 배포 후 실험 툴에서 노출 제어) | 1~3주+ | 높음. 기능 배포 의존, 릴리즈 일정 종속 |

**레벨 판정 질문 (순서대로)**

1. 요소의 **위치와 개수가 그대로**이고 문구·색·크기만 바뀌는가? → 레벨 1
2. 요소가 **추가/삭제되거나 순서가 바뀌는가**? 클릭 후 동작이 바뀌는가? → 레벨 2
3. **새로운 화면·기능·API**가 필요한가? 서버 데이터가 필요한가? 앱 네이티브 화면인가? → 레벨 3

**트리아지의 실무 의미**

- 레벨 1·2는 스쿼드가 자체 처리한다. 실험 처리량은 결국 "레벨 1·2로 설계할 수 있는 능력"에 비례한다. 6단계 MVP 4질문의 4번(개발팀 도움 없이 툴로 구현 가능한가)이 여기로 연결된다.
- 레벨 2는 **엔지니어 검토를 반드시 거친다.** 스쿼드가 만들었다는 이유로 검토를 건너뛰면 성능·보안·DOM 충돌 문제가 런칭 후에 발견된다.
- 레벨 3이 스프린트에 2개 이상 들어가면 그 스프린트는 실험이 아니라 개발 프로젝트가 된다. 스프린트 플래닝에서 레벨 3은 **최대 1개**로 제한하는 편이 안전하다.
- ICE의 Ease 점수와 레벨은 직결된다. 레벨 1 ≈ Ease 8~10, 레벨 2 ≈ Ease 5~7, 레벨 3 ≈ Ease 1~4.

## 절차

### ① 구현 트리아지

스프린트 플래닝 또는 정례 미팅에서 기획·디자인·개발이 함께 판정한다.

| 산출물 | 내용 |
|---|---|
| 난이도 레벨 | 1 / 2 / 3 |
| 담당자 | 스쿼드 / 스쿼드+엔지니어 검토 / 엔지니어 |
| 선행 작업 | 시안 디자인 필요 여부, 기능 배포 필요 여부, 신규 태깅 필요 여부 |
| 일정 | 세팅 착수일, QA일, 런칭 예정일 |

레벨 3으로 판정되면 **실험 구현에 대한 엔지니어 미팅**을 먼저 연다. 여기서 합의되지 않으면 스프린트에 넣지 않고 백로그로 되돌린다. "미합의 → 개발 검토 및 수정 → 재논의" 루프를 설계서 단계에서 돌리는 편이, 세팅 중에 막히는 것보다 훨씬 싸다.

### ② 시안 확정 / 코드 작성

- 레벨 1: 비주얼 에디터에서 바로 편집. 시안은 스크린샷 수준이면 충분하다.
- 레벨 2: 대상 요소의 **CSS 셀렉터를 먼저 확정**한 뒤 코드를 쓴다. 셀렉터는 실제 페이지에서 확인한 값만 쓴다(사이트 프론트엔드 가이드/사이트맵 문서가 있으면 참조하고, 없으면 직접 확인). 클래스명이 빌드마다 변하는 프레임워크라면 안정적인 앵커(data 속성, 텍스트 기반 탐색)를 찾는다.
- 레벨 3: 기능 배포 일정과 실험 세팅 일정을 분리해 관리한다. 기능이 운영 서버에 먼저 배포되고, 실험 툴은 그 요소의 **노출 여부만 제어**하는 구조가 가장 안전하다.

### ③ 툴 세팅

#### 3-1. 타겟팅

| 항목 | 확정 내용 | 흔한 실수 |
|---|---|---|
| **Pages URL** (노출 대상) | URL 패턴 (matches / contains / regex) | 와일드카드가 의도보다 넓어 무관한 페이지에 노출 |
| **Editor URL** (편집용) | 실제 접근 가능한 **구체적인** URL | Pages URL에 와일드카드를 쓰면서 Editor URL도 와일드카드로 넣어 에디터가 안 열림 |
| Device | Mobile / Desktop / Both | 설계서와 불일치 |
| Segment | 신규/재방문, 진입 경로, 로그인 상태 | 세그먼트 조건이 실험 툴에서 지원되지 않는데 설계서에만 존재 |
| Trigger | 페이지 진입 시 / 요소 노출 시 / 스크롤 n% | 트리거 시점이 Primary 지표 모수 정의와 어긋남 |
| 제외 조건 | 내부 IP, 봇, 특정 파라미터 유입 | |

> **Editor URL 규칙:** Pages URL에 와일드카드(`*`)를 사용하는 경우, Editor URL은 반드시 구체적이고 접근 가능한 URL이어야 한다. 예: Pages URL `/shop/item/*` → Editor URL `/shop/item/1024`.

#### 3-2. 트래픽 배분

- 설계서의 split을 그대로 입력한다(2개면 50:50, 3개면 34:33:33).
- 실험에 태울 전체 트래픽 비율(100% vs 일부)을 확인한다.
- 램프업 계획이 있으면 시작 비율로 세팅하고, 상향 시점을 캘린더에 등록한다.

#### 3-3. 지표 연결

가장 자주 막히는 지점이다.

1. **설계서의 Primary/Secondary/Guardrail을 툴의 기존 Metric에 매핑한다.**
2. 매핑되는 Metric이 **없으면 먼저 만든다.** 캠페인을 만들어 놓고 나중에 지표를 붙이려 하면, 툴에 따라 "Ready to start" 상태가 되지 않거나 시작 이후 붙인 지표가 소급 집계되지 않는다.
3. Metric의 **트리거 방식**을 확인한다. 페이지뷰 기반인지, 클릭 기반인지, Custom Conversion(코드 호출)인지에 따라 QA 방법이 달라진다. Custom Conversion은 자동 검증이 안 되므로 **수동 QA가 필수**다.
4. Metric **이름을 정리한다.** 운영 중 `[확인 필요]` 같은 임시 태그가 붙은 Metric을 그대로 연결하면 결과 보고 시점에 어떤 지표인지 아무도 확신하지 못한다.

#### 3-4. 캠페인 네이밍

`[식별접두어] SP{n}_EXP{nnn}_{지면}_{변경축}` 형태로 통일한다. 자동화 에이전트가 만든 캠페인은 접두어로 구분한다. 실험이 수십 개로 늘어난 뒤 규칙을 도입하려면 늦다.

### ④ QA — 기능 QA와 데이터 QA를 나눠서 한다

두 QA는 목적도 도구도 담당도 다르다. 하나로 뭉뜽그리면 한쪽이 반드시 빠진다.

| 구분 | 확인하는 것 | 도구 | 실패 시 증상 |
|---|---|---|---|
| **기능 QA** | Control/Variant 화면이 의도대로 보이고 동작하는가 | Preview 링크, QA 링크, 실기기, 스크린샷 | 사용자가 잘못된 화면을 봄 |
| **데이터 QA** | 실험 배정 정보와 지표 이벤트가 정상 수집되는가 | Analytics debugger, 실시간 리포트, 네트워크 탭 | 화면은 정상인데 결과를 분석할 수 없음 |

#### 4-1. 깜빡임(flicker) 방지

Variant 코드가 실행되기 전에 원본 화면이 잠깐 보이는 현상이다. 사용자 경험을 해칠 뿐 아니라 **결과를 오염시킨다** — 실험군만 깜빡이면 그 자체가 개입이 되어, 우리가 검증하려던 것과 다른 것을 측정하게 된다.

| 대응 | 방법 |
|---|---|
| 요소 숨김 | 툴의 "Hide elements until code runs"에 **변경 대상 셀렉터**를 지정. 페이지 전체(`body`)를 숨기면 체감 로딩이 나빠지므로 최소 범위로 지정 |
| 스크립트 위치 | 실험 툴 스크립트를 `<head>` 상단에 동기 로드 (비동기/GTM 경유는 flicker를 키운다) |
| 동적 렌더링 대응 | SPA·비동기 렌더링 지면은 요소 등장을 감지(MutationObserver 등)한 뒤 적용. 고정 `setTimeout`은 기기 성능에 따라 실패 |
| 검증 | **저사양 기기 + 느린 네트워크(3G 스로틀링)** 조건에서 확인. 개발자 PC에서는 거의 재현되지 않는다 |

#### 4-2. 디바이스/브라우저 테스트

기능 및 데이터 QA는 **다양한 디바이스와 브라우저 환경**에서 진행한다.

| 축 | 최소 커버리지 |
|---|---|
| OS | macOS, Windows, iOS, Android |
| 브라우저 | Chrome, Safari, (필요 시) Samsung Internet, 인앱 브라우저 |
| 뷰포트 | 소형 모바일(≤375px), 일반 모바일, 태블릿, 데스크톱 |
| 상태 | 비로그인 / 로그인, 신규 / 재방문(쿠키 보유) |

인앱 브라우저(카카오·인스타그램 등에서 열리는 웹뷰)는 별도 확인한다. 유입 비중이 큰데 스크립트 동작이 다른 경우가 있다.

#### 4-3. 기능 QA 체크리스트

- [ ] 대상 URL에서 캠페인이 노출된다.
- [ ] Control / Variant 구분이 정상이다. (Preview 드롭다운으로 각 Variant를 직접 확인)
- [ ] Variant UI가 의도대로 보인다. (설계서 시안과 스크린샷 대조)
- [ ] Variant의 변경된 DOM 값(텍스트·속성)이 실제로 바뀌어 있다.
- [ ] CTA/링크가 정상 동작한다. (클릭 시 이동 경로 확인)
- [ ] 깜빡임이 없다. (저사양·저속 조건 포함)
- [ ] 반응형이 깨지지 않는다. (모든 뷰포트)
- [ ] 모바일/데스크톱 타겟 조건이 설계서와 일치한다.
- [ ] 실험 대상이 아닌 페이지에는 노출되지 않는다.
- [ ] 실험 요소의 **기능적 제한사항**을 확인했다. (예: 리뷰 없는 상품에는 리뷰 모듈이 렌더링되지 않음 → 실험 지면 한정 필요)
- [ ] 다른 실행 중인 실험과 지면이 중복되지 않는다.

#### 4-4. 데이터 QA 체크리스트

- [ ] 실험 노출 이벤트(impression)가 수집되고, 하위 dimension(실험명, variant명)이 정상 값으로 들어온다.
- [ ] Primary 지표 이벤트가 수집된다.
- [ ] Secondary 지표 이벤트가 모두 수집된다.
- [ ] Guardrail 지표 이벤트가 수집된다.
- [ ] 신규 태깅이 필요했던 이벤트가 실제로 배포되어 있다.
- [ ] 이벤트/dimension 누락·오류가 있으면 데이터 담당(또는 협력사)에 리포팅하고 수정 개발을 요청했다.
- [ ] Custom Conversion 방식 지표는 수동으로 발화를 확인했다.
- [ ] 실험 툴과 분석 도구 양쪽에서 같은 사용자가 같은 variant로 보이는지 대조했다.

Analytics debugger류 확장 프로그램을 설치해 QA 링크에서 이벤트와 속성을 직접 눈으로 확인하는 것이 가장 확실하다.

#### 4-5. A/A 테스트 (실험 환경을 새로 구축했거나 툴/태깅을 교체한 경우)

A/B를 켜기 전에, 현재 화면(대조군) 상태에서 실험 지면 방문자를 실험의 variant 수만큼 자동 분배하는 테스트를 먼저 돌린다(50:50, 34:33:33 등). 목적은 셋업 데이터가 어떤 형태·값으로 분석 도구에 넘어오는지 확인, 각 실험군에서 variant 값이 유지되는지 확인, traffic split이 정상인지 확인이다. 통과 기준은 **그룹 간 지표에 유의한 차이가 없을 것**이다. 여기서 차이가 나면 A/B 결과를 신뢰할 수 없다.

### ⑤ 런칭 + 런칭 직후 확인

QA 통과 후 시작 버튼을 누르기 전에:

- [ ] 최종 승인자를 기록했다.
- [ ] 실험 시작·종료 예정일을 관련 팀에 공유했다. (프로모션·배포 일정과 재확인)
- [ ] 종료/일시정지 전 상태를 기록했다. (롤백 대비)
- [ ] 모니터링 담당과 확인 주기를 정했다.

**런칭 직후 30분 체크**

| 확인 | 정상 기준 | 이상 시 |
|---|---|---|
| 노출 시작 | 실험 노출 이벤트가 발생하기 시작 | 30분 내 0건이면 즉시 중단하고 타겟팅 재확인 |

| 확인 | 정상 기준 |
|---|---|

## 툴별 세팅 노트

### VWO (클라이언트 사이드 웹 실험)

**캠페인 구조**

```
Campaign (A/B Test)
 ├─ Variations : Control / Variation 1 / Variation 2 …
 │    └─ 각 Variation = 비주얼 에디터 변경분 + 커스텀 CSS/JS
 ├─ Pages      : 노출 대상 URL 조건 (+ Editor URL)
 ├─ Audience   : 세그먼트 / 디바이스 / 제외 조건
 ├─ Goals(Metrics) : Primary 1 + 나머지
 └─ Settings   : 트래픽 배분, Trigger, Hide elements until code runs
```

**세팅 노트**

| 항목 | 노트 |
|---|---|
| SmartCode | 사이트에 설치되어 있고 정상 로드되는지 먼저 확인한다. 미설치 상태에서 캠페인을 만들면 노출이 시작되지 않는다. |
| Metric 매핑 | Primary Metric은 **기존에 생성된 Metric 중에서 선택**해야 캠페인이 시작 가능 상태(Ready to start)가 된다. 필요한 Metric이 없으면 캠페인 생성 전에 먼저 만든다. |
| Metric 이름 | 임시 태그(`[확인 필요]` 등)가 붙은 Metric을 그대로 쓰지 않는다. 결과 해석 시 어떤 지표인지 확정할 수 없다. |
| Metric 트리거 | Custom Conversion 트리거는 자동 검증이 되지 않으므로 반드시 수동 QA한다. |
| Editor URL | Pages URL에 와일드카드를 쓰면 Editor URL은 구체 URL로 별도 지정한다. |
| 비주얼 에디터 vs 코드 에디터 | 레벨 1은 비주얼 에디터, 레벨 2 이상은 코드 에디터. 비주얼 에디터가 생성한 셀렉터는 DOM 변경에 취약하므로 레벨 2에서는 직접 작성한 셀렉터로 교체한다. |
| Hide elements until code runs | 변경 대상 셀렉터만 지정. flicker 방지의 핵심 설정. |
| Live Preview | 배포 후 Variation 드롭다운으로 각 Variation을 열어 **DOM 값을 직접 확인**한다. 코드가 저장되었다는 표시는 검증이 아니다. |

**배포·QA 흐름 (실전 운영 로그 기준)**

```
캠페인 생성 → SmartCode 설치 확인 → Variant 코드 주입
   → Live Preview에서 Variation별 수동 검증 (스크린샷 저장)
   → DOM 값 검증 통과
   → Metrics 단계 확인 (Primary Metric 연결·이름 정상 여부)
   → Ready 상태 확인 → 런칭
```

실전에서 반복적으로 걸린 지점 두 가지: **① Primary Metric 이름에 임시 태그가 남아 있어 정리가 필요했던 건, ② Custom Conversion 트리거라 자동 검증이 불가해 수동 QA가 필요했던 건.** 두 항목은 캠페인 생성 브리프에 고정 확인 항목으로 넣어둔다.

### Amplitude Experiment (feature flag 기반)

클라이언트 사이드 DOM 조작 방식이 아니라, **feature flag로 분기하고 제품 코드가 그 분기를 렌더링하는** 구조다. 웹뷰·네이티브 앱·서버 로직까지 같은 방식으로 실험할 수 있다.

```
Deployment (플랫폼별 전달 컨테이너 — web / iOS / Android 분리 권장)
 └─ Flag (실험 단위)
     ├─ Variants   : control / treatment-a / … (value + payload(JSON)로 값 전달 가능)
     ├─ Assignment : 타겟팅 룰(세그먼트·속성) + 트래픽 배분 %(합 100%)
     ├─ Exposure   : SDK가 variant를 반환할 때 노출 이벤트 발생 → 분석의 앵커 포인트
     └─ Goals      : 제품 분석 이벤트를 그대로 지표로 사용 (Goal 1개 + tracked metrics 다수)
```

| 항목 | 개요 |
|---|---|
| Bucketing unit | 배정 단위를 명시적으로 지정한다. 기본이자 대부분의 정답은 **User**이며, B2B는 Company ID 등 조직 단위도 가능. 로그인 전후 식별자 전환 시 배정이 바뀌지 않도록 주의 |
| 평가 모드 | **Remote**(Amplitude 서버가 평가) / **Local**(SDK 내 로컬 평가) 중 선택. 렌더링 전에 값이 필요하면 로컬 평가·부트스트랩으로 flicker를 원천 차단하되, **로컬 평가는 assignment 이벤트를 만들지 않으므로 커스텀 exposure 계측이 필수**가 된다 |
| 노출 기록 | exposure 이벤트가 발생해야 분석 모수가 된다. 원칙은 **기본 Amplitude Exposure 이벤트를 그대로 쓰는 것** — 커스텀 exposure는 발동 시점이 어긋나 SRM을 유발하는 가장 흔한 원인이다 |
| 지표 | 별도 Metric 생성 없이 기존 제품 분석 이벤트를 지표로 사용. **Goal(주 지표)은 실험당 1개만** 지정 가능하고 나머지는 참고용 tracked metric → 6단계 지표 3층 설계와 그대로 맞는다 |
| 실험 중 변경 | 트래픽 배분·variant 구성·sticky bucketing 설정을 실행 중에 바꾸지 않는다. 바꿔야 하면 새 실험으로 취급한다 |
| 롤아웃 | 실험 종료 후 flag를 100%로 올려 그대로 릴리즈. 실험과 릴리즈가 같은 장치라 롤백이 빠르다. **Activate/Deactivate 버튼으로 트래픽을 껐다 켜지 말고 "all users" 세그먼트 배분을 100%/0%로 조정**한다(Activate/Deactivate는 flag를 완전히 걷어낼 때만) |
| 정리 | 종료된 flag를 코드에서 제거하는 절차를 스프린트 리뷰에 넣는다. flag 부채가 쌓이면 코드가 분기로 뒤덮인다 |

> 이 절은 "웹 툴과 무엇이 구조적으로 다른가"만 다룬다. 생성 플로우 전체·exposure 이벤트 상세·통계 옵션은 아래 [외부 레퍼런스](#외부-레퍼런스)에서 공식 문서 기준으로 정리했다.

### 릴리즈 주기가 긴 앱 환경에서의 세팅 전략

앱은 스토어 심사·강제 업데이트 때문에 "코드를 고쳐 실험한다"가 성립하지 않는다. 릴리즈 주기가 2~4주 이상이면 아래 순서로 우회한다.

| 전략 | 내용 | 적용 조건 |
|---|---|---|
| **1. 웹뷰 지면 우선** | 앱 내 웹뷰로 구성된 지면(이벤트·상품상세·가이드 등)을 실험 대상으로 먼저 고른다. 웹 실험 툴을 그대로 쓸 수 있다 | 웹뷰 비중이 있는 앱 |
| **2. 서버 응답 제어** | 화면 구성이 서버 응답(배너·모듈 목록·문구)에 의존하면, 앱 배포 없이 서버에서 분기한다 | 서버 주도 UI |
| **3. Remote config / feature flag 선탑재** | 다음 릴리즈에 **실험 분기 코드와 flag를 미리 태워 배포**하고, 실험은 나중에 원격으로 켠다. 앱 실험의 표준 전략 | 릴리즈 열차에 사전 계획 필요 |
| **4. 앱 버전 타겟팅** | flag 대상을 특정 버전 이상으로 한정. 구버전 사용자는 실험에서 제외 | 항상 함께 설정 |
| **5. 네이티브 필수 변경은 레벨 3** | 위 셋 중 아무것도 안 되면 레벨 3으로 판정하고 개발 일정에 편입 | |

**앱 실험 세팅 시 추가 확인 항목**

- [ ] 실험 분기 코드가 포함된 최소 앱 버전을 확인하고, flag 타겟에 버전 조건을 넣었다.
- [ ] 구버전 사용자가 실험 모수에 섞이지 않는다.
- [ ] 앱 실행 시점에 flag 값을 가져오지 못하면 **Control로 폴백**하도록 되어 있다. (폴백이 없으면 네트워크 지연 사용자가 통째로 유실된다)
- [ ] **폴백으로 Control이 된 사용자에게는 exposure를 기록하지 않는다.** 폴백 variant를 노출로 카운트하면 실험에 실제로 참여하지 않은 사용자가 모수에 섞여 SRM이 발생한다.
- [ ] 배정이 세션마다 바뀌지 않는다. (동일 사용자 = 동일 variant 유지)
- [ ] 노출 이벤트가 실제 화면 렌더링 시점에 발생한다. (flag 평가 = assignment 시점이 아님. assignment는 세션 초반, exposure는 플로우 후반에 발생하는 것이 정상이며 하루 이상 벌어질 수도 있다)
- [ ] 실험 기간 중 강제 업데이트·대형 릴리즈 일정이 없다.

앱 실험은 **"다음 릴리즈에 무엇을 태울지"를 6단계 설계 시점에 이미 결정**해야 한다. 설계가 끝난 뒤에 릴리즈 열차를 잡으려 하면 실험 시작이 한 사이클(2~4주) 밀린다. 스프린트 플래닝에서 앱 실험은 항상 한 사이클 앞서 준비한다.

### 예시 A — B2B SaaS 웹, 헤드라인 카피 실험 (레벨 1)

| 단계 | 진행 |
|---|---|
| 트리아지 | 히어로 영역 H1·서브헤드 **문구만** 변경, 레이아웃 동일 → **레벨 1**. 스쿼드 자체 세팅, 반나절 |
| 세팅 | 캠페인 생성 → Pages URL 지정 → Control + Variation 2개 → 트래픽 34:33:33 → Primary Metric으로 기존 "문의 페이지 방문" 연결 |
| 사전 확인 | 실험 툴 스크립트 설치 상태 확인 ✅ |
| 기능 QA | Live Preview에서 Variation 1·2를 각각 열어 H1·서브헤드 텍스트 변경 확인, 스크린샷 저장 → 둘 다 PASS. DOM 값 직접 검증 통과 |
| 데이터 QA | Primary Metric 연결 확인. **이슈 2건 발견** — ⓐ Metric 이름에 임시 태그가 남아 있어 정리 필요 ⓑ Metric 트리거가 Custom Conversion이라 자동 검증 불가 → 수동 QA 수행 |
| 판정 | PASS — 모든 Variation의 코드 정상 적용, 실험 시작 가능 |
| 소요 | 가설 도출 → 설계 → 캠페인 배포 → QA PASS까지 약 3시간 (레벨 1 기준) |

레벨 1 실험은 **반나절 안에 런칭까지 갈 수 있다.** 스프린트 처리량을 올리려면 레벨 1로 설계 가능한 가설의 비중을 의도적으로 높인다.

### 예시 B — 피트니스 예약 앱 웹, 수업 상세 안내 모듈 추가 (레벨 2)

| 단계 | 진행 |
|---|---|
| 트리아지 | 시간표 선택 영역 아래에 안내 문구 블록 **신규 추가**, 위치·순서 변경 있음 → **레벨 2**. 스쿼드 코드 에디터 세팅 + 엔지니어 검토, 3일 |
| 세팅 | 대상 셀렉터를 실제 페이지에서 확정 → 비주얼 에디터 자동 셀렉터를 직접 작성한 셀렉터로 교체 → 코드 에디터로 블록 삽입 |
| flicker 대응 | 시간표 선택 영역 셀렉터를 Hide-until-code-runs에 등록. 3G 스로틀링 + 저사양 안드로이드에서 깜빡임 없음 확인 |
| 동적 렌더링 | 시간표 영역이 비동기 렌더링 → 고정 대기 대신 요소 등장 감지 방식으로 변경 (초기 세팅에서 저사양 기기 실패 재현됨) |
| 기능 QA | iOS Safari / Android Chrome / 인앱 브라우저 / 데스크톱 Chrome 4종 확인. 소형 모바일(360px)에서 줄바꿈 깨짐 발견 → 수정 후 재QA |
| 데이터 QA | 신규 Secondary 지표(안내 영역 노출률·조회율) 태깅이 미배포 상태임을 발견 → 데이터 담당에 요청, **런칭 3일 연기** |
| 엔지니어 검토 | 삽입 코드가 기존 스크립트와 충돌 없음 확인 |
| 런칭 후 30분 | 노출 이벤트 발생 ✅ / split 50:50 근접 ✅ / JS 에러 급증 없음 ✅ |
| 런칭 후 24시간 | 3층 지표 모두 집계 시작 ✅ / SRM 이상 없음 ✅ / 일 UV 실측이 가정치의 80% → 예상 기간 14일 → 17일로 재산정, 실현성 ✅ 유지 |

**학습:** 신규 Secondary 지표의 태깅 배포 여부는 **설계서 리뷰(6단계)에서 확인했어야 한다.** 세팅 단계에서 발견하면 런칭이 밀린다. 지표 설계 표에 "현재 트래킹 중인가" 열을 반드시 채우는 이유다.

## 코칭 활용 포인트

### 이 챕터를 코칭에 쓸 때

1. **트리아지부터 가르친다.** 대부분의 조직이 "실험을 못 하는" 이유는 아이디어 부족이 아니라 전부 레벨 3으로 설계하기 때문이다. 팀이 가져온 가설 5개를 그 자리에서 레벨 판정시키고, 레벨 3짜리를 레벨 1·2로 깎아보게 한다.
2. **QA를 두 갈래로 쪼개서 각인시킨다.** "화면 확인"만 하고 런칭하는 팀이 압도적으로 많다. 데이터 QA를 빠뜨리면 실험이 끝난 뒤에야 분석 불가를 알게 된다는 점을 실패 사례로 보여준다.
3. **flicker를 직접 보여준다.** 말로 설명하면 잘 와닿지 않는다. 스로틀링을 켜고 깜빡이는 화면을 시연하면 즉시 이해된다.
4. **런칭 직후 체크를 루틴으로 만든다.** 30분/24시간 두 개의 알람을 캘린더에 등록하게 한다.

### 자주 나오는 수강자 질문

**Q. "개발 리소스를 못 받는데 실험을 어떻게 하나요?"**
레벨 1·2로 설계 가능한 문제영역부터 고른다. MVP 4질문의 4번(툴로 구현 가능한가)을 설계 단계의 필수 관문으로 만든다. 개발 리소스는 레벨 3 실험이 명확한 학습 가치를 보여준 뒤에 요청하는 편이 성공률이 높다.

**Q. "비주얼 에디터로 만들었는데 며칠 뒤 실험이 깨졌어요."**
비주얼 에디터가 자동 생성한 셀렉터가 사이트 배포로 무효화된 경우다. 레벨 2 이상은 직접 작성한 안정적 셀렉터로 교체하고, 실험 기간 중 사이트 배포 일정이 있으면 배포 직후 재QA를 예약한다.

**Q. "QA를 어디까지 해야 하나요?"**
기능 QA 체크리스트 + 데이터 QA 체크리스트 전 항목이다. 시간이 없다면 우선순위는 ① 노출 이벤트 수집 ② Primary 지표 수집 ③ Variant DOM 값 검증 ④ flicker ⑤ 나머지 디바이스. ①②가 깨지면 실험 자체가 무의미해진다.

**Q. "앱이라 실험을 못 합니다."**
웹뷰 지면 → 서버 응답 제어 → feature flag 선탑재 순으로 검토한다. 세 가지 모두 안 되는 화면만 레벨 3이다. 앱 조직에서 실험 문화를 정착시키는 실질적 첫 단계는 "다음 릴리즈에 flag 인프라를 태우는 것"이다.

### 흔한 실수 5가지

| 실수 | 결과 | 교정 |
|---|---|---|
| 코드 저장 = 검증 완료로 간주 | 잘못된 화면이 노출된 채 며칠 진행 | Preview에서 DOM 값을 눈으로 확인, 스크린샷 저장 |
| 데이터 QA 생략 | 종료 후 분석 불가 | 지표 3층 전부 수집 확인을 런칭 게이트로 |
| 캠페인 먼저, 지표 나중 | 시작 불가 또는 소급 집계 안 됨 | Metric을 캠페인 생성 전에 만든다 |
| flicker 미검증 | 실험군만 깜빡여 결과 오염 | Hide-until-code-runs + 저속·저사양 조건 검증 |
| 실험 중 설정 변경 | split·타겟이 바뀌어 데이터 해석 불가 | 변경이 필요하면 중단하고 새 캠페인으로 재시작 |

### 자동화/에이전트로 세팅할 때의 가드레일

AI 에이전트에게 캠페인 세팅을 맡길 때 작업 시작 시점에 넣는 문구:

```text
이번 작업에서는 추측하지 않는다.
원본 자료에 없는 정보는 만들어내지 않는다.
모르는 항목은 질문으로 남긴다.
한 번에 많은 작업을 실행하지 않고 단계별로 확인한다.
결과는 문서/스크린샷/실제 플랫폼 상태로 검증한다.
고객사명, 실험ID, 수치, 인용문은 외부 공유 전 익명화한다.
```

브라우저 자동화 시 복명복창 패턴:

```text
반드시 헬퍼 함수를 사용합니다.
현 단계의 step 파일을 꼼꼼히 읽습니다.
한 번에 많이 실행하지 않고 step-by-step으로 진행합니다.
매번 스크린샷으로 결과를 확인합니다.
```

자동화가 만든 캠페인도 **사람의 QA 게이트를 통과해야 런칭한다.** 에이전트는 세팅 속도를 올리는 도구이지 검증 책임의 이관 대상이 아니다.

## 외부 레퍼런스

Amplitude Experiment 공식 문서(amplitude.com/docs, help.amplitude.com) 기준으로 본문 "툴별 세팅 노트"의 Amplitude 절을 보강한다. 본문 표는 이 문서들을 기준으로 정정·확장했다.

### 1. 실험 생성 플로우 — 8단계

Amplitude Experiment는 **feature flag를 실험의 최소 단위**로 취급한다. "실험(experiment)"은 사실상 통계 분석 기능이 붙은 feature flag다.

| # | 단계 | 결정 사항 |
|---|---|---|
| 1 | 프로젝트 선택 → flag 이름 지정 | 네이밍 컨벤션을 여기서 강제한다 (본문 3-4 참조) |
| 2 | **Evaluation mode** 선택 | Remote(Amplitude 서버가 평가) vs Local(SDK 내 로컬 평가) |
| 3 | **Bucketing unit** 지정 | "가장 좋은 bucketing unit은 대개 user". B2B는 Company ID 등 |
| 4 | Deployment 연결 | 프로젝트 내에서 flag/experiment를 특정 앱·플랫폼에 전달하는 컨테이너. **플랫폼별(web/iOS/Android) 분리 운영 권장** |
| 5 | Variant 생성 | name, value(식별자), **payload(JSON)** — payload가 remote config 성격의 핵심 |
| 6 | **Assignment** 섹션에서 타겟팅 | 지역·인구통계·사용량 등 룰 기반 세그먼트 + 트래픽 배분 %(합 100%) |
| 7 | **Goals(메트릭)** 섹션에서 지표 연결 | success / guardrail 타입 지정, 증가·감소 방향 지정, MDE 설정 |
| 8 | Flag Activate → 실험 시작 | |

**Inclusions**: 특정 user ID / device ID를 강제로 특정 variant에 배정하는 기능. 주로 개발·QA용이며, **대량 수동 배정은 랜덤화를 왜곡해 SRM 원인이 된다.**

### 2. 지표 연결 — Goal 1개 + tracked metrics

- 실험당 **Goal(주 지표)은 1개만** 지정 가능하다. 실험 성공/실패 판정 기준이 되는 "사용자의 단일 핵심 행동"이어야 한다. → 본 KB의 "Primary는 정확히 1개" 원칙이 툴 레벨에서 강제된다.
- 그 외 여러 **tracked metric(secondary)**을 붙여 모니터링할 수 있지만 성패 판정에는 관여하지 않는다.
- **Success metric**(좋아지길 바라는 것: 전환율·인게이지먼트·매출·리텐션) / **Guardrail metric**(나빠지면 안 되는 것: 성능·품질·비즈니스 헬스)을 타입으로 구분해 지정한다. 예: 체크아웃 실험에서 구매완료율 = success, 페이지 로드시간·에러율 = guardrail.
- 사용 가능한 지표 유형: Unique conversions, Event totals, Formula, Funnel conversions, Retention, Sum/Average of property value, **Aggregated Metrics**(웨어하우스 기반 사전계산 지표 — 복잡한 비즈니스 계산용).
- 기간 산정: **Duration Estimator**가 최근 29~30일 트래픽을 Analytics에서 가져와 일평균 유저 수 기반으로 필요 기간을 계산한다. Confidence level·statistical power·MDE·표준편차를 조정 가능하며 **T-test 로직을 사용**한다(실행 중 실험 화면에 표시되는 duration estimate는 sequential testing 기반이라 별개 — 용도를 혼동하지 않는다). 별도 [Sample Size Calculator](https://amplitude.com/calculate/sample-size)도 제공.

출처: [Define your experiment's goals](https://amplitude.com/docs/feature-experiment/workflow/define-goals) / [Advanced metric use cases](https://amplitude.com/docs/feature-experiment/advanced-techniques/advanced-metric-use-cases) / [Set the MDE](https://amplitude.com/docs/feature-experiment/experiment-theory/experiment-set-mde) / [Experiment duration estimates FAQ](https://amplitude.com/docs/faq/experiment-duration-estimates)

### 3. Exposure 이벤트 — 이 툴에서 가장 자주 깨지는 지점

- **정의**: 사용자가 실험 variant를 "실제로 마주친 순간"을 알리는 엄격하게 정의된 분석 이벤트. 사용자가 그 variant와 **상호작용했는지 여부와 무관하게 "보여준" 시점**에 발생한다.
- 실험 분석의 **앵커 포인트**다. 이 시점 이후에 발생한 지표 이벤트만 해당 variant에 귀속시켜 카운트한다(노이즈 감소 → 유의성 도달 가능성 향상).
- **기본값은 Amplitude Exposure 이벤트**(SDK가 `.variant()` 호출 시 자동 발송)이고, Amplitude는 **이 기본값을 그대로 쓰라고 권장**한다. 커스텀 exposure 이벤트는 잘못된 시점에 발동할 위험이 커서 **SRM을 유발하기 쉽다.**
- 그럼에도 커스텀이 필요한 경우의 경험칙: exposure는 **"variant 간 차이가 지표에 의미 있게 반영되기 시작하는 첫 순간"**에 발동해야 한다. 너무 이르면 노이즈가 섞이고, 너무 늦으면 실제로 노출된 사용자를 누락한다.
- **로컬 평가(local evaluation)는 assignment 이벤트를 만들지 않는다** → 커스텀 exposure 이벤트가 **필수**다. 로컬 평가를 쓰면서 커스텀 exposure를 만들지 않으면 exposure 데이터 자체가 존재하지 않는다.
- 커스텀 exposure의 대표적 실수: **fallback/default variant(할당 실패 시 control 등)에 exposure를 트래킹하는 것.** flag 응답을 제때 못 받아 control로 폴백된 사용자를 노출로 세면 안 된다.
- assignment ≠ exposure: assignment는 variant 배정 직전(보통 세션 초반), exposure는 사용자가 실제로 variant를 트리거할 때(플로우 후반) 발생한다. **assignment는 오늘, exposure는 다음 날 발송되는 경우도 정상**이다(양쪽 다 user property가 안 바뀌었다면 무해).

출처: [Event tracking](https://amplitude.com/docs/feature-experiment/under-the-hood/event-tracking) / [Experiment Evaluation](https://amplitude.com/docs/feature-experiment/implementation) / [Photoroom — Never underestimate the power of exposure events](https://www.photoroom.com/inside-photoroom/the-power-of-exposure-events-amplitude)

### 4. 릴리즈 주기가 긴 앱 — dark launch 패턴

본문 "릴리즈 주기가 긴 앱 환경에서의 세팅 전략" 표의 3번(Remote config / feature flag 선탑재)을 Amplitude 기능으로 구체화한 것이다.

| 패턴 | 내용 |
|---|---|
| **Payload = Remote config** | variant에 JSON payload를 실어 값(문구·임계치·노출 여부)을 원격으로 바꾼다. 공식 문서 표현: "그 숫자를 원격으로 설정하고, 개발 작업 없이도 그때그때 바꿀 수 있다." 코드 재배포 없이 실시간 조정 가능 |
| **Dark launch** ★ | 먼저 코드를 배포하되 **flag는 꺼둔 상태로 릴리즈** → 실험 시작은 "all users" 세그먼트 **배분 비율만 조정**해서 한다. 앱 배포 주기(2~4주)와 실험 시작·트래픽 조정(즉시)을 분리하는 핵심 장치 |
| **Deployment 플랫폼 분리** | web/iOS/Android를 별도 Deployment로 두면 배포 주기가 다른 플랫폼별로 각각 다른 시점에 flag를 켤 수 있다 |
| **Local evaluation** | 서버 호출 없이 클라이언트에 캐시된 규칙으로 즉시 평가 → 네트워크 지연에 민감한 모바일 앱에서 성능 이점. 단 exposure 계측 필수(위 3절) |

★ = 공식 문서의 개별 사실(Activate/Deactivate 대신 배분 비율로 트래픽을 제어하라는 권장 + payload remote config)을 조합한 해석이며, "긴 릴리즈 주기"를 다루는 전용 공식 문서는 확인하지 못했다. **고객사 적용 시 Amplitude CS 채널에 release-train 관련 별도 가이드가 있는지 재확인 권장.**

### 5. 런칭 전 최종 확인 (Amplitude 사용 시 추가 항목)

본문 "런칭 판정표"에 아래를 덧붙인다.

- [ ] Evaluation mode를 확정했고, **Local이면 커스텀 exposure 이벤트를 구현했다.**
- [ ] Bucketing unit이 설계서의 실험 단위와 일치한다.
