# 08. 모니터링·종료 의사결정 — 10단계 중 [8~9단계]

> 한 줄 요약: 실험이 도는 동안 **"측정이 제대로 되고 있는가"만 확인하고 "누가 이겼는가"는 판정하지 않는다.** 그리고 종료는 결과가 아니라 사전에 정한 기간·샘플 도달로 결정한다.

---

## 개념·프레임워크

### 1. 이 단계가 하는 일

7단계(세팅→테스트→런칭)가 끝나면 실험은 이미 사용자에게 노출되고 있다. 이 시점부터 종료 버튼을 누를 때까지가 8~9단계다.

| 단계 | 질문 | 산출물 |
|---|---|---|
| 8. 모니터링 | 이 실험은 **신뢰할 수 있는 데이터를 쌓고 있는가** | 모니터링 로그, 중단/유지 판단 |
| 9. 종료 의사결정 | 이제 **판정해도 되는가** | 종료 승인, 또는 연장/재설계 결정 |

핵심 분리 원칙: **8단계는 운영 신뢰성만 본다. 효과 크기·승패는 9단계 이후(10단계 결과분석)에서 본다.**

### 2. 확인 대상 vs 판정 대상 — 절대 섞지 않는다

| 구분 | 실험 진행 중 봐도 되는 것 (확인) | 실험 진행 중 보면 안 되는 것 (판정) |
|---|---|---|
| 데이터 유입 | 이벤트가 들어오는가, 0건인 지표는 없는가 | — |
| 배분 | Control/Variant 배분 비율이 설계대로인가 (SRM) | — |
| 가드레일 | **심각한 훼손**(장애 수준)이 있는가 | 가드레일이 몇 % 나빠졌는지로 승패 판단 |
| Primary | (지표가 기록되고 있는지만) | 지금 이기고 있는가 / 지금 종료할까 |
| Secondary | — | 원인 해석, 세그먼트 파고들기 |

한 문장으로: **"확인은 하되 판정하지 않는다."**

### 3. No Peeking 원칙 — 왜 중간 판독이 위험한가

**중간에 결과를 들여다보고 그때그때 판정하려는 행위(peeking)는 위양성(false positive)을 구조적으로 증가시킨다.**

- 근거 수치: **A/B 실험을 매일 peek 하면 잘못된 winner를 채택할 확률이 57% 증가.** (Speero Keynote 1 / Leah Tharin)
- 메커니즘 ① **다중 검정**: p<0.05는 "1회 판독 시 5% 위양성"을 전제로 한 임계값이다. 20일간 매일 판독하면 판독 횟수만큼 "우연히 p<0.05가 스쳐 지나갈" 기회가 늘어난다. 전환율은 표본이 쌓이는 동안 진동하므로, 진짜 차이가 0이어도 어느 날 하루는 유의해 보인다.
- 메커니즘 ② **정지 규칙의 편향**: "원하는 결과가 나온 날 멈춘다"는 규칙은 결과에 따라 표본 크기를 결정하는 것이다. 이는 통계적으로 표본이 랜덤하지 않게 되는 것과 같다.
- 메커니즘 ③ **인지 편향**: 사람이 ship/kill 결정에 들어가 있는 한, peeking은 **자기 믿음을 강화하는 방향으로 결과 해석을 왜곡한다.** 원하던 방향이면 "역시 됐다"로 조기 종료하고, 반대 방향이면 "아직 표본이 부족하다"로 연장한다. 같은 데이터에 대해 비대칭적으로 반응하는 순간 실험은 검증 도구가 아니라 자기확신 기계가 된다.

#### 방증: 사전등록 규칙의 효과

- 1970–2012, US NIH 대규모 임상시험 기준 (Kaplan & Irvin, *PLOS ONE*, 2015).
- 2000년에 룰 추가: **가설을 ClinicalTrials.gov에 시작 전에 등록해야 하고, 데이터를 본 뒤 winning metric을 바꿀 수 없다.**
- 결과: **유의미한 긍정 효과 보고율이 57% → 8%로 폭락.**
- 해석: 결과를 본 뒤 지표를 고를 자유가 있으면, 그 자유 자체가 거대한 거짓 양성 공장이다. 실험 설계서(6단계)에서 Primary 1개와 기간·샘플을 확정하는 이유가 여기 있다.

#### No peeking의 실무적 예외

원칙은 "판정 금지"이지 "보지 마라"가 아니다. 아래 3가지는 매일 봐도 된다. 단, **이 3가지를 보다가 Primary 수치가 눈에 들어와도 그 수치로는 아무 결정도 하지 않는다.**

1. 데이터 유입(이벤트 수집 정상 여부)
2. 배분 비율(SRM)
3. 장애 수준 가드레일(결제 실패, 에러율, 페이지 로딩)

> 운영 팁: 대시보드를 2개로 분리한다. **"헬스 대시보드"(위 3개만)** 는 매일 보고, **"결과 대시보드"(Primary/Secondary 리프트)** 는 종료 전까지 접근하지 않거나 팀 내 열람 권한을 제한한다. 눈에 안 보이게 만드는 것이 의지력보다 강하다.

### 4. 통계적 유의성이 보장하지 않는 것

Stat-sig가 의미하는 것은 딱 하나다.

> "결과가 clean test 하에서 단순 우연일 가능성이 낮다."

그게 전부다. Stat-sig는 다음 중 **무엇도 보장하지 않는다.**

- ✗ 메트릭이 옳다는 보장
- ✗ 효과가 지속될 것이라는 보장
- ✗ 일반화 가능하다는 보장
- ✗ 비즈니스 성장으로 이어진다는 보장
- ✗ Ship해도 된다는 보장

**Stat-sig는 1개 질문에 답한다. 실제로 알고 싶은 질문은 3개 질문이 더 떨어진 곳에 있다.**(메트릭이 맞나? 효과가 유지되나? 비즈니스에 연결되나?) 각 단계를 다 잘 결정하더라도 최종 "정말로 사업에 기여할 확률"은 25% 수준으로 떨어질 수 있다.

이 인식은 9단계에서 특히 중요하다. **"p<0.05가 떴으니 지금 끝내자"는 종료 사유가 될 수 없다.**

## 절차

### 8단계-A. 런칭 직후 24~48시간 체크 (Launch Health Check)

런칭 후 첫 24~48시간은 **실험의 성패가 아니라 실험의 유효성 자체가 결정되는 구간**이다. 이 구간에 문제를 못 잡으면 2~4주를 통째로 버린다.

| # | 체크 항목 | 정상 기준 | 이상 시 조치 |
|---|---|---|---|
| 1 | 데이터 유입 | Primary·Secondary·Guardrail 전 지표에 이벤트가 들어옴 | 0건 지표 발견 → **즉시 중단**, 트래킹 수정 후 재시작 |
| 2 | 노출 수 | 예상 일 트래픽의 ±30% 이내 | 크게 미달 → 타겟팅 조건·트리거 오류 점검 |
| 3 | 배분 비율(SRM) | 설계 비율(예: 50:50)과 실측이 유의하게 다르지 않음 | 유의한 불일치 → **즉시 중단**. 배분 로직·봇 트래픽·리다이렉트 점검 |
| 4 | 중복 노출 | 동일 유저가 양쪽 그룹에 모두 잡히지 않음 | 발생 시 중단, 식별자(user id vs device id) 정책 점검 |
| 5 | 렌더링 QA | 주요 브라우저·OS·화면폭에서 Variant가 의도대로 보임 | 깨짐 발견 → 중단 후 수정. 부분적이면 해당 환경 제외 |
| 6 | 심각 가드레일 | 결제 실패율·에러율·로딩시간에 급변 없음 | 급변 → **즉시 중단**(장애 대응 우선) |
| 7 | 지표 정의 확인 | 대시보드의 지표 정의가 설계서와 동일 | 불일치 → 정의 수정 후 데이터 재집계 가능한지 확인 |

> SRM(Sample Ratio Mismatch)은 "배분이 틀어졌다"는 신호이자 **거의 모든 경우 데이터 신뢰도 전체를 무너뜨리는 신호**다. SRM이 있으면 리프트가 아무리 예뻐도 그 결과는 쓰지 않는다.

### 8단계-B. 이후 주기 체크

첫 48시간을 통과하면 체크 주기를 늘리고 항목을 줄인다.

| 주기 | 항목 | 소요 | 산출 |
|---|---|---|---|
| 매일(자동 알림 권장) | 데이터 유입 이상, SRM, 장애 수준 가드레일 | 2~3분 | 이상 시 알림만 |
| 주 1회(스프린트 정기 회의) | 위 3개 + 누적 노출 진행률(샘플 목표 대비 %) + 예상 종료일 | 10분 | 모니터링 로그 1줄 |
| 필요 시 | 외부 이벤트 기록(프로모션, 대형 마케팅, 시즌성, 앱 업데이트, 장애) | — | 로그에 메모 |

주 1회 체크에서 **보고하는 문장은 딱 하나로 고정한다.**

> "샘플 목표 대비 진행률 XX%, 예상 종료일 M/D, 헬스 이상 없음."

리프트를 말하지 않는다. 말하는 순간 팀 전체가 peeking을 시작한다.

### 8단계-C. 모니터링 중 개입해야 하는 경우 (중단 기준)

| 중단 등급 | 트리거 | 조치 |
|---|---|---|
| **즉시 중단** | 결제/가입 등 핵심 전환 경로 장애, 에러율 급등, 개인정보·보안 이슈 | 실험 정지 → 원인 수정 → 데이터 폐기 후 재시작 |
| **즉시 중단** | SRM 감지, 중복 노출, Primary 지표 미수집 | 실험 정지 → 트래킹/배분 수정 → **처음부터 재시작**(부분 데이터 병합 금지) |
| **즉시 중단** | Variant 렌더링 심각 오류(주요 환경에서 콘텐츠 미노출·레이아웃 파괴) | 정지 → 수정 → 재시작 |
| **조건부 중단** | 가드레일이 사전에 정한 **중단 임계선**을 넘어 악화 | 팀 합의된 임계선(예: 결제 전환율 상대 -10% 이상 지속 3일)에 도달 시 중단. **임계선은 실험 설계서에 미리 적어둔다** |
| **유지** | Primary가 지금 지고 있다 / 이기고 있다 | 아무것도 하지 않는다. 이것은 중단 사유가 아니다 |
| **유지** | 팀·경영진의 "그만 하고 빨리 반영하자" 압력 | 사전 합의한 종료 조건을 근거로 유지. 압력은 중단 사유가 아니다 |

핵심: **중단 사유는 "데이터가 잘못되고 있다" 또는 "사업이 다치고 있다" 둘 뿐이다. "결과가 마음에 든다/안 든다"는 중단 사유가 아니다.**

### 9단계. 종료 의사결정 프로세스

#### 원칙: 사전에 정한 기간·샘플 도달로 종료한다

6단계(실험 설계)에서 계산한 값이 종료 조건이다.

- 그룹당 필요 샘플 = MDE·Baseline·검정력으로 산출한 값
- 기간 = (그룹당 샘플 × 변형 수) ÷ 일 트래픽
- **최소 기간은 요일 주기를 최소 1회, 권장 2회 포함해야 한다**(주중/주말 행동 차이 흡수 → 최소 7일, 권장 14일 이상)

기간 실현성 기준:

| 산출 기간 | 판정 | 조치 |
|---|---|---|
| ≤ 28일 | ✅ 진행 | 그대로 진행 |
| 28~90일 | ⚠️ 주의 | MDE 키우기(더 큰 변화 설계)·퍼널 세분화(더 상위 지표를 Primary로) 검토 |
| > 90일 | 🚫 재설계 | 이 실험은 A/B로 검증하지 않는다. 다른 검증 방법(UT, 정성, 로그 분석, 순차 배포)으로 전환 |

#### 종료 게이트 (4개 모두 통과해야 종료 승인)

| # | 게이트 | 확인 |
|---|---|---|
| G1 | 사전에 정한 **기간**에 도달했다 | 설계서의 종료 예정일 |
| G2 | 사전에 정한 **그룹당 샘플**에 도달했다 | 노출 수 기준(전환 수 아님) |
| G3 | 요일 주기를 최소 1회(권장 2회) 포함했다 | 시작·종료 요일 확인 |
| G4 | 기간 중 **결과 신뢰를 훼손하는 외부 이벤트**가 없었다 | 대형 프로모션·장애·시즌 이벤트 로그 |

G4가 깨지면(예: 실험 중반에 전사 할인 프로모션이 돌았다) 해당 구간을 제외하고 재집계하거나, 재실험을 검토한다.

#### 조기 종료: 조건과 위험

조기 종료는 **원칙적으로 하지 않는다.** 예외는 아래 3가지뿐이며, 어느 것도 "이겼으니 그만"이 아니다.

| 조기 종료 사유 | 허용 여부 | 비고 |
|---|---|---|
| 데이터 오염·장애·SRM | ✅ 허용(=중단) | 결과를 쓰지 않고 폐기 |
| 가드레일 중단 임계선 도달 | ✅ 허용 | Loss로 기록하고 학습 정리 |
| **사전에 설계된 순차 검정(Sequential Testing) 규칙 도달** | ✅ 허용 | 아래 참조. **설계 단계에서 규칙을 정해둔 경우에만** |
| Primary가 유의하게 이기고 있음 | ❌ 금지 | 대표적 위양성 생산 경로 |
| Primary가 지고 있어서 손해가 아까움 | ❌ 금지 | 노벨티/학습 효과로 초반이 왜곡될 수 있음 |
| 다음 릴리즈 일정이 급함 | ❌ 금지 | 일정은 6단계에서 반영했어야 할 제약 |

**순차 검정(Sequential Testing)** 은 "중간에 봐도 되는 규칙을 미리 만들어 두는" 방법이다. 고정 샘플 없이 중간에도 종료 가능하되, **너무 높거나 낮을 때만 종료하고 애매하면 계속한다**(Goldilocks 방식). 베이지안 승자확률 기준 예시:

- 95% 이상 → Variation 채택
- 5% 이하 → Variation 폐기
- 5%~95% → 실험 계속

장점은 트래픽이 적은 환경에서 실험을 더 빨리 끝낼 수 있다는 것. 전제는 **이 규칙을 실험 시작 전에 설계서에 적어두는 것.** 사후에 이 규칙을 꺼내 쓰면 그냥 peeking이다.

#### 연장 결정 기준

| 상황 | 연장 가능 여부 | 조건 |
|---|---|---|
| 샘플 목표 미달(트래픽이 예상보다 적었다) | ✅ 연장 | **연장 종료일을 새로 못박고 그 날짜를 다시 지킨다.** 무기한 연장 금지 |
| Primary는 유의, Guardrail이 유의하지 않게 나쁨 + 전환 절대 수가 적음 | ✅ 연장 | 가드레일 판단을 위한 추가 표본 확보 목적임을 명시 |
| Primary가 유의하지 않아서(=지고 있어서) 더 돌리고 싶다 | ❌ 금지 | 결과를 보고 기간을 늘리는 전형적 편향 |
| 90일을 넘길 것 같다 | ❌ 금지 | 연장이 아니라 **재설계**. MDE·Primary 재정의 |

> 연장은 1회로 제한하고, 연장 결정 사유를 로그에 남긴다. "왜 늘렸는지" 기록이 없으면 다음 분기에 같은 일이 반복된다.

## 실험 의사결정 위생 (Monday Fixes 5가지)

Speero Keynote 1(Leah Tharin)의 "월요일에 바로 할 일" 5가지. **공통 룰: AI에 적용하는 게이트 = 사람에게 적용하는 게이트.** 모델이든, 디렉터든, 창업자든 같은 룰을 적용한다.

### Fix 1. Probabilities, not assertions (단정 대신 확률)

- AI에게도, 자신에게도 **확률을 요구한다**: "나는 X% 확신한다, 이유는 이것이다."
- AI와 자기 자신에게 **반대 입장에서 논쟁하라**고 강제한다: "내가 이것에 대해 틀렸을 수 있는 이유는?"
- 주의: **AI로 AI를 채점하지 않는다.** 정밀도·길이·자기일관성을 측정할 뿐 품질을 측정하지 않는다. 굳이 한다면 pairwise 비교, 무작위 순서, 다른 모델 패밀리 다중 심판 같은 프로토콜이 필요하다.

### Fix 2. Re-baseline every quarter (분기별 리베이스라인)

- 옛날 룰: "2년 넘은 데이터 쓰지 마라."
- 새 룰: **"2분기 넘은 데이터 쓰지 마라."**
- 이유: AI가 유입 채널과 퍼널 구성을 바꾸는 속도. 예를 들어 검색 결과의 AI 요약 때문에 사이트에 오던 사람의 일부가 오지 않고, 도달한 사람만 구매 의향이 높아진다. 그러면 CTR 같은 표면 지표는 좋아 보이지만 **효율이 좋아진 게 아니라 모집단 구성이 바뀐 것**이다. 이 변화를 인식하지 못하면 잘못된 결론을 학습한다.
- 실무 기준: **"이번 분기 우리 샘플 구성을 한 줄로 설명할 수 없다면, 우리에겐 샘플이 없는 것이다."**
- 적용: 분기마다 Baseline 전환율·트래픽·디바이스 구성비·유입 채널 구성비를 다시 측정하고, 샘플사이즈 계산의 입력값을 갱신한다.

### Fix 3. No peeking

- 앞의 [No Peeking 원칙](#3-no-peeking-원칙--왜-중간-판독이-위험한가) 참조. 매일 peek 시 잘못된 winner 채택 확률 **+57%**.

### Fix 4. Use the right model (분석에 쓰는 모델을 강제하라)

- AI 모델을 분석 용도로 쓸 때 **모델 종류를 명시적으로 지정**한다.
- 요약·집계 같은 단순 작업에서는 작은 모델이 큰 frontier 모델보다 자주 더 안정적이다. 큰 모델은 추론은 좋지만 단순 집계에서 흔들리는 경향이 있다.
- 사내 도구가 어느 모델을 쓰는지 모른다면 검증 체크포인트를 박아둔다. **모든 모델에는 10%대의 오류 위험이 있고, 그건 데이터 분석에서 큰 숫자다.**

### Fix 5. Don't run tests on small stuff (작은 것에 테스트 돌리지 않기)

- 작은 변화에 실험을 돌리면 **효과가 작아 노이즈만 표면화된다.**
- **Data-driven vs Data-informed의 차이**: Data-driven은 모든 걸 증명하려 한다. Data-informed는 **"이건 지금 안 테스트해도 된다"고 판단할 수 있다.**
- 매 테스트마다 잡음이 들어온다. 테스트 횟수 자체가 조직의 위양성 총량을 늘린다.

#### "작은 것"의 판별 기준 (실험 대상에서 제외)

| 기준 | 질문 | 제외 신호 |
|---|---|---|
| 기대 효과 크기 | 이 변화가 설계 단계 MDE를 넘을 것으로 기대되는가 | 기대 리프트 < MDE → 테스트해도 못 잡는다 |
| 가역성 | 틀렸을 때 되돌리는 비용이 낮은가 | 되돌리기 쉽고 리스크 낮음 → 그냥 반영하고 모니터링 |
| 의사결정 레벨 | Meta 결정인가 Local 결정인가 | Local + 저위험 → 테스트 없이 판단 |
| 학습 가치 | 이 실험이 끝나면 우리 믿음이 바뀌는가 | 결과와 무관하게 행동이 같다면 → 테스트 불필요 |

> Meta vs Local 판별 룰: **"잘못된 결론(false positive)을 채택했을 때의 비용이 클수록 Meta 의사결정이다."** 무엇을 바꾸는가가 아니라, 틀렸을 때 회복 비용이 기준이다. 홈 카피 변경(전체 유입·마케팅 메시지에 영향)은 Meta, 특정 랜딩페이지 카피 변경은 Local.

### 템플릿 5. Complexity Checklist — 실험 1건당 반드시 갖춰야 할 7가지

종료 전에 이 7가지가 문서로 존재하는지 확인한다. **이 7가지만 강제해도 조직의 bias가 크게 줄어든다.**

| # | 항목 | 확인 질문 | 채움 |
|---|---|---|---|
| 1 | **Author** | 이 실험의 작성자는 누구인가 (사람 이름 — 책임의 시작점) | |
| 2 | **Second pair of eyes** | 누가 동료 검토했는가 | |
| 3 | **Decision** | 이 실험으로 무엇을 결정하려 했는가 | |
| 4 | **Claim** | 가설·주장은 무엇인가 (PSR 한 문장) | |
| 5 | **Inference chain** | 데이터 → 결론까지 어떻게 갔는가 | |
| 6 | **Confidence** | 모든 데이터를 고려한 후 현재 확신도는 몇 %인가 | |
| 7 | **Reversibility** | 어떤 증거가 나오면 이 결정을 뒤집을 것인가 | |

참고 벤치마크(한 고성장 SaaS의 400+ 실험 자체 감사 결과 — Speero Keynote 1 / Leah Tharin 발표 사례):

- **41%** 의 실험: 가설이 문서로 적혀있지 않음
- **74%** 의 "위너" 실험: 주장한 lift를 감지할 샘플사이즈가 부족했음(일부는 12배, 일부는 30배의 샘플이 필요) → **승리가 30~50% 부풀려진 상태**
- **약 50%** 의 중단된 실험: 결론이 적혀있지 않음

> "AI가 이걸 만든 게 아니다. AI는 이미 자기 사고를 author하지 않는 시스템에 들어와서, 그걸 보이지 않는 형태로 압축했을 뿐이다." — 프로세스가 깨져 있으면 AI는 그 깨진 프로세스를 더 빠르고 더 안 보이게 굴린다.

실험 루프 8단계 중 **사람이 반드시 결정해야 하는 구간**:

| 단계 | 내용 | AI 위임 |
|---|---|---|
| 1 | 아이디어 발생 | 가능 |
| 2 | "해야 하는가?" | 사람 |
| 3 | **"어떻게/무엇을 테스트하나?"** | **금지** |

| 5 | 데이터 분석 | 가능(검증 필요) |
| 6 | **결론 도출** | **금지** |
| 7 | **컨텍스트 정리·문서화** | **금지** |

## 워크드 예시

> 아래는 설명을 위해 지어낸 가상 예시다. 업종·수치·발화 모두 실제 사례가 아니다.

### 예시 A. 중고 거래 앱 — 런칭 48시간 내 SRM 감지

- 상황: 채팅 화면 상단의 「안전결제 안내」 배너 실험. 설계 배분 50:50, 목표 그룹당 노출 3만.
- 24시간 체크: 데이터 유입 정상, 렌더링 정상. 그러나 **실측 배분이 약 55:45**(대조군이 많음)로 나옴.
- 판단: SRM 신호. Primary 리프트가 +7%로 이미 좋게 나오고 있었지만 **리프트는 보지 않고 즉시 중단**.
- 원인: 처치군 배너 스크립트가 화면 로딩을 늦춰, 채팅 화면을 금방 닫은 처치군 사용자의 노출 이벤트가 기록되지 않았다. 처치군에는 오래 머문 사용자만 남아 리프트가 부풀려진 것이다.
- 조치: 노출 이벤트를 배너 렌더링이 아니라 화면 진입 시점에 기록하도록 수정 → 기존 데이터 전량 폐기 → 재시작. 재시작 후 배분 50.2:49.8, 최종 Primary 리프트는 +1.1%(유의하지 않음)로 나옴.
- 배움: **첫 48시간에 SRM을 못 잡았다면 "+7% 승리"를 그대로 반영했을 것이다.** 헬스 체크가 리프트 체크보다 먼저다.

### 예시 B. B2B SaaS 무료체험 — 조기 종료 압력을 견딘 경우

- 상황: 체험 첫 화면의 3단계 온보딩 체크리스트 실험. 설계 기간 14일, 그룹당 목표 노출 7,500.
- 6일차: 대시보드에서 Primary(워크스페이스 생성률)가 +8%, p≈0.04로 유의. 영업 담당자가 "이미 이겼으니 오늘 종료하고 전체 반영하자"고 요청.
- 팀 판단: **종료 게이트 4개 중 G1(기간)·G2(샘플) 미달, G3(요일 주기) 미충족.** 조기 종료 사유는 데이터 오염·가드레일 훼손 둘 뿐이므로 유지 결정. 설계서의 종료 조건 문구를 근거로 공유.
- 14일차 결과: Primary +2.0%, p≈0.14로 유의하지 않음. 6일차 유의성은 웨비나 직후 몰린 고관여 가입자에서 온 일시적 진동이었음.
- 후속: 리프트 방향이 양수이고 신뢰구간 대부분이 양수 영역이라 판단 보류 → 표본을 더 확보하는 재실험으로 연결.
- 배움: **6일차에 종료했다면 조직은 "이 솔루션은 +8% 효과가 있다"는 잘못된 학습을 자산으로 등록했을 것이다.** 위양성의 진짜 비용은 그 실험 1건이 아니라, 그 잘못된 믿음 위에 쌓일 다음 10개 실험이다.

## 코칭 활용 포인트

### 이 챕터를 쓸 세션 유형

- 실험은 돌리는데 결과 신뢰가 낮은 조직(중간에 자주 끄고 켠다, 종료 시점이 매번 다르다)
- 경영진/사업 부서의 조기 종료 압력이 반복되는 조직
- "실험을 많이 돌린다"가 KPI가 되어 있는 조직

### 수강자 흔한 질문 · 답변

| 질문 | 답변 |
|---|---|
| "중간 결과를 아예 안 보는 건 현실적으로 불가능한데요?" | 보는 것과 판정하는 것을 분리하라. 헬스 대시보드는 매일, 결과 대시보드는 종료 전 비공개. 대시보드 분리가 의지력보다 강하다 |
| "임원이 매일 물어보는데 뭐라고 하나요?" | 고정 문장 1개로 응답: "진행률 XX%, 예상 종료 M/D, 헬스 이상 없음." 이 문장을 스프린트 시작 시 임원과 사전 합의해두면 압력이 크게 줄어든다 |
| "명백히 지고 있는데도 끝까지 돌려야 하나요?" | 가드레일 중단 임계선에 걸리지 않는 한 돌린다. 초반 열세는 학습 효과/변화 저항일 수 있고, "얼마나 지는가"도 학습 자산이다 |
| "트래픽이 적어서 28일로도 샘플이 안 찹니다" | 이 경우 판정 프레임 자체를 바꾼다(09 챕터 저트래픽 해석). 또는 순차 검정 규칙을 **설계 단계에서** 넣는다 |
| "실험 개수를 늘리라는 지시가 있습니다" | 볼륨은 rigor를 해결하지 않는다. 부담이 selection에서 interpretation으로 이동할 뿐. 진짜 KPI는 "한 분기에 우리 믿음이 실제 시그널로 몇 번 업데이트됐나"다 |

### 흔한 실수 (코치가 먼저 짚어줄 것)

1. **모니터링 로그에 리프트 칸을 만든다** → 칸이 있으면 채우고, 채우면 판정한다
2. **중단 임계선을 설계서에 안 적어놓고 실험 중에 정한다** → 사후 임계선은 자기 편의대로 움직인다
3. **연장 종료일을 정하지 않고 연장한다** → 무기한 연장은 결국 "원하는 결과 나올 때까지"가 된다
4. **부분 데이터를 병합한다** ("앞 3일은 트래킹이 깨졌으니 4일차부터 합쳐서 보자") → 노출 모수 정의가 달라져 리프트가 왜곡된다
5. **작은 변화까지 전부 테스트한다** → 위양성 총량이 늘어나고, 정작 중요한 실험에 트래픽이 부족해진다

### 세션 진행 팁

- 종료 게이트 4개를 **고객사 실제 진행 중 실험에 그 자리에서 적용**시킨다. 대부분 G3(요일 주기)나 G4(외부 이벤트 로그)에서 걸린다. 이 체감이 가장 효과적이다.
- Complexity Checklist 7항목을 최근 종료 실험 3건에 적용시켜 채움률을 세어보게 한다. 벤치마크(가설 미작성 41%, 결론 미작성 ~50%)와 비교하면 방어적 반응 없이 자기 진단이 된다.
- Monday Fixes는 5개를 다 주지 말고 **조직 성숙도에 맞춰 1~2개만 처방**한다. 초기 조직은 Fix 3(No peeking) + Fix 5(작은 것 테스트 금지), 성숙 조직은 Fix 1(확률) + Fix 2(리베이스라인).

### A. Peeking · SRM · 신뢰성 (방법론 문헌)

#### A-1. Peeking이 위양성을 키우는 정도 — 반복 확인 횟수별 수치

본문 3절은 "매일 peek 시 잘못된 winner 채택 확률 +57%"(Speero) 하나를 근거로 든다. 다른 계열의 수치도 함께 제시하면 설득력이 커진다.

| 결과 확인 횟수 | 위양성률(α=5% 설계 기준) |
|---|---|
| 1회만 확인(고정 기간) | 약 **5%** |
| 5회 반복 확인 | 약 **15%** |
| 20회 반복 확인 | 약 **30%** |

메커니즘은 본문 설명과 동일하다. 빈도주의 p-value는 **"표본 크기를 사전에 고정하고 그 시점에만 1회 검정한다"**는 전제 위에서만 유효하다. 유의해지는 순간 멈추면 사실상 여러 번의 독립 검정을 수행한 것이 된다. Kohavi 등은 이를 **"5~10배의 편향(bias)"**으로 표현하며, 절대 원칙으로 *"p-value를 계속 모니터링하다가 유의해지는 순간 멈추지 말 것"*을 못박는다.

출처: [AB Tasty — Frequentist vs Bayesian](https://www.abtasty.com/blog/bayesian-ab-testing/) / [The Peeking Problem](https://medium.com/@atticusli/the-peeking-problem-why-checking-your-test-early-destroys-validity-92d5a7031e64) / [*Trustworthy Online Controlled Experiments* 요약](https://howtoes.blog/2025/06/11/trustworthy-online-controlled-experiments-complete-book-summary-all-key-ideas/)

#### A-2. Peeking 대응 3트랙 비교 — 무엇을 쓸지 고르는 기준

본문은 "고정 기간 원칙"을 기본으로 하고 순차 검정을 예외로 둔다. 세 트랙을 나란히 놓으면 그 선택의 근거가 분명해진다.

| 트랙 | 원리 | 도구 지원 | 비용·한계 |
|---|---|---|---|
| **① 고정 기간(Fixed-horizon)** | 사전에 표본 크기·기간을 정하고 그 시점까지 판정하지 않는다. 모니터링 목적 관찰은 허용 | 도구 무관 | 가장 단순하지만 **조직 규율**이 필요 |
| **② Sequential Testing / Always-valid p-value** | 표본 크기를 고정하지 않고도 어느 시점에 멈추든 위양성률이 보장되도록 설계. 신약 임상시험에서 유래 | **GrowthBook**: Asymptotic Confidence Sequences — 표준보다 넓은 "신뢰 수열" 사용, 튜닝 파라미터 N*를 **예상 의사결정 시점에 맞춰** 설정하는 것이 핵심 / **Statsig**: 사전 분석 구간마다 자동 보정 / **Optimizely**: mSPRT 기반 always-valid p-value | 신뢰구간이 **넓어지는 비용**을 치른다. N*에서 벗어날수록 비용 증가. Statsig는 "조기 유의성은 언더파워된 효과 추정치"라고 경고하며, **정확한 효과 크기가 중요하면 사전 계산된 표본까지 기다릴 것**을 권고 |
| **③ Bayesian** | 매 확인 시점마다 이전 결과가 사전분포가 되고 새 데이터가 증거로 갱신 — 원리적으로 반복 확인이 다중비교 문제를 일으키지 않음 | 다수 툴 지원 | **"베이지안이면 무제한으로 아무 때나 봐도 된다"는 과장된 통념.** 실제로는 정지 규칙(stopping rule)이 여전히 결과 해석에 영향을 주고, 사전분포가 틀리면 빈도주의보다 더 많은 데이터가 필요해질 수 있다 |

**저트래픽 조직에 대한 권고 (본문 코칭 포인트 보강)**

저트래픽 조직은 표본을 채우는 데 오래 걸려 **조바심에 의한 조기 종료 유혹이 하이트래픽 조직보다 구조적으로 크다** — 즉 peeking이 실제로 발생할 확률 자체가 더 높다. 그런데 sequential testing의 "넓어진 신뢰구간" 비용은 절대 표본이 적을 때 더 아프게 느껴진다(원래도 검정력이 부족한데 구간까지 넓어진다).

> 따라서 저트래픽 환경의 1차 대응은 **sequential testing이 아니라 "고정 기간 원칙 + 판정일 사전 고지"**다. sequential testing·Bayesian은 검토 가능한 보조 옵션으로 포지셔닝하는 편이 안전하다. 본문 종료 게이트 G1~G4를 그대로 쓰는 것이 저트래픽 조직에 오히려 더 맞다.

출처: [GrowthBook — Sequential Testing](https://docs.growthbook.io/statistics/sequential) / [Statsig — Sequential Testing](https://docs.statsig.com/experiments-plus/sequential-testing) / [Wish — Always Valid p-values](https://towardsdatascience.com/wish-tackles-peeking-with-always-valid-p-values-8a0782ac9654/) / [Eppo — Frequentist vs Bayesian vs Sequential](https://www.geteppo.com/blog/comparing-frequentist-vs-bayesian-approaches)

#### A-3. SRM 감지 시 대응 절차 — 종료 직전 체크

본문은 "SRM 감지 = 즉시 중단"까지만 규정한다. 중단 후 원인을 찾는 절차는 아래 순서로 진행한다. (SRM의 정의·원인 4단계 분류·카이제곱 검정 임계값은 [09 결과분석](09_analysis-reporting.md) 외부 레퍼런스 참조)

1. **세그먼트 분석** — 전체가 깨졌는지, 특정 국가·디바이스·브라우저에 국한되는지 확인. **전체는 정상이어도 특정 세그먼트만 깨질 수 있다.**
2. **트리거링 조건 재검토** — 분석 대상 필터가 실제로는 필요한 로그를 배제하고 있지 않은지
3. **시점 분석** — 언제부터 비율이 깨지기 시작했는지 시계열로 확인 → 배포 시점과 매칭
4. **기술 속성 비교** — 그룹 간 로딩 속도·API 지연 비교(트리트먼트가 이탈을 유발했는지 확인)
5. 원인 불명 시 **실험 재실행**. **원인 불명 SRM은 "출시 보류"가 기본값**이어야 한다.

Kohavi 등은 이를 조직 차원의 **"게이트"**로 명시한다 — **SRM이 감지된 실험은 결과 대시보드를 자동으로 숨기고(hide scorecard) 강한 경고를 띄운다.** 본문의 "헬스 대시보드 / 결과 대시보드 분리" 운영 팁이 이 게이트의 경량 버전이다.

방향이 뒤집힌 실제 사례: MSN에서 SRM 보정 전에는 결과가 음수였으나, 보정 후 실제로는 **+3.3%의 양의 효과**로 뒤집혔다.

**저트래픽 조직의 주의점**: 저트래픽에서는 카이제곱 검정의 검정력 자체가 낮아 실제로 배정이 깨졌어도(예: 48:52) 유의한 SRM으로 안 잡힐 수 있다. 반대로 표본이 작을수록 우연한 변동으로 비율이 크게 튀므로, **절대적인 배정 비율 차이(%)만 보고 "이상하다"고 판단하면 오판하기 쉽다.** 반드시 카이제곱 통계량·p-value 기준으로 판단한다. 또한 봇 트래픽이나 특정 캠페인 유입 스파이크 같은 단발성 이벤트 하나가 전체 비율을 쉽게 왜곡시킨다.

출처: [Microsoft Research — Diagnosing Sample Ratio Mismatch in A/B Testing](https://www.microsoft.com/en-us/research/articles/diagnosing-sample-ratio-mismatch-in-a-b-testing/) / [Eppo — Understanding Sample Ratio Mismatch](https://www.geteppo.com/blog/understanding-sample-ratio-mismatch-ab-testing)

#### A-4. Kohavi 신뢰성 체크리스트 — 실행 중·종료 시점 항목

본문 템플릿 5(Complexity Checklist 7항목)와 병행해 쓴다. 핵심 명제는 **"숫자를 얻는 것은 쉽다. 신뢰할 수 있는 숫자를 얻는 것이 어렵다."**

- **SRM 게이트** — 카이제곱 p-value가 임계값(예: 0.001) 미만이면 결과 대시보드를 자동으로 숨기고 강한 경고
- **다중비교 관리** — 핵심 모니터링 지표는 **5개 내외로 제한**. 너무 많으면 인지 과부하 + 우연한 유의성이 늘어난다. 지표가 많으면 FDR 통제 필요 → [06 실험 설계](06_experiment-design.md) 외부 레퍼런스
- **Peeking 방지** — 위 A-1·A-2
- **Twyman의 법칙** — *"흥미롭거나 이례적으로 보이는 수치는 대개 틀렸다."* 특히 breakthrough급 양의 결과일수록 더 의심하고 재검증한다

> **저트래픽·소규모 팀에서의 경량화**: 이 체크리스트는 원래 "연간 수만 건의 실험"을 돌리는 대기업 플랫폼 전제로 설계돼 자동화된 SRM 게이트·전문가 리뷰 미팅 같은 무거운 프로세스를 포함한다. 그대로 이식하지 말고 **① 자동 SRM 대시보드가 없다면 최소한 종료 시 수동 카이제곱 계산 1회는 반드시 거치고 ② 리뷰 미팅 대신 "종료 전 체크리스트 5줄"만이라도 팀 내 표준화**한다. 실험 횟수가 적어 메타분석·기관 기억 축적이 느린 조직일수록 개별 실험의 Twyman 체크(이례적으로 좋은 결과 의심하기)를 **더 엄격히** 적용해 표본 부족에서 오는 우연한 승리를 걸러야 한다.

### B. Amplitude Experiment의 자동 감지 기능 (공식 문서 기준)

본문 8단계-A/B의 수동 체크를 툴이 대신하는 부분이다. Amplitude를 쓰는 조직은 아래 3개 화면을 **헬스 대시보드**로 지정한다.

#### B-1. SRM 자동 감지

- Amplitude는 **sequential chi-squared test(alpha = .01)**로 관측된 variant 배분 비율이 설정값과 유의하게 다른지 **상시 감지**하고, 이상 감지 시 **알림(notification)을 발송**한다.
- SRM이 뜬 실험 결과는 **"의심(suspect)"으로 간주하고 신뢰하지 않는다** — 본문의 "즉시 중단" 등급과 동일한 처리.

#### B-2. 진단 화면 2종

| 화면 | 무엇을 보여주는가 | 언제 보는가 |
|---|---|---|
| **Diagnostics card** | variant jumping 비율, assignment→exposure 퍼널 차트 | SRM 알림이 왔을 때 원인 진단 |
| **Exposures without Assignments 차트** | 매일 "assignment 이벤트 없이 exposure 이벤트만 발생한 순유저 수"의 누적치 | **실험 시작 전·중 상시** — 데이터 품질 이상을 조기에 잡는 핵심 도구 |

Exposures without Assignments가 증가하는 3대 원인: ① user ID / device ID 불일치 ② 한 기기에서 여러 계정 전환 시 로그인·로그아웃 후 `fetch()` 재호출 누락 ③ **fallback variant에 대한 수동 exposure 트래킹 오류**.

#### B-3. SRM 원인 13가지 — 중간점검 체크리스트

공식 troubleshooting 문서가 정리한 빈도순 원인 목록이다. **코치가 실험 중간점검 시 그대로 훑어볼 수 있다.**

| # | 원인 |
|---|---|
| 1 | 커스텀 exposure 이벤트가 user property 할당 **전에** 발송되어 분석에서 exposure로 안 잡히는 타이밍 문제 |
| 2 | **실험 도중 트래픽 배분 비율 변경** → 유저가 variant 간 "점프" |
| 3 | **exposure window와 analysis window 불일치** — variant별 재방문 패턴이 다르면 불공정 비교 유발 |
| 4 | Variant jumping (익명 상태·device ID 변경 등) |
| 5 | 특정 variant에서만 assignment→exposure 전환율이 다름 |
| 6 | **실험 도중 variant 추가/제거** |
| 7 | **sticky bucketing을 실행 중 켰다/껐다** |
| 8 | 특정 세그먼트(국가·OS·앱버전)에만 영향을 준 인프라 버그·업데이트 |
| 9 | 개별 유저에 대한 **대량 수동 배정(Inclusions 남용)**이 랜덤화를 왜곡 |
| 10 | 첫 실험에서의 계측 버그 |
| 11 | 잦은 로그아웃으로 device ID가 재생성되며 새 버케팅 인스턴스 생성 |
| 12 | exposure 이벤트 누락·불일치 |
| 13 | **fallback variant에 대한 잘못된 exposure 카운팅** |

> **본문 중단 기준에 추가할 원칙**: 2·6·7번은 전부 "실험 중 설정을 만졌다"가 원인이다. 본문 "흔한 실수" 표의 *실험 중 설정 변경* 항목을 툴 레벨에서 재확인한 것으로, **실험 실행 중에는 트래픽 배분·variant 구성·sticky bucketing을 바꾸지 않는다. 바꿔야 하면 중단하고 새 실험으로 재시작한다.** 종료 판단 게이트에 "기간 중 설정 변경 이력이 없는가"를 한 줄 추가하면 G4(외부 이벤트)와 짝을 이룬다.
