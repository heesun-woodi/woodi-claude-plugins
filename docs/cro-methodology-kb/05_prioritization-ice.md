# 05. ICE 우선순위 평가 — 10단계 중 [5단계]

> 한 줄 요약: 그루밍을 마친 PSR 가설들에 Impact·Confidence·Ease를 각각 1~10점으로 매겨 **합산(최대 30점)**하고, QuickWin 규칙으로 스프린트에 태울 조합을 정한다. 점수 자체보다 점수에 도달하는 토론이 본질이다.

---

## 개념·프레임워크

### 1. ICE 프레임워크

가설 백로그의 우선순위를 **합의 가능한 단위**로 정렬하기 위한 표준 스코어링 프레임이다.

| 축 | 정의 | 무엇을 묻는가 |
|---|---|---|
| **I — Impact** | 가설이 성공했을 때 비즈니스 지표에 미칠 영향력의 크기 | Problem이 진짜 사용자의 문제이고 얼마나 많은 사용자가 느끼는가 / Result(지표)가 개선됐을 때 KPI에 얼마나 영향을 주는가 |
| **C — Confidence** | 가설의 성공 가능성에 대한 확신 정도 (근거의 품질과 양) | Solution이 그 Problem을 해결하는 데 얼마나 효과적이고 검증된 솔루션인가 / 목표 Result 값에 대한 근거의 품질은 어떤가 |
| **E — Ease** | 실험을 구현하고 실행하는 데 필요한 리소스와 시간의 난이도 (점수가 높을수록 쉬움) | 이 실험을 런칭하는 데 어느 정도 기간이 필요한가 / 얼마나 많은 사람의 도움이 필요한가 |

### 2. 공식 (정본)

```
ICE = Impact + Confidence + Ease

각 항목 1~10점 → 총점 최대 30점
```

**QuickWin 기준**

```
QuickWin = ICE ≥ 21   또는   (ICE ≥ 15 AND Ease ≥ 8)
```

> **각주 — 공식 통일 이력.** 과거 문서에는 곱셈식 `(I × C × E) / 100` (최대 10점)과 평균식 `(I + C + E) / 3` (최대 10점) 표기가 혼재했다. 곱셈식은 한 항목이 낮으면 총점이 비현실적으로 붕괴하고(예: I=10, C=10, E=3 → 3.0), 평균식은 항목 간 트레이드오프가 점수에 드러나지 않는 문제가 있었다. **합산식(I+C+E, 최대 30점)으로 통일**했다. 과거 문서에서 곱셈식·평균식 점수를 발견하면 원 점수(I/C/E 각 값)를 그대로 두고 총점만 합산으로 재계산한다. 예: 평균식 8.3점 → 합산 25점 / 평균식 8.0점 → 합산 24점.

**QuickWin 규칙의 두 갈래를 이해한다.**

- `ICE ≥ 21` — 세 축이 고르게 높은 가설. 정공법으로 우선 실행한다.
- `(ICE ≥ 15 AND Ease ≥ 8)` — 총점은 중간이지만 **하루 안에 붙였다 뗄 수 있는** 가설. 카피 변경, 색상 변경, 요소 순서 변경 등이 여기 해당한다. 실패해도 리스크가 낮고, 빠르게 학습이 쌓인다. 스프린트에 이런 가설을 1~2개 섞으면 스프린트가 비지 않는다.

### 3. I / C / E 점수 앵커 기준표

팀이 합의해서 조정할 수 있는 기준선이다. Impact는 10/5/1 세 앵커, Confidence·Ease는 4개 밴드(10 / 7~9 / 4~6 / 1~3)로 정의한다. 조정하더라도 최상·중간·최하 앵커는 반드시 문서화한다.

#### Impact — 영향력

| 점수 | 기준 |
|---|---|
| **10** | 지표 20% 이상 개선 예상, 대상 지면 트래픽 대(大) |
| **5** | 지표 10% 개선 예상, 대상 지면 트래픽 중(中) |
| **1** | 지표 5% 미만 개선 예상, 대상 지면 트래픽 하(下) |

세부 평가 요소 — 실무에서는 아래 3요소로 쪼개 근거를 남긴다.

| 평가 요소 | 확인 사항 |
|---|---|
| 전환 퍼널 위치 | 상위 퍼널일수록 영향 범위가 크다 |
| 영향받는 트래픽 | 대상 지면·세그먼트의 월 UV, 전체 대비 비중 |
| 예상 개선 효과 | Baseline → Target 개선폭, Uplift 시뮬레이션 결과 |

**가중 규칙.** BIAS Block 단계 문제는 Impact +2 가중을 적용한다. 앞 단계 실패가 뒤 단계 전부를 막기 때문이다. 트래픽 볼륨이 압도적으로 큰 지면에도 가중을 줄 수 있으나, 가중 규칙은 팀 내에서 사전 합의하고 문서화한 것만 적용한다.

#### Confidence — 확신 수준

| 점수 | 기준 |
|---|---|
| **10** | "하면 무조건 성공한다" — 검증된 자사 데이터 있음, 경쟁사 대부분이 하고 있고 성공해본 경험이 있음 |
| **7~9** | 경쟁사 벤치마크 강함, 신뢰할 만한 레퍼런스 다수 |
| **4~6** | 좋은 사례가 있는 수준 — 경쟁사 1~2곳이 하고 있거나, Case Study·행동경제학 이론 수준의 근거 |
| **1~3** | 근거 부족, "그냥 고쳐졌으면 좋겠다" 수준의 직관 |

#### Ease — 구현 용이성

| 점수 | 기준 (워킹데이 기준) |
|---|---|
| **10** | 당일 바로 구현 가능, 실험 담당자 혼자 구현 — 카피·색상 변경 등 |
| **7~9** | 2~3일 내 구현 가능, 담당자 중심에 소폭 지원만 필요 |
| **4~6** | 5일 이내(=1주일), 시안 디자인 및 개발 도움 필요 |
| **1~3** | 10일 이상(=2주일 이상), 대규모 개발 필요 |

Ease는 개발 공수만이 아니라 **인프라·내부 승인을 포함한 종합 코스트**로 본다. 개발이 30분이어도 법무 검토가 2주 걸리면 Ease는 낮다.

### 4. I 점수와 C 점수는 어디서 오는가 — 앞 단계와의 연결

ICE는 별개의 평가 활동이 아니라, **2·3·4단계 산출물을 점수로 환산하는 절차**다. 근거 없이 매긴 점수는 회의실 목소리 크기 싸움이 된다.

```
[2단계] 문제정의 + Validation
   → 진짜 문제 근거(정성·정량) + 비싼 문제 근거(Uplift 시뮬레이션)
   → 문제 Impact 점수
                         ↓
                    ICE의 I 점수

[3단계] 솔루션 아이데이션 + Rationale
   → 경쟁사 UX / 지식 레퍼런스 / 자사 과거 실험 / UT / 행동경제학
                         ↓
                    ICE의 C 점수

[3단계] Variant MVP 축소 + [6단계] 구현 방식 판단
   → 실험 툴 단독 구현 가능 여부, 디자인·개발 의존성
                         ↓
                    ICE의 E 점수
```

| ICE 축 | 근거의 출처 | 근거가 없을 때 |
|---|---|---|
| **Impact** | 2단계 문제 Impact 점수 — 경험자 수 × 개선 gap × 심각도, Uplift 시뮬레이션 | 1~3점을 넘길 수 없다. 트래픽 실측 없이 "많을 것 같아서" 10점은 방어 불가 |
| **Confidence** | 3단계 Solution Rationale — 근거 유형별 레퍼런스 | 1~3점. Rationale 없는 가설은 스프린트에 태우지 않는다 |
| **Ease** | 3단계 MVP 축소 결과 + 지원 부서 검토 | 실험 담당자 단독 판단은 과대평가되기 쉽다. 스프린트 플래닝에서 개발자가 조정한다 |

**실무 함의.** Impact 10점을 받고 싶으면 회의에서 주장하는 게 아니라 2단계로 돌아가 트래픽·Gap·Uplift를 실측한다. Confidence를 올리고 싶으면 경쟁사 스크린샷 3장을 찾아온다. **ICE는 점수를 매기는 활동이 아니라, 점수를 올리기 위해 근거를 찾게 만드는 장치다.**

### 5. 운영 원칙 — 점수보다 토론이 본질

ICE 점수는 정밀 측정이 목적이 아니다. **단순 합산 점수가 아닌 합의 도구로 사용한다. 점수 자체보다 점수에 도달하는 토론이 본질이다.**

| 유의사항 | 의미 |
|---|---|
| 빠른 우선순위용 프레임워크 | 정밀 점수 산출이 목표가 아니다. 소수점 논쟁은 시간 낭비 |
| 팀원 주관에 따라 갈린다 | 점수 산정 기준을 팀 내에서 합의해야 잘 쓰인다. 앵커 기준표를 팀 문서로 고정 |
| 조직 상황에 맞춰 조정 | 조직의 목표 지표와 상황에 맞게 기준을 정해 사용. 정해진 정답 없음 |
| 사람이 최종 검토 | 점수는 가정값이다. 자동 정렬 결과를 그대로 실행하지 않는다 |

**운영 방식 — 개인 스코어링 → 스쿼드 조정 토론**

1. **개인 스코어링 (비동기).** 각자 백로그의 가설에 I/C/E를 매기고, 각 점수의 근거를 한 줄씩 적는다. 남의 점수를 보기 전에 매긴다(앵커링 방지).
2. **점수 분산 확인.** 같은 가설에 점수가 크게 갈린 항목을 찾는다. **점수가 갈린 지점이 토론할 지점이다.** 모두가 같은 점수를 준 항목은 논의하지 않는다.
3. **스쿼드 조정 토론.** 최고점을 준 사람과 최저점을 준 사람이 각각 근거를 말한다. 대개 "서로 다른 정보를 갖고 있어서" 점수가 갈린다. 정보를 합치면 자연스럽게 수렴한다.
4. **Ease는 지원 부서가 확정한다.** 실험 담당자가 매긴 Ease는 낙관 편향이 있다. 디자이너·개발자가 참석해 조정한다.
5. **조합 확정.** 스프린트 캐파 안에서 QuickWin 1~2개 + 큰 가설 1개 식으로 섞는다.

조직별 변형은 자유롭다 — 시트 평균 방식, 즉석 경매식(각자 포인트를 배분) 등. 중요한 것은 **점수가 갈린 지점을 그냥 평균 내지 않는 것**이다.

### 6. 스프린트 플래닝(선정 미팅)에서의 사용

| 항목 | 내용 |
|---|---|
| 참석 | 실험 담당자, 디자이너, 서비스 기획자, 개발자 |
| 진행 | ① 상위 가설(1~2개)을 실험설계서 초안(배경·목표·실험군 아이디어)으로 설명 → ② ICE 점수를 기준에 맞춰 논의·조정 → ③ 구현 난이도(Ease)를 지원 부서와 검토해 스프린트 내 진행 가설 조합 확정 |
| 산출 | 이번 스프린트 실험 목록 + 각 실험의 담당자·구현 방법 |

## 절차

### Step 1. 백로그 등록 — 메타데이터 표준 7필드

가설을 백로그에 넣을 때 아래 7개 필드를 채운다. 이 필드가 비어 있으면 ICE 점수를 매길 수 없다.

| 필드 | 설명 |
|---|---|
| **문제정의 (P)** | 어떤 사용자의 어떤 Pain-point에 대한 것인가 |
| **관련 지표** | 골트리(Goal Tree)의 어느 노드에 연결되는가 — NSM / Reach / Activation / Retention 등 |
| **기대효과 (R)** | 성공 시 해당 지표에 어떻게 기여하는가 |
| **구현 난이도** | 개발·인프라 관점의 코스트 |
| **설득 필요도** | 의사결정권자·인접 부서 합의에 필요한 작업량 |
| **검증 방식** | A/B 테스트 / MVP 노출 / 사전예약 / 인터뷰 / 증분실험 |
| **ICE 스코어** | I, C, E 각 점수 + 종합 |

"설득 필요도"가 별도 필드인 이유: 개발 난이도는 낮은데 조직 합의가 어려운 가설(가격 표기 변경, 브랜드 톤 변경 등)이 실제로 스프린트를 지연시킨다. Ease에 뭉뚱그리면 놓친다.

### Step 2. 개인 스코어링

각자 I/C/E를 매기고 근거 한 줄을 남긴다. 근거 없는 점수는 무효로 처리한다.

### Step 3. 점수 분산 확인 → 토론

갈린 항목만 토론한다. 정보 격차를 메우고 재조정한다.

### Step 4. 합산 + QuickWin 판정

ICE = I + C + E. QuickWin 규칙(ICE≥21 또는 ICE≥15 & Ease≥8)을 적용해 태그를 붙인다.

### Step 5. 그루밍 리뷰 (점수를 올릴 여지 확인)

낮은 점수의 원인을 진단하고 보완 방향을 제시한다.

| 낮은 항목 | 조언 |
|---|---|
| Confidence 낮음 | "유사한 성공 사례나 경쟁사 레퍼런스를 더 찾아보세요" — 3단계 Rationale로 되돌림 |
| Impact 낮음 | "영향받는 트래픽이 더 큰 지면이나, 더 근본적인 고객 문제를 찾아보세요" — 1·2단계로 되돌림 |
| Ease 낮음 | "MVP 관점에서 솔루션을 재설계하거나, 구현·QA 난이도가 낮은 화면을 대상으로 바꿔보세요" |

### Step 6. 스프린트 조합 확정

캐파 안에서 QuickWin과 큰 가설을 섞는다. 지원 부서가 Ease를 최종 확인한다.

### 템플릿 3. 그루밍 리뷰 체크리스트 (5단계 19항목)

문서 단계에 따라 기준을 차등 적용한다.

> **문서 단계 확인 — 리뷰 시작 전 반드시 판정한다**
> - **가설 아이데이션**: 초기 아이디어 단계 (완화된 기준)
> - **그루밍 진행중**: 상세화 진행 단계 (표준 기준)
> - **실험 준비 완료**: 런칭 직전 단계 (엄격한 기준)

#### 1단계: 고객 문제 정의 (3항목)

- [ ] **1-1** 고객 관점의 언어인가 — 공급자 언어("구매 전환율이 낮다")가 아닌 고객 경험("왜 구매해야 하는지 모른다")으로 정의되었는가
- [ ] **1-2** 문제 주체가 명확한가 — "고객은…", "방문자는…" 등 주체가 명시되어 있는가
- [ ] **1-3** 문제 상황이 구체적인가 — 언제, 어디서, 무엇을 하다가 문제를 겪는지 명시되어 있는가

#### 2단계: 문제 검증 (4항목)

- [ ] **2-1** 정성적 근거가 있는가 — UT·인터뷰·VOC·서베이 1개 이상
- [ ] **2-2** 정량적 근거가 있는가 — 퍼널 분석·코호트 분석·히트맵 1개 이상
- [ ] **2-3** 벤치마크 비교를 했는가 — 산업 평균·경쟁사·과거 데이터
- [ ] **2-4** 비즈니스 임팩트 시뮬레이션을 했는가 — Uplift 시뮬레이션

평가 가이드: 2-1·2-2 중 하나라도 없으면 **Critical**. 2-3·2-4가 없으면 **Recommended**.

#### 3단계: 솔루션 제안 및 근거 (4항목)

- [ ] **3-1** Variant 2개 이상인가 — Control 외 최소 2개 (문서 단계별 차등)
- [ ] **3-2** 성공 근거(Rationale)가 있는가 — 경쟁사 UX·성공 사례·행동경제학 1개 이상
- [ ] **3-3** BIAS 전술이 적절히 매칭되었는가 — 문제 단계와 적용 전술이 논리적으로 일치하는가
- [ ] **3-4** Counter Rationale이 있는가 — 실패 가능성·리스크를 검토했는가 (문서 단계별 차등)

3-3 판정 기준: BIAS 전술 명시 + 문제 단계 일치 → Pass / 전술 미명시 + 레퍼런스 충분 → Pass / 전술 미명시 + 레퍼런스 부족 → Fail / **Block 문제에 Social Proof만 적용 → Fail(단계 불일치)**.

#### 4단계: 결과 지표 설정 (5항목)

- [ ] **4-1** Primary Metric이 설정되었는가 — 핵심 성공 지표 1개
- [ ] **4-2** Secondary Metric이 설정되었는가 — 행동 관찰 지표 1개 이상
- [ ] **4-3** Guardrail Metric이 설정되었는가 — 부작용 방지 지표 1개 이상
- [ ] **4-4** Baseline이 명시되었는가 — 현재 수준(%)
- [ ] **4-5** Target이 명시되었는가 — 목표 수준 및 개선율

4-1이 없으면 **Critical**. 4-2~4-5는 2단계 평가를 적용한다.

```
1단계: 본문에 개념이 있는가?
2단계: 양식 섹션에 기재되었는가?

- 개념 없음                → Fail (Critical)
- 개념 있음 + 양식 미기재  → Warning (등급 산정 시 Pass로 카운트)
- 개념 있음 + 양식 기재    → Pass
```

#### 5단계: 가설 문장 및 모형화 (3항목)

- [ ] **5-1** PSR 형식을 준수하는가 — "P를 S로 바꾸면 R이 개선될 것이다" 구조
- [ ] **5-2** 변수 관계가 명확한가 — 독립변수(솔루션)와 종속변수(지표)의 인과관계
- [ ] **5-3** 측정 가능한 수치가 있는가 — 구체적 % 또는 수치

#### ICE 점수 검증 (별도 3항목)

- [ ] **ICE-1** 계산이 정확한가 — **ICE = I + C + E (최대 30점)**이며 총점이 기재되어 있는가
- [ ] **ICE-2** Impact 근거가 있는가 — 트래픽 규모, 예상 개선율 근거
- [ ] **ICE-3** Confidence 근거가 있는가 — 레퍼런스, 경쟁사 사례, 과거 경험

> 원본 리뷰 가이드라인에는 ICE-1이 평균식 `(I+C+E)/3`으로 기재되어 있었으나, 정본 합산식으로 갱신했다.

### 문서 단계별 차등 기준

| 체크 ID | 가설 아이데이션 | 그루밍 진행중 | 실험 준비 완료 |
|---|---|---|---|
| 3-1 (Variant 수) | Variant 1개 OK (Recommended) | Variant 2개 필수 (Critical) | Variant 2개 + 시안 필수 (Critical) |
| 3-4 (Counter Rationale) | Optional | Recommended (없으면 Warning) | Critical (없으면 Fail) |
| 4-2, 4-3 (Secondary·Guardrail) | Optional | 개념 필요 | 양식 기재 필수 |
| 4-4, 4-5 (Baseline·Target) | 개념만 OK | 개념 필요 | 양식 기재 필수 |

### 리뷰 피드백 등급 — Critical / Recommended / Optional

리뷰 결과는 항목별 Pass/Fail이 아니라 **보완 우선순위 등급**으로 전달한다. 수정 순서가 명확해야 리뷰가 실제 개선으로 이어진다.

| 등급 | 정의 | 전달 방식 |
|---|---|---|
| **Critical** (필수 보완) | Fail이면서 가설 품질에 치명적인 영향을 주는 항목. 이 상태로는 실험을 설계할 수 없다 | "지금 바로 수정해야 할 것" — 항목별 예상 소요 시간과 수정 후 예상 등급을 함께 표시 |
| **Recommended** (권장 보완) | Fail이지만 보완 시 품질이 향상되는 항목. 없어도 실험은 가능하나 ICE 점수가 낮게 유지된다 | "그루밍 미팅 전 추천" |
| **Optional** (선택 보완) | 있으면 좋지만 필수는 아닌 항목. 주로 문서 단계가 초기일 때 적용 | 목록으로만 제시 |

**등급 산정 로직 요약**

```
그루밍 품질 점수 = (Pass 항목 수 / 전체 체크 항목 수) × 100%
  - Warning은 Pass로 카운트한다(권장 보완으로 별도 표시)
  - 문서 단계에 따라 Optional 항목은 분모에서 제외한다
```

| 종합 등급 | 점수 범위 | 상태 | 다음 액션 |
|---|---|---|---|
| **A** | 90% 이상 | 실험 진행 가능 | 런칭 준비, 경미한 Warning만 수정 |
| **B+** | 80~89% | 경미한 수정 후 진행 | Critical만 수정 후 재검토 |
| **B** | 70~79% | 보완 후 진행 | Critical + 상위 2개 Recommended 수정 |
| **C** | 50~69% | 상당한 보완 필요 | 재그루밍 권장, Critical 반드시 보완 |
| **D** | 50% 미만 | 가설 재수립 권장 | Problem 정의부터 재검토 |

리뷰 산출물에는 다음 4가지를 함께 담는다: ① 종합 등급 + 품질 점수(Pass 수/전체 수) ② Critical / Warning / Pass 건수 ③ 등급별 수정 체크리스트 ④ ICE 요약(I·C·E·총점·QuickWin 여부).

## 워크드 예시

### 예시 1. 같은 가설, 그루밍 전후 ICE 변화 (가상 예시 — 오디오 강의 앱)

> 설명을 위해 지어낸 가상 예시다. 업종·근거 모두 실제 사례가 아니다.

**가설**
> "오디오 강의 앱에서 첫 무료 강의를 끝까지 들은 비구독자에게 같은 시리즈의 다음 강의 1개를 무료로 열어 주면 두 번째 강의 재생 시작률이 20% 오를 것이다"

**그루밍 전**

| 축 | 점수 | 당시 판단 |
|---|---:|---|
| Impact | 4 | "무료 강의 완주자가 적지 않을 것이다" — 근거 수치 없음 |
| Confidence | 3 | "무료로 하나 더 주면 더 듣겠지" — 참고 사례 없음 |
| Ease | 7 | 실험툴만으로 만들 수 있어 보임 |
| **ICE** | **14** | QuickWin 기준 미달 → 이번 스프린트 제외 |

**그루밍 후**

| 축 | 점수 | 새로 확보한 자료 |
|---|---:|---|
| Impact | 8 | 첫 강의를 끝까지 들은 비구독자 수 실측 + 첫 강의 → 두 번째 강의 구간 이탈이 퍼널에서 가장 큼 + 재생 시작률이 20% 오를 때의 구독 증분을 보수·중도·낙관으로 추정한 Uplift 시뮬레이션 |
| Confidence | 7 | 동종 학습 앱 3곳이 「다음 강의 미리 열기」류 장치를 쓰고 있음(화면 캡처 확보) + 시리즈 진행도를 보여주는 Goal Gradient 전술 + 자사 과거 실험의 시리즈 진행 표시 클릭 데이터 |
| Ease | 8 | 개인 맞춤 추천을 빼고(MVP 축소) 같은 시리즈 다음 강의를 고정으로 열어 실험툴만으로 구현 |
| **ICE** | **23** | QuickWin(ICE ≥ 21) 충족 → 다음 스프린트에 편성 |

**변한 것은 근거뿐이다. 가설 문장은 한 글자도 바뀌지 않았다.** 이것이 그루밍의 정의다.

### 예시 2. 자사 — 블로그 하단 맥락 기반 CTA

> 자사 블로그를 소재로 한 예시이며 수치는 설명용 가상값이다.

| 항목 | 점수 | 근거 |
|---|---:|---|
| **Impact** | 10 | 전환 퍼널 위치: 최상위 퍼널(CTA 클릭 → 데모 → 계약) +3 / 영향 트래픽: 블로그 4,800 UV/월, 사이트 45% +4 / 예상 개선: 0.25% → 1.5%(6배), 연간 +11.25억원 +3 |
| **Confidence** | 8 | 데이터 근거: Mixpanel 퍼널 99.75% 이탈 확인 +3 / 행동과학: Goal Gradient + Framing + Social Proof 복합 +3 / 업계 벤치마크: B2B 블로그 CTA 표준 패턴, 개인화 +202% +2 |
| **Ease** | 7 | 개발 복잡도: JS로 CTA 카드 삽입 + 카테고리 감지 로직 +3 / 디자인: 기존 버튼 스타일 재활용 +2 / 의존성: 블로그 카테고리 메타데이터 존재 확인 필요 +2 |
| **ICE** | **25 / 30** | **QuickWin (ICE ≥ 21)** |

> 원본 설계서에는 `(10+8+7)/3 = 8.3`으로 기재되어 있으나 정본 합산식으로 환산해 25점으로 표기한다.

**Impact 10점이 방어 가능한 이유:** 세 근거가 모두 실측이다. 트래픽 영향 규모(Mixpanel 30일 실측), 벤치마크 Gap(업계 중앙값 대비 10배), 정성 심각도(CRO Checklist Fail 86%, BIAS Block 9/10). 회의에서 "정말 10점이냐"는 질문이 나오면 이 세 줄로 답한다.

### 예시 3. 자사 — 블로그 ATF 가치 제안 배너

| 항목 | 점수 | 근거 요약 |
|---|---:|---|
| **Impact** | 9 | ATF는 블로그 방문자 100%가 보는 영역, 최상위 퍼널 |
| **Confidence** | 7 | 자체 데이터 없음, 업계 벤치마크 기반. Block 단계 문제는 VP 추가로 해결되는 것이 검증됨. 동일 도메인 실험은 미진행 |
| **Ease** | 8 | 실험툴 Code Editor로 DOM 삽입, 프론트엔드 변경만으로 완결, 의존성 없음 |
| **ICE** | **24 / 30** | **QuickWin (ICE ≥ 21)** — Ease 8이므로 `ICE≥15 & Ease≥8` 조건으로도 성립 |

이 사례는 **Confidence 7의 정직한 사용법**을 보여준다. 자사 데이터가 없다는 사실을 근거란에 그대로 적었다. Confidence를 부풀리지 않았기 때문에, 실험이 실패해도 "왜 실패했나"를 추적할 수 있다.

### 예시 4. 점수가 갈렸을 때의 토론 (진행 예시)

| 참여자 | Impact | 근거 |
|---|---:|---|
| 실험 담당자 | 9 | "메인 화면이라 트래픽이 제일 큼" |
| 데이터 분석가 | 4 | "메인 트래픽은 크지만, 이 배너 영역까지 스크롤하는 비율이 30%대" |
| 기획자 | 7 | "스크롤 안 해도 상단에 노출되도록 위치를 바꾸면 됨" |

**토론 결과.** 세 사람의 정보를 합치면 — 현재 위치 기준 Impact는 4~5가 맞고, 위치를 상단으로 옮기면 8이 된다. 그런데 위치 변경은 다른 영역을 밀어내므로 Ease가 떨어지고 Guardrail이 추가된다. 결론: **가설을 두 개로 쪼갠다.** ① 현 위치에서 문구만 변경(Ease 9, Impact 5) ② 위치 이동 포함(Ease 5, Impact 8). ①을 QuickWin으로 먼저 돌리고, 결과를 근거 삼아 ②의 Confidence를 올린다.

평균을 내서 6.7점으로 정리했다면 이 결론에 도달하지 못했을 것이다. **점수가 갈린 지점이 설계를 바꾼다.**

## 코칭 활용 포인트

### 세션 운영

- **공식 통일부터 선언한다.** 조직 내 기존 문서에 곱셈식·평균식이 섞여 있으면 반드시 첫 슬라이드에서 정리한다. "오늘부터 ICE는 합산 30점 만점"을 명시하지 않으면 세션 내내 계산이 어긋난다. 기존 문서의 점수는 I/C/E 원 점수만 살려 재계산하면 된다고 안내한다.
- **앵커 기준표를 팀 문서로 만드는 시간을 세션에 배정한다.** 10/5/1 기준을 조직 상황에 맞게 조정하는 작업 자체가 워크샵의 산출물이다. "트래픽 대(大)는 월 몇 UV인가"를 그 자리에서 정한다.
- **개인 스코어링을 반드시 비동기로 먼저 시킨다.** 회의실에서 같이 매기면 목소리 큰 사람 점수로 수렴한다. 사전에 시트를 돌리고, 세션에서는 분산이 큰 항목만 다룬다. 세션 시간이 절반으로 줄어든다.
- **분산 히트맵을 준비한다.** 가설 × 참여자 매트릭스에서 표준편차가 큰 칸을 색으로 표시해 오면, 토론할 지점이 한눈에 보인다.
- **Ease는 개발자를 반드시 참석시킨다.** 담당자 단독 Ease는 평균 2~3점 과대평가된다. 개발자가 없으면 그 스프린트의 Ease 점수는 전부 보류로 둔다.

### 흔한 수강자 질문

**Q. 왜 합산인가요? 곱셈이 더 변별력 있지 않나요?**
곱셈은 한 항목이 낮으면 총점이 붕괴한다. Impact 10, Confidence 10인데 Ease가 3이면 곱셈식으로는 3.0점이 되어 백로그 최하위로 밀린다. 하지만 실무에서는 "임팩트 크고 확신 높은데 좀 어려운 실험"이야말로 다음 분기에 준비해야 할 가설이다. 합산은 이 트레이드오프를 점수에 남긴다. 대신 "쉬운 실험"을 놓치지 않기 위해 QuickWin 규칙에 Ease 조건(ICE≥15 & Ease≥8)을 따로 뒀다.

**Q. 점수를 소수점까지 매겨도 되나요?**
권하지 않는다. ICE는 정밀 측정 도구가 아니다. 소수점 논쟁에 쓰는 시간을 Confidence 근거 찾는 데 쓰는 편이 점수를 더 크게 움직인다.

**Q. 팀원마다 점수가 너무 다릅니다.**
정상이고, 오히려 이 프레임워크가 작동하고 있다는 신호다. 점수가 갈렸다는 것은 서로 다른 정보를 갖고 있다는 뜻이다. 최고점·최저점을 준 사람이 근거를 말하게 하면 대부분 수렴한다. 수렴하지 않으면 그 항목은 "근거가 부족한 상태"이므로 그루밍으로 되돌린다.

**Q. QuickWin만 계속 돌리면 안 되나요?**
QuickWin만 돌리면 학습이 표면에 머문다. 카피·색상 실험은 빠르지만 조직의 큰 문제를 건드리지 못한다. 스프린트마다 QuickWin 1~2개 + 구조적 가설 1개를 섞는 것을 권장한다.

**Q. ICE 점수가 높은데 실험이 실패했습니다.**
정상이다. ICE는 성공 확률 예측치가 아니라 우선순위 정렬 도구다. 다만 Confidence 8~10을 준 가설이 반복해서 실패한다면 Confidence 앵커 기준이 조직에 맞지 않는 것이다. 회고에서 앵커를 조정한다.

**Q. 백로그가 200개인데 전부 점수를 매겨야 하나요?**
아니다. 먼저 메타데이터 7필드가 채워진 것만 남기고, 나머지는 "아이디어" 상태로 격리한다. 점수는 스프린트 후보(보통 10~20개)에만 매긴다.

### 흔한 실수

| 실수 | 교정 |
|---|---|
| 근거 없이 점수만 기재 | 각 점수에 근거 한 줄을 강제한다. 근거 없는 점수는 무효 처리 |
| Impact를 "느낌"으로 10점 | 2단계로 되돌려 트래픽·Gap·Uplift를 실측한다 |
| Confidence를 희망으로 채움 | "잘 될 것 같다"는 1~3점이다. 레퍼런스 개수로 환산한다 |
| Ease를 담당자 혼자 판단 | 스프린트 플래닝에서 개발자·디자이너가 조정한다 |
| 갈린 점수를 그냥 평균 | 갈린 지점이 토론 지점이다. 평균은 정보를 버린다 |
| ICE 순위대로 기계적 실행 | 점수는 가정값이다. 사람이 최종 검토하고 조합을 짠다 |
| 곱셈식·평균식 문서가 계속 유통됨 | 조직 문서를 일괄 갱신한다. 갱신 전까지는 I/C/E 원 점수만 신뢰하고 총점은 재계산 |
| 백로그 메타데이터 없이 점수만 존재 | 7필드를 채우지 않으면 6개월 뒤 아무도 그 가설을 해석하지 못한다 |
| "설득 필요도"를 Ease에 뭉뚱그림 | 별도 필드로 분리한다. 조직 합의 비용이 실제 지연 원인인 경우가 많다 |
